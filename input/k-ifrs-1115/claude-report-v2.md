# K-IFRS 1115 지식그래프 챗봇 — 상세 제안 보고서 (v2)

본 보고서는 K-IFRS 제1115호(고객과의 계약에서 생기는 수익) 질의응답 시스템의 문제 정의, 솔루션 구조, 차별점, 검증 성과, 확장 로드맵을 기술한다. 독자는 회계법인·재무팀의 도입 의사결정자를 상정하며, 모든 수치는 프로젝트 소스 문서에서 원문 그대로 인용하고 출처를 `[파일명.md]`로 표기한다.

## 1. 문제 제기 — 회계 챗봇에서 치명적인 오류는 "2종 오류"다

**헤드라인:** 일반 LLM은 수익인식 질문에 그럴듯한 답을 즉시 내놓지만, 그 답을 회계 실무에 그대로 쓸 수 없다.
**거버닝 메시지:** 근거 없는 확신(2종 오류)이 부실감사와 재무제표 왜곡으로 이어지므로, 시스템 설계 전체가 2종 오류를 구조적으로 어렵게 만드는 방향으로 편향되어야 한다.

수익인식(K-IFRS 1115)은 실무자가 자주 막히지만, 답을 틀리면 재무제표가 왜곡되는 영역이다 [1_OVERVIEW.md]. 일반 LLM에 물으면 그럴듯한 답을 즉시 내놓지만, 근거 조문을 확인할 수 없고, 매번 답이 달라지며, 기준서에 없는 판단을 지어낸다 [1_OVERVIEW.md]. 회계법인 감사 현장에서 이런 답변을 무비판적으로 수용하면 판단의 근거 자체가 무너진다. 따라서 도구의 가치는 "얼마나 그럴듯하게 답하는가"가 아니라 "얼마나 근거를 추적 가능하게 답하는가"에 있다.

핵심 주장은 세 가지다.

첫째, **회계 도메인에서 위험한 오류는 1종이 아니라 2종이다.** 1종 오류(놓침)는 근거가 있는데 못 찾아 "모른다"고 답하는 것으로, 불편하지만 추가 검토로 해소되는 안전한 실패다. 반면 2종 오류(허위 확정)는 근거가 없거나 틀렸는데 확신에 찬 답을 내놓는 것이며, 회계에서는 이것이 실제 손해 — 부실감사 — 로 이어진다 [1_OVERVIEW.md] [PROJECT_OVERVIEW.md].

둘째, **"환각 0" 주장은 과장이며, 정직한 목표는 "근거 없는 확정을 구조적으로 어렵게" 만드는 것이다.** 이 시스템은 환각 0을 주장하지 않는다고 명시하며, 검증 결과도 재현율로 정직하게 보고한다 [1_OVERVIEW.md]. 이 태도는 검증 설계(자가순환 차단, §11)까지 일관되게 이어진다.

셋째, **원칙은 한 문장으로 수렴한다 — "확실할 때만 확정하고, 애매하면 근거를 보여주며 유보한다."** 이 원칙이 진입부 설계(결정적 그래프 탐색), 답변 유형(확정/조건부/되물음), UI(근거 선행)까지 전 층위를 관통한다 [1_OVERVIEW.md] [5_INTERFACE.md].

- 용어 정의: **2종 오류** = 근거가 없거나 틀렸는데 확신에 찬 답을 내놓는 오류. 1종 오류(놓침)의 반대 방향 실패 [1_OVERVIEW.md].
- 정량 데이터: 오류 위험도 비교 — 1종(놓침)은 "낮음, 추가 검토로 해소", 2종(허위 확정)은 "치명적, 부실감사로 이어짐" [PROJECT_OVERVIEW.md].
- 방법론(문제 인식의 경로): 입력 = 일반 LLM의 수익인식 답변 관찰 → 처리 = 오류를 1종/2종으로 분류하고 위험도 평가 → 출력 = "2종 오류 방지"를 설계 전반의 단일 편향으로 확정 [1_OVERVIEW.md] [PROJECT_OVERVIEW.md].
- 예상 반론과 대응: "유보가 많으면 도구가 답답해진다"는 반론이 가능하다. 실제로 홀드아웃 검증에서 유보 편향(사실관계가 충분한 질문까지 되물음 9건)이 실측되었고, 프롬프트 재균형으로 "결정적 사실이 주어졌으면 확정, 진짜 없을 때만 조건부"로 교정했다 [4_SEARCH-PIPELINE.md] [08-routing-rebalance-verify.md]. 즉 유보 편향은 방치가 아니라 측정·교정의 대상이다.
- 비교 벤치마크: 일반 LLM 대비 — 범용 챗봇은 "근거 조문 확인 불가, 답변 비일관, 없는 판단 창작"의 세 결함을 갖는다 [1_OVERVIEW.md]. 본 시스템은 이 세 결함 각각에 구조적 대응(그래프 근거 경로, 구조화 출력, 판단트리 앵커)을 배치한다.

## 2. 문제 제기 — 임베딩 유사도 RAG의 구조적 한계

**헤드라인:** 일상어 질문과 법조문체 기준서의 임베딩 유사도는 절대값 0.29~0.47에 불과해, 라우팅이 근소한 점수 차 싸움이 된다.
**거버닝 메시지:** "비슷한 것"을 찾는 확률적 검색은 회계 기준서처럼 명시적 구조를 가진 도메인에서 설명 불가능성과 비결정성이라는 이중 결함을 낳는다.

이 프로젝트의 초기 구조는 벡터 임베딩 유사도로 관련 문서를 찾는 전형적 RAG였다 [1_OVERVIEW.md]. 4단계 발전을 거치며 검색 구조는 "벡터 임베딩 + BM25 + RRF 결합 + weight_score 가중치 + 핀포인트 + Cohere 리랭커 + 26토픽 판단트리"라는 복합체가 되었고, 적중률과 환각 방지 지표는 좋아 보였다 [7_JOURNEY.md]. 그러나 그 안에 네 가지 균열이 있었고, 균열은 전부 한 방향 — 확률적 신호가 명시적 구조를 뭉개고 있다 — 을 가리켰다 [7_JOURNEY.md].

핵심 주장 네 가지가 균열 각각에 대응한다.

첫째, **리랭커가 정답을 떨어뜨린다.** Cohere 리랭커는 query-document 표면 유사도로 정렬하는데, 전문가 배정 큐레이션 문서가 유사도가 낮아 105건 중 103건이 탈락했고, 이를 bypass로 우회하고 있었다 — "유사도 필터가 정답을 거른다"는 신호였다 [7_JOURNEY.md].

둘째, **가중치에 근거가 없다.** weight_score는 "왜 이 문단이 3점인가"를 설명하지 못했다. 검색 순위를 좌우하는 값이 근거 불명이면, 답변의 근거 경로 전체가 설명 불가능해진다 [7_JOURNEY.md].

셋째, **유사도 라우팅이 비결정적이다.** 키워드+LLM+임베딩 3중 매칭에서 신호가 서로를 압도해, 동일 질문에 토픽이 바뀌면 답도 바뀌었다 [7_JOURNEY.md]. 임베딩 유사도의 절대값 자체가 0.29~0.47로 낮아(tree_matcher 실측) 라우팅이 근소한 점수 차이 싸움이 되고, 왜 그 문서가 뽑혔는지 설명이 불가능했다 [00-overview.md] [1_OVERVIEW.md].

넷째, **문제의 본질은 도메인 구조의 방치다.** 회계 기준서는 5단계 수익인식 모형, 문단 상호참조("문단 47~72 참조"), 부록B가 본문에 매달리는 관계 등 관계가 명확한 구조인데, 이 명시적 구조를 확률적·근거 불명 신호로 뭉개고 있었다 [7_JOURNEY.md] [1_OVERVIEW.md].

- 용어 정의: **RAG**(Retrieval-Augmented Generation) = 외부 문서를 검색해 LLM 답변의 근거로 주입하는 방식. **리랭커** = 검색된 후보 문서를 관련성 점수로 재정렬하는 모듈.
- 정량 데이터: 임베딩 유사도 절대값 0.29~0.47 [00-overview.md]; 리랭커에서 큐레이션 문서 105건 중 103건 탈락 [7_JOURNEY.md].
- 방법론(균열 진단): 입력 = 기존 파이프라인의 운영 관찰(리랭커 bypass, 동일 질문 상이 답변) → 처리 = 균열 4건을 원인 단위로 분해하고 공통 원인 도출 → 출력 = "명시적 구조를 그대로 쓰는" 전환 결정 [7_JOURNEY.md].
- 예상 반론과 대응: "임베딩을 버리면 사전에 없는 표현의 질문을 놓친다"는 반론이 있다. 설계는 이를 인지하고, 사전에도 안 걸리고 LLM도 개념을 못 찾는 극단 질문은 임베딩을 되살리는 대신 실패 사례 기반으로 사전·예외간선을 보강하는 방침을 확정했다(0.29~0.47 유사도 문제의 뒷문 차단) [00-overview.md]. 실측으로도 개념 진입은 이미 55/57(96.5%)로 병목이 아니었다 [7_JOURNEY.md].
- 비교 벤치마크(전환 전/후): 리랭커·가중치·RRF·BM25·HyDE·3중 유사도 매칭 전부를 그래프 위상 순서·개념 계층·용어사전 substring으로 대체했다 [7_JOURNEY.md].

## 3. 문제 제기 — AI 생성 큐레이션과 PDF 파싱의 신빙성 부재

**헤드라인:** 토픽 구분·판단 트리·섹션 분할이 전부 사람 검증 없는 AI 생성물이었고, 이것이 틀리면 답변 내용 자체가 오염된다.
**거버닝 메시지:** 문제는 "AI가 지어냄"이 아니라 "딸깍 생성물을 검수 없이 신뢰"한 것이며, 데이터 원천(PDF 파싱)의 비재현성까지 겹쳐 지식 기반의 뿌리가 흔들리고 있었다.

기존 구조의 두 번째 문제는 AI 생성 큐레이션의 신빙성 부재였다. 토픽 26개 구분, 디시전 트리(체크리스트·결론 가이드), topics.json 섹션 분할이 전부 AI 생성물이며 사람 검증을 거치지 않았다 [00-overview.md]. 이 산출물이 틀리면 프롬프트에 틀린 판단 기준이 주입되어 답변 내용 자체가 오염된다 [1_OVERVIEW.md]. 데이터 원천에서도 문제가 있었다. 기준서를 PDF 파싱으로 추출했을 때 볼 때마다 새로운 오류(HTML 태그 혼입·표 구조 손실·문단번호 불일치)가 나왔고, 사후 패치가 정상 문단까지 손상시켰다 [2_DATA-TAXONOMY.md].

핵심 주장은 세 가지다.

첫째, **미검수 AI 산출물은 검증된 자산과 신빙성이 근본적으로 다르다.** 판단 트리는 3AI 교차생성 결과물을 기준서 원문 대조 없이 신뢰한 것이었다. 문제의 본질은 AI 사용 자체가 아니라 검수 부재다 [7_JOURNEY.md].

둘째, **"내가 관계를 설계했다"고 말할 수 없는 지식 기반은 공허하다.** 기존 데이터의 관계는 여러 곳(related_paragraphs JSON, 파이썬 dict의 디시전트리 인용, summary-embeddings의 topic 필드)에 흩어져 암묵적이었고, 사례↔토픽 배정은 AI가 큐레이션한 것이라 설계 주체가 관계를 소유하지 못했다 [00-design-log.md].

셋째, **PDF는 물리 레이아웃을 논리 구조로 변환하는 데 본질적 한계가 있다.** kifrs.com REST API 크롤링으로 전환하자 문단번호와 재현성이 100%가 되었다 [2_DATA-TAXONOMY.md] [7_JOURNEY.md]. 감리지적사례만 공개 API가 없어 LLM으로 수동 JSON 변환했다 [2_DATA-TAXONOMY.md].

- 용어 정의: **큐레이션** = 원천 자료를 선별·분류·요약해 시스템이 소비할 형태로 가공하는 작업.
- 정량 데이터: AI 자의 재분류 토픽 26개(구 체계 29토픽 표기 병존) [00-overview.md] [01-topic-taxonomy-draft.md]; PDF→REST API 전환 후 문단번호·재현성 100% [2_DATA-TAXONOMY.md]; 감리사례 원문은 금감원 PDF 14건 + 한공회 HWP/HWPX 5건으로 git 히스토리에서 복구 가능 [00-design-log.md].
- 방법론(원천 신뢰도 실측): 입력 = findings-final.json의 related_paragraphs와 원문 PDF → 처리 = 대조 1건(FSS-CASE-2022-2311-02)에서 원문 "지적 근거" 인용 조문(문단 9, 31)과 가공본이 정확히 일치함을 확인, 미검증 17건은 분모 명시 → 출력 = "엣지 뿌리가 지어낸 게 아니라 공식 원문 인용 조문"이라는 신뢰 상한 확정, 단 검증 커버리지 1/18로 정직하게 기록 [00-design-log.md].
- 예상 반론과 대응: "1건 일치로 전건을 신뢰할 수 있나"라는 반론이 정당하며, 소스 자체가 "1건 일치 → 전건 일치 일반화 금지"를 명시했다 [00-design-log.md]. 이후 감리 23/23 원문 대조, QNA는 Sonnet 21에이전트 전문 통독 교차검증으로 전수 감사가 완결되었다 [03-cases.md] [2_DATA-TAXONOMY.md].
- 비교 벤치마크(전/후): 26토픽 미검수 판단트리 → 본문·부록B 원문 앵커 판단트리 41개로 대체 [7_JOURNEY.md]; AI 생성 섹션 분할 → 기계 생성 개념 노드의 paras가 대체 [01-concepts.md].

## 4. 솔루션 — 온톨로지 지식그래프: "비슷한 것"이 아니라 "연결된 것"

**헤드라인:** 임베딩 유사도로 "비슷한 문서"를 끌어오던 구조를 걷어내고, 기준서의 명시적 관계 위에서 근거를 결정적으로 탐색한다.
**거버닝 메시지:** 검색 진입부에 확률적 신호(유사도·가중치·리랭커)가 0인 구조 — 노드 4종과 간선 3축의 지식그래프 — 가 설명 가능성과 재현성을 동시에 제공한다.

대안은 회계 기준서가 이미 가진 명시적 구조를 그대로 쓰는 것이다. 5단계 수익인식 모형, 문단 상호참조, 부록B가 본문에 매달리는 관계는 원문에 적혀 있어 확률이 아니라 사실이다 [1_OVERVIEW.md]. 지식그래프는 노드 개념 80 · 문단 250 · 사례 188(QNA 101·감리 22·IE 65) · 용어 423 · BC 그룹 21과 판단트리 41개로 구성되며, 고립 노드 0 — 모든 노드가 최소 하나의 경로로 본문에 닿는다 [0_README.md] [3_KNOWLEDGE-GRAPH.md].

핵심 주장은 네 가지다.

첫째, **노드 4종은 출처와 AI 개입 여부가 명시된다.** 개념(기준서 공식 소제목)은 기계 생성으로 AI 판단 0, 문단은 원문 그대로, 사례는 원문 대조·교차검증분 재사용, 용어만 AI 초안 + 사람 전수 검수(신규 창작 0)다 [2_DATA-TAXONOMY.md].

둘째, **간선 7종은 의미적으로 3개 축으로 수렴하며, 축마다 출처 규칙이 하나다.** 구조축(계층 79·개념→문단 250)은 기계 생성이라 검증 불요, 참조축(E3 상호참조 264·E4 본문↔부록B 3·사례→문단 1,220)은 회계 항등식으로 전수 검증, 의미축(E2 선행판단 7·사례→개념 65)은 사람이 확정한 얇은 층으로 사용자 O/X 전수 검수를 거쳤다 [2_DATA-TAXONOMY.md] [06-graph-audit.md].

셋째, **새 간선은 등록부를 통과해야만 만들 수 있다.** 새 간선 유형은 4항목(답하는 질문·출처·방향·검증)을 먼저 등록해야 추가할 수 있고, 등록하지 못하면 만들지 않는다 [2_DATA-TAXONOMY.md] [06-graph-audit.md]. 이 통제가 "간선 추가의 병목을 축 등록 + 검증 방식으로 묶는 한 복잡도는 통제 하에 있다"는 감사 결론의 근거다 [06-graph-audit.md].

넷째, **그래프 위상 순서가 곧 근거 순위다.** 유사도 정렬도 리랭커도 없이, "이 근거가 왜 왔는지"를 경로로 설명할 수 있다 [3_KNOWLEDGE-GRAPH.md]. 실증 예시로, "밀어내기 매출" 질문이 사례 FSS-CASE-2022-2311-02에 닿으면 그 사례가 지적한 문단 9·31을 타고 같은 문단을 지적한 다른 사례를 추가로 끌어온다 — 텍스트는 안 비슷해도 "법적 이웃"이므로 임베딩이 놓치는 근거를 관계가 잡는다 [3_KNOWLEDGE-GRAPH.md] [00-design-log.md].

- 용어 정의: **온톨로지** = 도메인의 개체(노드)와 관계(간선)를 명시적으로 정의한 지식 체계; **간선(edge)** = 노드 사이의 관계 선.
- 정량 데이터: 노드 개념 80 / 문단 250 / 사례 188 / 용어 423 / BC 그룹 21, 판단트리 41, 고립 노드 0 [0_README.md]; 간선 등록부 기준 hier 79 · cp 250 · e2 7 · e3 244 · case 1,220 · example 74 · term 755 · bc2 41 · bc3 24 [06-graph-audit.md]; 그래프 v14 노드 929 · 간선 2,697 · 끊어짐 0 [04-aliases.md].
- 방법론: 입력 = kifrs.com 크롤링 기준서 파싱본 + 기검증 사례 자산 + 사람 1차 자료 3종 → 처리 = 노드 4종 추출(기계)·간선 3축 생성(기계+검수)·항등식 검증 → 출력 = data/ontology JSON 8종(concepts / edges / case_links / bc_links / aliases / judgment_trees / topic_concept_map / ie-group-concept-map) [2_DATA-TAXONOMY.md] [PROJECT_OVERVIEW.md].
- 예상 반론과 대응: "간선 7종은 과도한 복잡도 아닌가"라는 우려를 감으로 답하지 않고 구조 분석 + 4종 실측으로 판정했다. 결과는 완전 중복 0건, 동일쌍 이형 간선 0건, 고아는 알려진 6건과 정확히 일치 — "위험은 간선 수가 아니라 출처 없는 간선이며, 현재 0건" [06-graph-audit.md].
- 비교 벤치마크: 임베딩 방식("비슷한 것", 유사도 상위 N, 확률적·설명 불가) vs 온톨로지 방식("연결된 것", 명시적 관계, 결정적·경로 제시 가능) [1_OVERVIEW.md].

## 5. 솔루션 — 데이터 구축 방법론: 검사-후-모집단 방지와 회계 항등식

**헤드라인:** 검색 품질은 모델이 아니라 지식을 어떤 구조로 정리했는가가 결정하며, 구축의 매 단계를 "누수 없음"을 증명하는 방식으로 검증했다.
**거버닝 메시지:** 분모를 권위 출처에서 독립 재계수하고, 모든 언급을 항등식으로 전수 계정하며, 원본 PDF로 외부 검증까지 거친 지식 기반이 시스템 신뢰의 뿌리다.

이 프로젝트의 핵심은 데이터와 taxonomy 구축 방법론이다 [2_DATA-TAXONOMY.md]. 개념 노드는 기준서 공식 소제목을 그대로 삼아 최종 80개, 문단 250개 배정(본문 49·부록A 1·부록B 25·부록C 5)이며 [2_DATA-TAXONOMY.md] [01-concepts.md], 문단→소제목 연결은 ref 문자열 파싱이 아니라 documentId를 권위 출처로 삼았다 [01-concepts.md]. E3 상호참조 264개는 검증 완료 문단 250개의 원문에서 "문단+번호" 언급을 정규식 전수 수집한 뒤 회계 항등식 `언급 267 = 내부해소 264 + 타기준서 3 + 미해소 0`으로 검증했다 [2_DATA-TAXONOMY.md] [02-edges.md].

핵심 주장은 네 가지다.

첫째, **분모는 산출물에서 역산하지 않는다(검사-후-모집단 방지).** 개념 노드의 분모 N=251은 필터가 본 것이 아니라 원본 파일 전체 문단 1,298개(권위 출처)에서 도출했고, 번호체계가 본문/B/C인 문단 247개 전원이 수집 범위 안에 있음(누수 0건)을 스크립트가 매 실행마다 재증명한다 [01-concepts.md]. 사례 모집단도 QNA 101·감리 22·IE 65를 권위 출처에서 독립 재계수해 산출물 행수와 1:1 대조했다(101/101, 22/22, 65/65, 잔존 0건) [03-cases.md].

둘째, **음의 공간을 증명한다 — "안 본 곳에 대상이 없음".** 수집 범위 밖에 본문/B/C 문단 0건, 기준서가 선언한 번호 범위(본문 1~129, B1~89, C1~10) 대비 빠진 번호 0건을 두 방향에서 기계 확인했다 [01-concepts.md] [2_DATA-TAXONOMY.md]. 0건 사례도 빈 행으로 출력해 조용한 누락을 막는다 [2_DATA-TAXONOMY.md].

셋째, **JSON 내부 정합에 그치지 않고 원본 PDF로 외부 검증했다.** 원본 PDF 517쪽에서 level 9층 × 각 1개 층위표본(체리피킹 방지를 위해 층 내 문서순 중위 원소 선택)을 대조해 9/9층 PASS를 얻었다 [01-concepts.md] [2_DATA-TAXONOMY.md]. 검사기 자체의 가정이 틀렸던 사례(소제목이 행 시작에 온다는 가정으로 6층 FAIL → 검사 규칙 교체)까지 기록했다 [01-concepts.md].

넷째, **사례 연결은 감사본 단일 원천 원칙을 확정했다.** 초기엔 자체 정규식 추출을 감사본과 합쳤으나, 전행 대조 결과 자체 정규식이 감사본 대비 초과 4건(전부 타기준서 오귀속)을 만들어 감사본을 단일 원천으로 확정하고 정규식은 감사 필드가 없는 IE 전용으로 강등했다 [2_DATA-TAXONOMY.md] [03-cases.md]. 정규식 규칙이 v1→v3로 진화했음에도 감사본 대비 8토큰이 뚫렸다는 사실이 "정규식 추출은 감사를 대체할 수 없다"의 실측 근거다 [03-cases.md].

- 용어 정의: **회계 항등식 검증** = 모든 언급을 "해소 + 외부 + 미해소"로 빠짐없이 분류해 합계가 일치함을 증명하는 전수 계정 방식 [2_DATA-TAXONOMY.md].
- 정량 데이터: 개념 80·문단 250, ref 교차 검증 78/80 대상 전수 불일치 0 [01-concepts.md]; E3 항등식 267=264+3+0, E4 3/80 해소 실패 0, E2 초안 8→7 확정 [02-edges.md]; 사례→문단 1,220개, QNA 커버리지 95/101·감리 22/22·IE 63/65 [03-cases.md]; IE 항등식 `언급 350 = 해소 350 + 외부 0 + 미해소 0` [03-cases.md]; IE 귀속 버그 16건 복구(언급 175→350, 커버리지 49→63/65) [03-cases.md]; BC 652 전수 귀속 미귀속 0, E-BC1 항등식 `341 = 해소 327 + 외부 7 + 미해소 7`, E-BC2 516/652 배정, E-BC3 예약 59건 전부 활성화 [05-bc.md].
- 방법론: 입력 = 기준서 파싱본(kifrs-1115-all.json)·감사본 related_paragraphs·BC 원문 → 처리 = ① type별 중복 제거 ② level 스택 트리 복원 ③ documentId 귀속 ④ 정규식 언급 수집 후 항등식 계정 ⑤ 검수 대상만 사람 판정 → 출력 = STEP별 산출물 JSON + 검증 로그 원문 [01-concepts.md] [02-edges.md] [03-cases.md] [05-bc.md].
- 예상 반론과 대응: "검증 기대값 자체가 틀리면 어떻게 하나" — 실제로 "B21이 문단 47~72를 참조한다"고 기대값을 손으로 썼는데 실제 참조는 B23에 있었던 사례가 발생했고, 이후 "검증 기대값(ripple)조차 손으로 쓰지 않고 원문에서 따온다"를 원칙화했다 [02-edges.md] [3_KNOWLEDGE-GRAPH.md].
- 비교 벤치마크(전/후): E3 외부 참조 오분류가 규칙 강화("기준서 명칭이 문단 직전에 인접할 때만 외부")로 9→3건으로 정제, 전건 원문 확인 [02-edges.md].

## 6. 솔루션 — 런타임 검색 파이프라인: analyze → retrieve → generate → format

**헤드라인:** 질문이 답으로 나가기까지 4개 노드가 순수 Python으로 오케스트레이션되며, 진입부 임베딩 유사도는 0이다.
**거버닝 메시지:** 진입(용어사전 substring + LLM 주제 지목)과 탐색(그래프 1-hop) 모두 결정적 로직이므로 라우팅의 블랙박스가 제거된다.

런타임 노드는 analyze → retrieve → generate → format 4개다. LangGraph를 걷어내고 순수 Python으로 오케스트레이션하며(app/pipeline.py), 각 노드는 부분 dict를 반환해 state에 병합되고 SSE로 진행 상황을 스트리밍한다 [4_SEARCH-PIPELINE.md]. 초기 구조에 있던 rerank 단계는 STEP 5-4에서 제거했다 — 그래프 탐색이 개념→문단·사례를 결정적으로 골라오므로 유사도 재정렬이 불필요하다 [4_SEARCH-PIPELINE.md]. 되물음 후속 턴은 fast-path로 analyze·retrieve를 스킵하고 generate 1회만 실행한다 [4_SEARCH-PIPELINE.md] [PROJECT_OVERVIEW.md].

핵심 주장은 네 가지다.

첫째, **질문을 개념 노드로 잇는 문은 두 개이며 둘 다 임베딩 유사도를 쓰지 않는다.** ① 용어사전 substring 조회(결정적)와 ② analyze LLM(gpt-4.1-mini)의 topic_hints(주제 지목)다. LLM이 고르는 것은 35개 토픽 목록이지 개념 80개가 아니며, 토픽→개념 변환은 topic_concept_map이 결정적으로 수행한다 — LLM이 concept_id를 직접 만들지 않는다 [4_SEARCH-PIPELINE.md].

둘째, **라우팅 경계는 2중으로 방어한다.** analyze는 범위 판정(IN/OUT)을 겸하며, 타 기준서 전용 용어(예: 1116호 "증분차입이자율")를 감지하면 코드 레벨에서 강제 OUT시킨다 — 프롬프트만으로 놓치는 경계를 이중 방어한다 [4_SEARCH-PIPELINE.md].

셋째, **진입 우선순위가 최종 문서 순서까지 보존된다.** graph.traverse(concept_ids, hops=1)가 개념에서 문단·사례·BC·관련 개념을 수집하고 상호참조 이웃(E3)을 1홉 확장한 뒤, MongoDB `$in` 조회가 입력 순서를 보장하지 않는 문제를 paraNum→doc 딕셔너리 재배열로 해결했다 [4_SEARCH-PIPELINE.md] [07-retrieval-priority.md].

넷째, **배경어 독식 문제를 세 가지 수정으로 해결했다.** 홀드아웃에서 근거 문단 재현이 최저(1.36/2)였고 누락 문단의 45%가 "상한 밀림"이었는데, 원인은 "계약" 같은 골격 용어가 광범위 개념을 진입 앞자리에 독식시키는 것이었다 [4_SEARCH-PIPELINE.md] [07-retrieval-priority.md]. ① topic_hint 우선 진입(LLM 주제 지목을 앞에, 용어사전 배경어를 뒤에) ② fetch 순서 보존 ③ 유형별 슬롯 상한(감리 top-2·IE top-3·QNA top-3, 문단은 상한 없음)으로 대응했다 [4_SEARCH-PIPELINE.md].

- 용어 정의: **SSE**(Server-Sent Events) = 서버가 클라이언트로 진행 상황을 실시간 스트리밍하는 단방향 통신 방식; **substring 매칭** = 문자열 포함 여부로 판단하는 결정적 조회.
- 정량 데이터: 실증(201909A, 항공 연착 보상 질문) — 진입 개념 9개 중 배경어 개념이 [0]·[1]을 차지하고 gold 핵심(변동대가 50~54, 보증 B33)은 [4]·[6]으로 밀려 traverse 문단 99개 중 16~28번째에 위치, generate 상한에 잘림 [07-retrieval-priority.md] [4_SEARCH-PIPELINE.md]; 누락 문단 분류 — 상한 밀림 45% / 검색 실패 33% / 생성 누락 18% / 온톨로지 밖 1% [07-retrieval-priority.md]; 프롬프트 31토픽 중 29개 topic_map 완전 일치(미연결 2개는 `기타`/`Gray Area`로 정상) [07-retrieval-priority.md].
- 방법론: 입력 = 사용자 질문 → 처리 = analyze(개념 진입+IN/OUT 판정) → retrieve(그래프 탐색 + MongoDB 원문 조회: paraNum→메인 컬렉션, db_parent_id→parent 컬렉션) → generate(판단트리 주입 답변 생성) → format(감리사례 넛지·꼬리질문) → 출력 = SSE 스트리밍 응답 [4_SEARCH-PIPELINE.md] [05-pipeline.md] [PROJECT_OVERVIEW.md].
- 예상 반론과 대응: "상한값을 골든셋 점수로 튜닝한 것 아닌가" — 사례·감리 슬롯값은 골든셋 점수가 아니라 비용 예산(입력 약 8K 토큰 목표)으로 정하며, 92건은 재현율 하락만 감시하는 회귀 안전망으로만 쓴다 [4_SEARCH-PIPELINE.md] [07-retrieval-priority.md].
- 비교 벤치마크(대안 신호 비교): 개념 계층 활용은 불가(80개 개념이 거의 평면), 용어 변별력 정렬은 역효과(gold 밀림), 판단트리 트리거는 약함(동점 시 오매칭) — 유효 신호는 LLM 주제 지목(topic_hints) 하나로 수렴했다 [07-retrieval-priority.md].

## 7. 솔루션 — 판단트리 주입과 듀얼 LLM 라우팅

**헤드라인:** 기준서에 흩어진 조건-분기를 원문 앵커와 함께 미리 조립한 판단트리 41개를 주제 기반으로 다중 주입하고, 회계 추론과 산술을 서로 다른 모델에 라우팅한다.
**거버닝 메시지:** LLM이 판단 순서를 매번 다르게 조립하는 비결정성과, 단일 모델로 양립하지 않는 회계 추론·산술 정확도를 각각 구조로 해결했다.

기준서의 판단은 여러 문단에 흩어져 있어("변동대가는 문단 50에서 추정하되, 문단 56 제약을 적용하고…") LLM에게 문단 뭉치만 주면 판단 순서를 매번 다르게 조립한다 [3_KNOWLEDGE-GRAPH.md]. 판단트리는 이 조건-분기 골격을 원문 앵커와 함께 미리 옮겨 둔 것으로, 모든 분기가 기준서 문단 번호를 근거로 가지며 AI 창작 없이 본문·부록B에서 추출했다 [3_KNOWLEDGE-GRAPH.md]. generate 단계에서 `[판단 절차]`로 주입되어 LLM이 판단 순서를 스스로 조립하는 부담을 없앤다 [3_KNOWLEDGE-GRAPH.md].

핵심 주장은 세 가지다.

첫째, **판단트리 선택은 best-1 단일 선택에서 주제기반 다중주입으로 재설계됐다.** 기존 방식은 진입 개념 전체와 트리 trigger의 최다 겹침으로 트리 1개를 골랐는데, subtree로 딸려온 배경 개념이 투표수로 진짜 주제 트리를 밀어내 오선택 14/27, 신규 트리 미주입 17/18이 발생했다. 개선은 via_topic(LLM이 직접 지목한 주제 직속 개념) 하나로만 매칭하고 걸린 트리를 전부 이어붙여 주입한다 — "질문이 여러 개념에 걸치면, 걸린 판단 절차를 모두 넣는다" [4_SEARCH-PIPELINE.md].

둘째, **회계 추론과 산술 정확도는 단일 모델로 양립하지 않는다 — 7개 모델 218회 A/B 테스트의 수렴 결론이다.** 회계 판단 질문은 Gemini Flash(thinking=high, 종합 0.81, 회계 추론 1위, 산술 20~40%)로, 산술 계산 질문은 gpt-4.1-mini(추론 4위, 산술 100%)로 라우팅한다 [6_TEST-DECISIONS.md]. 결정적 증거는 투입법 진행률 문제(정답 500÷2,400=20.83%)에서 Gemini가 분모에서 낭비원가를 빼지 않은 500÷2,500=20.00%를 thinking 강도와 무관하게 반복한 반면 gpt-4.1-mini는 100% 정확했다는 것이다 [6_TEST-DECISIONS.md].

셋째, **"계산 필요?" 판정 자체도 정규식에서 AI 판단으로 바꿔 정확도를 33%→42/42=100%로 올렸다** [6_TEST-DECISIONS.md]. 이 듀얼 라우팅은 검색 계층 아래에 있어 온톨로지 전환 후에도 그대로 유효하다 [6_TEST-DECISIONS.md].

- 용어 정의: **판단트리** = 기준서 조건-분기 골격을 문단 번호 앵커와 함께 사전 조립한 절차 데이터(judgment_trees.json); **듀얼 라우팅** = 질문 유형별로 서로 다른 LLM에 배정하는 방식.
- 정량 데이터: 판단트리는 최초 timing-35 트리 1개 → 본문 검수 추출 23개 → 현재 41개 [3_KNOWLEDGE-GRAPH.md]; 7개 모델 218회 A/B [6_TEST-DECISIONS.md]; 추론 강도 high→medium 조정으로 꼬리질문 일관성 60→100% [6_TEST-DECISIONS.md].
- 방법론: 입력 = 질문 + 수집된 기준서 원문 + 그래프 경로 → 처리 = generate가 3갈래 분기(is_situation→clarify_agent 되물음 / needs_calculation→calc_clarify_agent 산술 / 그 외→generate_agent 확정·조건부) + via_topic 기반 트리 매칭(없으면 concept_ids 폴백) → 출력 = 구조화 답변(결론 + 인용 문단 + 분기) [4_SEARCH-PIPELINE.md].
- 예상 반론과 대응: "트리를 여러 개 주입하면 컨텍스트가 오염되지 않나" — 기준은 배경 개념이 아니라 LLM이 지목한 주제 개념이므로, 다중주입은 무차별 병합이 아니라 주제 정합 트리의 합집합이다 [4_SEARCH-PIPELINE.md]. 판단트리가 정답규칙을 이미 주입하고 있었음에도 미재현으로 남은 케이스(35567)는 기준서 자체의 개념 교차연결이 원인으로, 트리 주입 방식의 결함이 아님이 실측됐다 [7_JOURNEY.md].
- 비교 벤치마크(전/후): 트리 선택 방식 개선 전 오선택 14/27·신규 트리 미주입 17/18 → 주제기반 다중주입으로 재설계 [4_SEARCH-PIPELINE.md]; 산술 정확도는 지시를 줄여야 오른다(중복 포맷 지시 제거)는 ADR도 유효하다 [6_TEST-DECISIONS.md].

## 8. 차별점 — 결정성과 설명 가능성: 유사도 싸움이 사라진 경로

**헤드라인:** "0.43 vs 0.41 도토리 키재기"가 사라지고, 모든 근거에 "이 근거는 이 경로로 왔다"는 설명이 붙는다.
**거버닝 메시지:** 결정적 진입·탐색은 동일 질문에 동일 근거를 보장하며, 이것이 감사 조서에 인용 가능한 수준의 추적성을 만든다.

기존 방식은 질문 전체를 임베딩해 문서 200개와 유사도를 계산하는 "0.43 vs 0.41 도토리 키재기"였고, 전환 후에는 질문→용어 건지기→사전 확정 매칭→선 따라 수집으로 점수 경쟁 자체가 없다 [90-diagrams.md]. AI 개입은 2곳(개념 추출, 답변 생성)으로 한정되고 나머지는 결정적 코드다 — 틀리면 사전이나 선을 고치면 된다 [90-diagrams.md] [00-overview.md].

핵심 주장은 세 가지다.

첫째, **개념 계층이 질문의 구체성과 정합하는 진입 지점을 제공한다.** 기준서 목차의 들여쓰기 깊이가 그대로 level이 되어(본문 1~5, 부록 1.5~4.5), level 2 [측정]은 문단 45개를 관할하는 넓은 노드, level 5 [변동대가 추정치를 제약함]은 문단 3개를 관할하는 좁은 노드다. "리베이트 상한" 질문은 level 5 노드에 콕 꽂힌다 [90-diagrams.md].

둘째, **근거 경로가 사용자에게 그대로 제시된다.** 질문 진입 개념에서 관할 문단(cp 간선), 상호참조 이웃 문단(E3), 소속 사례(case), BC 그룹, 관련 개념(계층·E2)으로 수집 경로가 명시된다 [3_KNOWLEDGE-GRAPH.md]. "고객사에 리베이트 주기로 했는데 매출 얼마로 잡아야 해요?" 질문이라면 리베이트→[고객에게 지급할 대가]·[변동대가] 사전 조회 → 문단 70,71,72 + E3로 문단 50~59 → IE·QNA 사례 수집이라는 경로가 남아 "왜 이 문서?"에 답할 수 있다 [90-diagrams.md] [00-overview.md].

셋째, **동명이인·교차연결 같은 미묘한 함정을 교차검증이 잡는다.** 개념 80개 중 유일한 동명이인 쌍("기간에 걸쳐 이행하는 수행의무"가 본문과 부록B에 각각 존재)에서 IE 그룹 매핑이 부록B를 임의 선택한 실결함 1건을 축 간 교차검증이 적발해 본문으로 확정했고, 수정 후 축 간 일치가 54→57로 올랐다 [06-graph-audit.md] [3_KNOWLEDGE-GRAPH.md].

- 용어 정의: **결정적(deterministic)** = 같은 입력에 항상 같은 출력이 나오는 성질. 확률적 라우팅의 반대.
- 정량 데이터: 축 간 교차검증 57/63 일치(불일치 6건은 다주제 사례의 목차≠인용으로 모순 아님) [3_KNOWLEDGE-GRAPH.md] [06-graph-audit.md]; 부록B↔본문 다리는 E3 상호참조 55선(부록B 문단 96개 중 38개 본문 직결) [06-graph-audit.md]; 허브 분해 — 문단 35 차수 53(case 36 + e3 13 + e4 3 + cp 1)은 실무 분쟁 핵심 문단으로 현실 반영 [06-graph-audit.md].
- 방법론: 입력 = 그래프 전체(노드·간선) → 처리 = 4종 실측 감사(축 간 교차검증 / 고아 전수 / 중복 / 허브 분해) → 출력 = 실결함 1건 적발·수정 + "구조는 건강하다" 판정 [06-graph-audit.md].
- 예상 반론과 대응: "결정적 진입이 오히려 융통성을 잃게 하지 않나" — 용어사전은 확정 라우터가 아니라 후보 진입점으로 설계되어, 한 용어가 여러 개념·사례로 이어질 수 있고 최종 선택은 질문 문맥이 담당한다(다중 목적지 허용) [2_DATA-TAXONOMY.md] [04-aliases.md]. 그래프가 후보를 축소하고 문맥이 선별하는 분업이다 [00-overview.md].
- 비교 벤치마크: 기존 3중 유사도 토픽 매칭(키워드+LLM+임베딩 합산)은 비결정적이라 폐기, 용어사전 substring으로 대체 [6_TEST-DECISIONS.md]; 핀포인트 직접 조회(+40%p 개선 이력)는 교훈만 유효하고 메커니즘은 그래프 탐색으로 대체됐다 [6_TEST-DECISIONS.md].

## 9. 차별점 — AI 개입 최소화 원칙과 환각 방지 레이어

**헤드라인:** AI가 만드는 것은 사람이 전수 검수 가능한 용어 색인 하나로 제한하고, 색인 오류는 "내용 오염"이 아니라 "검색 실패"로 안전하게 드러나게 했다.
**거버닝 메시지:** 오류의 표출 방향을 설계하는 것 — 틀려도 1종 오류(안전)로 무너지게 하는 배치 — 이 환각 방지의 실체다.

신빙성 원칙의 핵심은 배치다. 그래프의 뼈대(개념·개념→문단 연결·상호참조 간선)는 기준서에서 기계 생성하므로 검증 자체가 불필요한 영역이고, AI가 만드는 것은 용어 색인 하나로 한정한다. 색인이 틀리면 "못 찾음(안전한 1종 오류)"으로 드러나고, 뼈대가 AI 생성이었다면 "틀린 근거로 확신(위험한 2종 오류)"이 됐을 것이다 [2_DATA-TAXONOMY.md]. AI 초안은 반드시 사람이 전수 검수 가능한 크기로 만든다 [00-overview.md].

핵심 주장은 네 가지다.

첫째, **용어사전 원천은 사람이 만든 1차 자료 3개뿐이며 AI 신규 창작 용어는 0건이다.** query-mapping 기존 자산 288, QNA·감리 제목 123, 부록A 공식 정의 9가 원천이다 [2_DATA-TAXONOMY.md] [04-aliases.md]. 최종 등재 규모는 용어사전 423 엔트리(자동 316 / 위임판단 86 / 사용자검토 18 / 사용자확정 1 / 제외 2)다 [2_DATA-TAXONOMY.md].

둘째, **검수는 백지 위임이 아니라 근거 부착 제안으로 진화했다.** v1은 미매칭 99건을 백지 목적지로 제시해 반려됐고, v2는 용어가 실제 출현하는 본문 문단의 소속 개념 상위 3개를 근거 문단과 함께 A/B/C로 제시했으며(제안 보유 78건 + 제외 권고 21건 + 자동 316건 구조) [04-aliases.md] [04-aliases-review.md], v3는 78건을 AI가 전수 판단(전부채택 41 + 판단개입 34 + 에스컬레이션 3)하되 행별 `decision{by, dropped, added, reason}` 기록으로 전건 추적 가능하게 했다. 진짜 애매한 3건만 사람이 판정했다 [04-aliases.md].

셋째, **어휘 구멍은 전수 감사로 찾아 규칙 기반으로만 보강했다.** 사례 제목 123건이 실제 주제로 직행하는지 전수 대조한 결과 PASS 62 · MISS 42 · DEAD-END 19였고 [04b-title-topic-audit.md] [04-aliases.md], DEAD-END 19건 중 11단어를 등재하되 3제한(단어는 사례 제목에서만 추출 / 목적지는 감사본 주제 합집합으로 규칙 산출, 수기 지정 금지 / 사례 자체도 목적지 포함)을 지켰다 [04-aliases.md]. MISS는 후보 진입점 원칙상 오류가 아니다 — 사례 경유 2-hop으로 123/123 도달한다 [04-aliases.md].

넷째, **환각 방지는 단일 장치가 아니라 다층 레이어다.** 도메인 큐레이션(체크리스트+결론가이드+선례), PydanticAI 구조화 출력(selected_branches + cited_paragraphs 강제), result_validator(빈 인용/빈 분기 시 ModelRetry 자동 재호출), reasoning_guard(결론가이드에 없는 분기 생성 금지), 선례 원문 직접 주입의 5단계 방어 레이어가 "LLM이 근거 없는 답변을 생성할 수 없는 구조"를 이룬다 [LIMITATION.md]. LLM의 역할은 자유 추론이 아니라 큐레이션된 결론가이드의 "전달자"로 제한된다 [LIMITATION.md].

- 용어 정의: **구조화 출력(Structured Output)** = LLM 응답을 자유 텍스트가 아닌 스키마 강제 필드(결론·인용문단·분기 등)로 받는 방식.
- 정량 데이터: 원천 항등 288+123+9 누락 0, 위임 판단 41+34+3=78 전수 추적 [2_DATA-TAXONOMY.md]; 04-aliases 기준 최종 회계 등재 400(389+11) / 용어 간선 755(개념 606 + 사례 149) [04-aliases.md]; 섬 사례 6건(문단 인용 0인 QNA)을 개념 직결해 기본 화면 고아 0건 실측 [04-aliases.md] [03-cases.md]; 개념→사례 도달성 전수 — 문단 인용 1+ 사례 117/117 도달 가능 [04-aliases.md].
- 방법론: 입력 = 사람 1차 자료 3원천 → 처리 = AI 초안 생성 → 본문 출현 근거 제안 부착 → 위임 판단 + 에스컬레이션 → 전수 감사(04b) → DEAD-END 규칙 보강 → 출력 = aliases.json(전건 decision 추적) [04-aliases.md] [04-aliases-review.md] [04b-title-topic-audit.md].
- 예상 반론과 대응: "형식화된(formed) 답변은 자유형 질문에 못 답한다" — 이는 버그가 아닌 의도된 trade-off로 문서화되어 있다. 사례 요청·자유형 질문·범위 외 교차 질문(예: 1116호 리스 결합)·계산 재검증이 대응 불가 유형이며, 4가지 대안(UI 버튼/파이프라인 분기/프롬프트 확장/graceful 거절)을 검토한 뒤 환각 방지 레이어 약화 위험 등을 이유로 현행 유지를 선택했다 [LIMITATION.md].
- 비교 벤치마크: 검수 없는 AI 산출물(기존 디시전 트리)과 동일한 신빙성 문제를 피하기 위해, 기존 트리는 라우팅 근간에서 제외하고 부가 층으로 강등했다 [00-overview.md].

## 10. 차별점 — 근거 선행 UI: AI가 먼저 답하지 않는다

**헤드라인:** 일반 챗봇의 순서를 뒤집어, 사용자가 먼저 기준서 근거를 보고 AI 답변은 그 위에 얹힌다.
**거버닝 메시지:** UI 층위의 "근거 선행, AI 후행"은 2종 오류를 사용자 눈으로 한 번 더 거르는 마지막 방어선이다.

UI는 3단계 State Machine(home / evidence / ai_answer)으로 구성된다. home은 자유 입력, evidence는 기준서 근거를 먼저 열람하는 화면, ai_answer는 좌우 Split View로 근거와 답변을 나란히 보여준다 [5_INTERFACE.md] [PROJECT_OVERVIEW.md]. AI가 인용한 문단은 좌측 근거 패널에서 볼드로 강조되어, 사용자가 "이 결론이 어느 조문에서 나왔는지"를 눈으로 대조할 수 있다 [5_INTERFACE.md].

핵심 주장은 세 가지다.

첫째, **답변 유형이 명시적으로 구분되어 확신의 수준이 UI에 드러난다.** 확정(TYPE2)은 결정적 사실이 충분할 때 단정 결론 + 인용 문단, 조건부(TYPE1)는 사실관계가 갈릴 때 Case 1/2 분기 결론, 되물음(clarify)은 사실관계 부족 시 부족한 정보를 질문, 산술(calc)은 gpt-4.1-mini 계산 결과다 [5_INTERFACE.md].

둘째, **멀티턴 안전장치가 과잉 되물음과 성급한 단정을 양방향으로 막는다.** concluded 플래그로 결론 후 불필요한 되물음을 막고, 핵심 요소(통제권·가격결정권·재고위험)가 미확인이면 단정을 자동 반려한다 [5_INTERFACE.md].

셋째, **감리사례 넛지가 실무 경각심을 자동 부착한다.** format 노드가 그래프가 수집한 문서에서 감리지적사례를 골라 "이런 지적 사례가 있으니 주의하라"는 경고와 꼬리질문을 덧붙인다. 되물음 경로에서는 불필요하므로 스킵한다 [4_SEARCH-PIPELINE.md] [5_INTERFACE.md].

- 용어 정의: **Split View** = 좌측 근거 문서와 우측 AI 답변을 한 화면에 나란히 배치한 이중 패널 뷰.
- 정량 데이터: UI 상태 3단계(home/evidence/ai_answer), 답변 유형 4종 [5_INTERFACE.md]; 사용자가 사례를 찾는 기존 경로 4가지(토픽 브라우즈 4탭 열람 / evidence 패널 아코디언 / cited_paragraphs 목록 / 감리사례 넛지) [LIMITATION.md].
- 방법론: 입력 = 질문 → 처리 = home에서 /chat 직행 또는 evidence(/search 경유)에서 근거 확인 후 질문 → 출력 = ai_answer Split View(좌 근거·인용 볼드 강조·감리 경고 / 우 결론·인용 번호·꼬리질문) [5_INTERFACE.md].
- 예상 반론과 대응: 코드 정합의 정직한 공개 — session.py 주석에는 topic_browse 포함 4단계로 적혀 있으나 실제 라우터와 렌더러는 3단계만 구현되어 있고, topic_browse는 미구현 상태임을 보고서 자체가 명시한다 [5_INTERFACE.md] [PROJECT_OVERVIEW.md]. 문서와 코드의 불일치까지 드러내는 태도가 신뢰의 근거다.
- 비교 벤치마크: "AI가 먼저 답하고 근거를 붙이는" 일반 챗봇 순서의 역전 [5_INTERFACE.md]; 범용 LLM 대비 차별화가 없다는 초기 문제(단순 챗봇은 범용 AI가 더 넓게 커버)에 대한 해답이 이 UX State Machine이었다 [7_JOURNEY.md].

## 11. 성과·증거 — 92건 홀드아웃 검증: 자가순환을 차단한 설계

**헤드라인:** 사람이 작성한 실제 질의회신 92건을, 정답이 적힌 문서(QNA)를 검색에서 전면 차단한 상태에서 재현 78/92, 에러 0으로 통과했다.
**거버닝 메시지:** AI가 만든 질문을 AI가 채점하는 자가순환을 두 겹으로 차단한 검증이므로, 수치가 시스템의 실제 능력을 반영한다.

검증의 핵심 위험은 자가순환이다. 이를 두 겹으로 차단했다: ① 질문 출처 — 개발자 자작 시나리오(구 53건 골든셋)를 버리고 사람이 쓴 실제 질의회신 92건(질의자·회계기준원·해석위원회 작성)을 사용, ② 답 출처 격리 — 질의회신(QNA)이 검색에 끌려오면 자기 답을 자기가 인용하므로 QNA 검색을 전면 차단(exclude_qna)하고 본문 + 판단트리만으로 답변을 강제했다. 격리 증명: 92건 검색결과 중 질의회신 0/92 [6_TEST-DECISIONS.md].

핵심 주장은 네 가지다.

첫째, **측정 대상은 "기준서 본문만으로 사람 전문가의 결론을 재현하는가"다.** 이는 "본문은 일반 규범이므로 개별 질의회신 없이도 답이 나온다"는 가설의 독립 검증이다 [6_TEST-DECISIONS.md].

둘째, **결과는 재현 78/92, 소프트 채점 92/92, 에러 0이다.** 하드 재현율(인용 재현)은 59.1%(인용 0 제외 84건 평균)로 별도 보고한다 [6_TEST-DECISIONS.md]. 재현 판정 기준은 결론축 ≥ 1 AND 3축(결론·문단·분기) 합 ≥ 4로, 인용률만으로 품질을 재지 않는다 — 하드 인용재현율 100%인데 결론이 정반대인 케이스를 소프트 채점이 0점으로 포착한 사례가 이를 실증한다 [6_TEST-DECISIONS.md].

셋째, **개선이 수치로 추적된다.** topic_concept_map 도입 전후로 재현 72→78, 평균 총점 4.79→4.88로 상승했다(results_pre_topicmap 대조) [6_TEST-DECISIONS.md]. 채점 신뢰는 Sonnet 채점을 표본 10건 저자 재대조해 불일치 0으로 확인했다 [6_TEST-DECISIONS.md].

넷째, **fitting 경계를 스스로 선언한다.** 92건은 이미 전수 열람되어 순수 홀드아웃이 아니라 튜닝셋으로 오염됐음을 명시하고, ① 우선순위 신호는 질문 구조에서만 도출(정답 미열람) ② 상한값은 비용 예산으로 결정 ③ 92건은 재현율 하락만 감시하는 회귀 안전망으로 사용하며, 최종 성능은 안 본 질문으로 검증해야 한다고 못박는다 [6_TEST-DECISIONS.md] [07-retrieval-priority.md].

- 용어 정의: **홀드아웃(holdout)** = 시스템 조정에 쓰지 않고 성능 측정에만 쓰는 검증 세트.
- 정량 데이터: 케이스 92건, 재현 78/92, 하드 재현율 59.1%, 소프트 채점 92/92, 에러 0 [6_TEST-DECISIONS.md]; QNA 격리 증명 0/92 [6_TEST-DECISIONS.md]; 재현 72→78·평균 총점 4.79→4.88 [6_TEST-DECISIONS.md].
- 방법론: 입력 = 사람 작성 질의회신 92건(qna_testset.json) → 처리 = exclude_qna 상태로 파이프라인 실행 → 3축(결론·문단·분기) 채점 + 표본 재대조 → 출력 = report.md 실측 수치와 미재현 분석 [6_TEST-DECISIONS.md] [PROJECT_OVERVIEW.md].
- 예상 반론과 대응: "LLM 채점을 믿을 수 있나" — Sonnet 채점 표본 10건을 저자가 재대조해 불일치 0을 확인했고 [6_TEST-DECISIONS.md], 채점 축 설계 자체가 인용률 단독 지표의 함정(인용 100%인데 결론 정반대)을 잡도록 다축화되어 있다 [6_TEST-DECISIONS.md].
- 비교 벤치마크(전환 직후 대비): 온톨로지 전환 직후 첫 측정은 재현 81%(당시 72/89)였고, 동시에 노출된 두 결함(비용 폭증·조문 누락)을 §12의 개선으로 해소하며 현재 수치에 도달했다 [7_JOURNEY.md].

## 12. 성과·증거 — 정직한 실패 분석: 미재현 14건의 해부와 "고칠 수 없는 것"의 확정

**헤드라인:** 미재현 14건을 케이스 단위로 전수 해부하고, 세 가지 개선 레버를 실제 구현·실측한 끝에 전부 기각했다.
**거버닝 메시지:** "검색 재설계로 남는 실질 레버는 헤지 대신 결론 확정 2~4건뿐"이라는 경계 확정 — 근거 없는 4번째 시도보다 손댈 수 없는 경계를 수치로 긋는 편이 정직하다.

미재현 14건은 두 렌즈로 분석됐다. 문단 재현 렌즈로는 근거 누락이 상한 밀림 45% / 검색 실패 33% / 생성 누락 18% / 온톨로지 밖 1%로 나뉘고, 케이스 결과 렌즈로는 A 진입누락 2건 + D 프레임 4건 + OUT 범위밖 2건 + 기타 소프트축 6건 = 14건(전수, 분모 14)으로 버킷 분류됐다 [6_TEST-DECISIONS.md]. 소프트축 6건은 타 기준서 4건(IAS38·1002·1008·1037호 — 1115 코퍼스 밖이라 인용 불가)과 헤지 2건(gold 문단 확보 상태에서 결론 미확정)으로 다시 쪼개진다 [6_TEST-DECISIONS.md].

핵심 주장은 네 가지다.

첫째, **개선 가설은 구현·실측 후에만 채택하거나 기각한다.** 레버 1(임베딩 코사인으로 진입 재현율 보강)은 baseline 개념 진입이 이미 55/57(96.5%)로 병목이 아니었고 코사인 실익이 dev 1건뿐이라 폐기됐다. 레버 2(혼동쌍 프레임 판별)는 3신호 전부 무효로 미채택, 레버 3(개념별 섹션 그룹핑)은 3회 재실행 3/3 여전히 오프레임 인용(gold 교집합 0/3)으로 기각됐다 [7_JOURNEY.md].

둘째, **리랭커 제거의 숨은 비용을 실측으로 배웠다.** 리랭커를 제거하면서 문서 수 상한도 함께 사라져, generate가 검색 문단 평균 138건(최대 299)을 통째 주입해 입력 토큰이 폭증하고 Gemini 월 지출 상한(429)을 넘겨 생성이 실패했다. generate_doc_limit으로 상한을 되살려 건당 약 14원까지 낮췄다 [7_JOURNEY.md]. "무언가를 제거할 땐 그것이 조용히 하던 일을 세어라"가 이 사건의 교훈이다 [7_JOURNEY.md].

셋째, **오답의 근본 원인까지 내려가 검증 노드를 설계했다.** 미재현 중 진짜 오답 2건은 근거 부족이 아니라 가진 문단을 거꾸로 읽은 것이었다 — KQA007은 답변이 문단 47 원문("판매세는 제외")을 인용하고도 결론은 "포함"이었다. 생성 후 결론↔인용문단 정합을 검사하는 verify 노드(모순 시 재생성이 아니라 "잠정"으로 강등)가 설계됐다 [08-routing-rebalance-verify.md].

넷째, **유보 편향 교정에도 과확정 방지선을 함께 걸었다.** 유보 9건 중 다수를 확정 전환하되, 본래 조건부여야 할 6건은 조건부 유지(6/6)를 실패 조건으로 명시해 골든셋 과적합을 차단했다 [08-routing-rebalance-verify.md] [4_SEARCH-PIPELINE.md].

- 용어 정의: **헤지(hedge)** = 결론을 확정하지 않고 유보적으로 표현하는 생성 경향; **fitting** = 평가 세트에 과적합하도록 시스템을 조정하는 것.
- 정량 데이터: 미재현 버킷 A2 + D4 + OUT2 + 기타6 = 14 [6_TEST-DECISIONS.md]; 검색·진입 파이프라인으로 실제 움직일 수 있는 것은 A 코사인 실익 1건뿐 [6_TEST-DECISIONS.md]; verify 설계의 성공조건 — 오답 2건 모순 포착 2/2, 유보 확정 전환 ≥5/9, 일치 조건부 유지 6/6 [08-routing-rebalance-verify.md]; 홀드아웃 정오 검증 — 진짜 오답 2건·유보 9건·일치 6건 [08-routing-rebalance-verify.md].
- 방법론: 입력 = 미재현 14건 + 실패 버킷(failure_buckets.json) → 처리 = 레버 3종을 실제 구현·실측 → 기각 근거 기록 → 출력 = "잔여 미재현은 ① 기준서 자체의 개념 교차연결 ② 코퍼스 밖 타 기준서 ③ 채점의 단일 확정 요구 vs LLM 헤지에서 온다"는 원인 지도 [7_JOURNEY.md] [6_TEST-DECISIONS.md].
- 예상 반론과 대응: "기각된 실험은 낭비 아닌가" — 세 레버를 붓고 전부 기각한 끝에 남은 실패가 검색이 아니라 기준서 교차연결·코퍼스 범위·생성 헤지에서 온다는 지도를 얻었다. "'고칠 수 없다'를 실측으로 확정하는 것도 결론이다" [7_JOURNEY.md].
- 비교 벤치마크(검증 노드의 한계 자인): verify는 결론↔인용 정합만 보며, 인용 자체가 잘못됐거나 근거 밖 판단은 못 잡는다. 강등은 "안전"이지 "정답화"가 아니다 — 오답을 정답으로 바꾸지 않고 확정 오답을 막을 뿐 [08-routing-rebalance-verify.md].

## 13. 성과·증거 — 재구축 여정이 증명하는 실행력

**헤드라인:** 7단계 여정의 각 단계는 앞 단계가 만든 문제를 풀었고, 분수령은 유사도·가중치·리랭커 복합체를 통째로 버린 5단계였다.
**거버닝 메시지:** 이 시스템의 신뢰성은 최종 산출물만이 아니라, 폐기 결정과 그 근거가 커밋 단위로 추적되는 과정에서 나온다.

여정은 ① 범용 AI 차별화(UX 3단계) → ② PDF 파싱 한계(REST API 전환) → ③ 답변 형식 분산(LangGraph→PydanticAI 구조화 출력) → ④ 답변 내용 비결정성(판단트리) → ⑤ 온톨로지 전면 전환(분수령) → ⑥ 홀드아웃 검증과 결함 개선 → ⑦ 잔여 레버 해부로 이어진다 [7_JOURNEY.md]. 백업은 커밋 787bd2c에 보존했고, 전환은 8fcb540(파이프라인 전환)·f922261(레거시 격리)에 기록했다 [7_JOURNEY.md].

핵심 주장은 세 가지다.

첫째, **주요 의사결정(ADR)이 온톨로지 전환 후 유효성까지 재평가됐다.** LangGraph→PydanticAI, 듀얼 LLM 라우팅, 산술 정확도 회복, 추론 강도 조정, 범위 밖 2중 방어, 실사용 로그 자동 채점은 유효 판정, 3중 유사도 토픽 매칭은 폐기, 전문가 큐레이션 트리는 부분 폐기(철학 계승, 원문 앵커 판단트리 41개로 대체), 핀포인트 파싱 개선은 교훈만 유효로 분류됐다 [6_TEST-DECISIONS.md].

둘째, **관통하는 교훈이 명시적으로 축적됐다.** "모델보다 데이터·구조가 품질을 결정한다 — 적중률·산술·일관성의 큰 개선은 전부 데이터 정확성과 구조 설계에서 나왔지 모델 교체에서 나오지 않았다", "AI 산출물은 검수 가능한 크기로", "무언가를 제거할 땐 그것이 조용히 하던 일을 세어라", "검증 기대값조차 원문에서 따온다" [7_JOURNEY.md].

셋째, **토픽 체계까지 원문 목차 기반으로 재구성해 자의성을 제거했다.** 기존 29토픽(AI 자의 재분류)을 버리고 K-IFRS 1115호 원문 목차 그대로 — 본문 절 + 부록B B1의 공식 14항목 열거 — 토픽 체계를 재구성했으며, 문단의 중복 소속은 원문이 명시한 참조("B## 참조")를 근거로만 허용했다 [01-topic-taxonomy-draft.md]. 본문 18 + 부록B 14 = 32 토픽 초안이 이 원칙의 산출물이다 [01-topic-taxonomy-draft.md].

- 용어 정의: **ADR**(Architecture Decision Record) = 아키텍처 의사결정과 그 근거를 기록한 문서.
- 정량 데이터: 부록B는 B1이 직접 14항목을 열거(자의성 0)하며 실측 세분과 정확히 일치 [01-topic-taxonomy-draft.md]; 본문↔부록B 참조맵 11행(예: 본문 34 "B64~B76 참조" → 재매입약정 중복 소속) [01-topic-taxonomy-draft.md]; 기술 스택 — FastAPI+uvicorn / Streamlit / PydanticAI / MongoDB Atlas / uv(Python 3.11) [1_OVERVIEW.md].
- 방법론: 입력 = 각 단계의 문제(오류 관찰·검증 결과) → 처리 = 원인 진단 → 해결 구현 → 다음 단계로 승계 → 출력 = 7단계 여정 기록 + 폐기·대체표 [7_JOURNEY.md].
- 예상 반론과 대응: "전면 재구축은 위험하다" — 재구축은 백업 커밋 보존과 레거시 격리 커밋으로 되돌릴 수 있게 진행됐고 [7_JOURNEY.md], 제거 대상도 에이전트 감사로 전수 확정한 목록(weight_score 곱셈·window boost·Cohere Reranker·벡터/BM25/RRF/HyDE·tree_matcher·decision_trees 등)에 따라 "비활성 → 검증 통과 → 파일 삭제"의 단계적 절차를 밟았다 [05-pipeline.md]. weight_score 필드 자체는 스키마 파급 방지를 위해 DB에 남기고 그 값을 읽는 코드만 제거했다 [05-pipeline.md].
- 비교 벤치마크(전/후): LangGraph 자유형 출력 + 3단 폴백의 비결정성 → PydanticAI 구조화 출력·양식 미충족 시 답변 거부·자동 재시도 [7_JOURNEY.md].

## 14. 확장 로드맵 — 검증된 뼈대 위의 증분 확장

**헤드라인:** 단기(verify 노드 배선·듀얼 모드·Gray Area 방어)에서 중장기(RAGAS 자동 평가·타 기준서 확장)까지, 로드맵은 검증된 구조의 증분 확장으로 설계되어 있다.
**거버닝 메시지:** 확장의 각 항목은 이미 설계 문서 또는 실측 근거를 보유하고 있어, 실행 리스크가 통제된 상태다.

발전 방향은 단기 — 듀얼 모드(V2 자유질문 전환), 교차 질문 매칭, Gray Area 방어 — 와 중장기 — BIG4 가이드 임베딩, RAGAS 자동 평가(Faithfulness·Context Precision), 타 기준서 확장(1116·1109), verify 노드 런타임 배선 — 로 제시된다 [6_TEST-DECISIONS.md]. 확정 답변의 결론↔인용 정합을 검사하는 verify 노드는 설계 완료·런타임 미배선 상태로, 라우팅 재균형은 프롬프트 수정으로 이미 반영됐다 [4_SEARCH-PIPELINE.md] [PROJECT_OVERVIEW.md].

핵심 주장은 세 가지다.

첫째, **verify 노드는 실측 실패 사례에서 역설계된 다음 단계다.** 오답 2건(가진 문단을 거꾸로 읽음)이라는 구체 결함을 겨냥해, 확정(TYPE2) 답변만 대상으로 결론과 인용 문단 원문의 모순을 판정하고 모순 시 강등하는 설계가 성공조건(오답 2/2 포착, 과확정 FAIL 기준 포함)과 함께 완성되어 있다 [08-routing-rebalance-verify.md].

둘째, **듀얼 모드는 의도된 설계 한계의 공식 해소 경로다.** formed 답변이 대응 불가한 유형(사례 요청·자유형 질문)에 대해, formed 답변 완료 후 "자유 질문 모드로 전환" 버튼으로 별도 generate_agent를 쓰는 V2가 검토되어 있다 — 단, 환각 방지 레이어 약화를 감수하는 trade-off임이 명시된다 [LIMITATION.md]. 멀티턴 컨텍스트 확장(clarify fast-path에서의 부분 retrieve 허용)도 성능·품질 균형점 탐색 과제로 등재되어 있다 [LIMITATION.md].

셋째, **타 기준서 확장은 방법론의 재적용이다.** 이 시스템의 핵심 자산은 특정 데이터가 아니라 "기계 추출 뼈대 + 항등식 검증 + AI 개입 최소화"라는 구축 방법론이며, 1116호(리스)·1109호 확장은 동일 방법론을 새 코퍼스에 적용하는 문제다 [6_TEST-DECISIONS.md] [PROJECT_OVERVIEW.md]. 현재 미재현의 타 기준서 4건(IAS38·1002·1008·1037호)이 코퍼스 밖 원인으로 실측 분류되어 있어, 확장의 기대 효과 또한 수치로 특정되어 있다 [6_TEST-DECISIONS.md].

- 용어 정의: **RAGAS** = RAG 파이프라인의 답변 충실성(Faithfulness)·컨텍스트 정밀도(Context Precision) 등을 자동 평가하는 프레임워크.
- 정량 데이터: 로드맵 체크리스트 — 온톨로지 전환 + QNA-off 홀드아웃 검증 완료, verify 노드 배선·Gray Area 방어·멀티토픽 동시 매칭·RAGAS·타 기준서 확장 미완 [PROJECT_OVERVIEW.md]; verify 성공조건 임계 — 유보 확정 전환 ≥5/9, 일치 조건부 유지 6/6 [08-routing-rebalance-verify.md].
- 방법론(확장 절차): 입력 = 실측 실패 사례·설계 문서 → 처리 = 설계 완료 항목의 런타임 배선 → 새 질의 세트로 검증(92건 밖) → 출력 = 증분 릴리스 [08-routing-rebalance-verify.md] [6_TEST-DECISIONS.md].
- 예상 반론과 대응: "로드맵이 낙관적이지 않나" — 각 항목에 실패 조건이 사전 정의되어 있고(예: verify가 오답 2건 중 2건 미만을 잡으면 검증 무력 FAIL) [08-routing-rebalance-verify.md], 검증 문화 자체가 "측정 전 완료 선언 금지"를 미검증 전제 목록으로 문서화해 온 이력이 있다 [05-pipeline.md].
- 비교 벤치마크: 소스에 근거 없음 — 경쟁 제품 대비 로드맵 벤치마크는 소스 문서에 존재하지 않아 기재하지 않는다.
