### 2. 문제 인식과 해결 방향

- 문제 인식
  - 생성 후 편집 불가능 : 범용 LLM은 PPT결과물을 이미지 형태로 생성
  - 일관성 보장 어려움 : 프로젝트마다 다른 규격과 템플릿으로 생성
- 해결 방향
  - 편집 가능한 PPT : 파이썬 활용 도형과 텍스트 직접 배치
  - 템플릿 고정 : 내용 생성과 디자인을 분리 → 일관성이 필요한 서식 규칙만 고정

## 1. 문제 인식과 접근 비교

### 소유의 경계

- 핵심 명제 : 토큰이 소유하면 한 곳을 고쳐 전체가 바뀌고, 부품이 소유하면 안 맞는 장에서도 그 형태로 그려짐
- 그래서 가른 것 : 일관성이 필요한 축만 템플릿에 넘기고 나머지는 코드에 남김

### 아키텍처 원칙 5

| #   | 원칙                             | 코드에 어떻게 박혔나                                                   |
| --- | -------------------------------- | ---------------------------------------------------------------------- |
| 1   | 일관성이 필요한 것만 소유        | 토큰 33개가 색, 글꼴, 판형, 임계를 지고 조판과 게이트가 리터럴을 안 씀 |
| 2   | 장 구성은 소유하지 않음          | 흐름도와 관계도를 그리는 도해 부품이 0종, 사각과 커넥터만 제공         |
| 3   | 기계는 통보자이지 판정자가 아님  | 물리와 기하는 하드페일, 표 행 높이와 재료 커버리지는 경고만            |
| 4   | 임계는 리터럴이 아니라 실측 파생 | 밀도 하한 535자는 골든 17장 스냅샷의 가장 성긴 장에서 계산             |
| 5   | 지어내는 것은 입력에서 차단      | 부 이름을 게이트로 뒤에서 잡지 않고 계약에서 읽어옴                    |

- 원칙 3과 4가 같은 뿌리인 이유 : 숫자로 굳히면 그 숫자를 채우는 쪽으로 왜곡됨
- 실측 근거 : 글자 수 하한을 걸었더니 본문 12장 합계로 글자 +2,091, 시각 요소 −39. 막대가 텍스트 목록이 됨

### 통상적 접근 대비 차이

| 관점               | 통상적 접근                  | 이 하네스                                        | 차이가 만드는 효과                                  |
| ------------------ | ---------------------------- | ------------------------------------------------ | --------------------------------------------------- |
| 템플릿의 범위      | 레이아웃 자리표시자까지 소유 | 색, 글꼴, 여백, 페이지 골격 4개만, 도해 부품 0종 | 자리표시자가 없어 장 구성이 굳지 않음               |
| 제목과 부 이름     | 조판 단계에서 결정           | 계약이 재료 헤딩에서 따와 확정                   | 사용자가 안 보는 자리에서 문구가 바뀌지 않음        |
| 게이트의 성격      | 통과와 실패의 판정자         | 물리와 기하만 하드페일, 미적인 것은 경고         | 재료를 부품에 맞춰 휘게 만들지 않음                 |
| 임계의 출처        | 설계자가 정한 리터럴         | 실측 파생, 기준선이 바뀌면 따라 이동             | 추측 선언값 10종 중 9종이 실측과 달랐던 전례를 차단 |
| 현재 상태의 기록   | 사람이 문서로 유지           | 코드에서 추출, 어긋나면 종료코드 1               | 문서가 갱신을 잊고 거짓말하는 경로가 닫힘           |
| 사용자 왕복의 위치 | 완성 후 피드백               | 그리기 전에 후보를 실제 pptx로 그려 선택         | 반려에 방향이 생김, 1안씩 내밀면 별로다로 끝남      |

## 2. 실증 예시

`local-ai-assist` 덱 10번 슬라이드 「룰 기반 검증 29종」이 재료에서 게이트까지 통과하는 과정

<p align="center">
  <img src="images/deck/s10.png" width="860" alt="10장 완성 화면 — 좌측 두 출처 박스와 커넥터, 중앙 지적 빈도 비례 막대 9행, 하단 주제별 6그룹, 우측 화면 캡처 3종">
</p>

1. **재료 읽기**
   - 원문 위치 : 완성본 README 3-2 기술 설명 절
   - 실체 : 감리 지적사례 230건(2009\~2025), 회계감사기준서 240호
   - 수치 : 조작 대상 9종의 지적 빈도 `147 / 80 / 23 / 22 / 20 / 20 / 12 / 3 / 2`, 활성 룰 29종의 주제별 6그룹 `4, 5, 5, 6, 5, 4`
2. **계약 확정**
   - 장 제목 : 룰 29종, 재료 헤딩 뎁스 그대로
   - 헤드라인 : 룰 기반 검증 29종, 슬라이드에 실제로 박히는 한 줄
   - 채록 원문 : "룰 하나하나에 출전이 있다", 사용자 육성 그대로 보존

3. **형태 후보와 선택**
   - 초점 : 채록이 지목한 "출전이 있다"
   - 고른 형태 : 두 출처에서 두 축으로, 다시 29종으로 갈라지는 인과 구도
4. **조판**

### 계약 서식 — 장 목록 7열

| 열             | 무엇                           | 누가 읽나             |
| -------------- | ------------------------------ | --------------------- |
| `#`            | 장 번호, `S4` 또는 `4`         | 파서와 게이트         |
| `부`           | 로마자 Ⅰ에서 Ⅴ, 정형 장은 대시 | 부 내비 강조 대조     |
| 장 제목        | 재료 헤딩 그대로               | 재료 대조기           |
| 헤드라인       | 슬라이드에 실제로 박히는 한 줄 | 덱 게이트             |
| 전하고 싶은 것 | 사용자 육성 채록 원문          | 형태 후보 단계의 초점 |
| 재료 출처      | 어느 절에서 왔나               | 사람                  |
| 상태           | 확정 또는 보류                 | 사람                  |

- 별도 표 하나 더 : 부와 간지 표가 **부 내비게이션 문구의 유일한 출처**
- 결합 방식 : 조판은 한 줄로 이 표를 읽고, 게이트는 **같은 함수로** 기대값을 만듦

### 지어내는 것을 막는 두 경로

| 대상    | 막는 방식            | 왜 이 방식인가                                              |
| ------- | -------------------- | ----------------------------------------------------------- |
| 장 제목 | 게이트로 뒤에서 대조 | 장마다 한 곳이라 틀릴 자리가 장 수만큼                      |
| 부 이름 | 계약에서 읽어옴      | 본문 전 장 상단에 5줄이 깔려 틀릴 자리가 장 수 곱하기 부 수 |

- 실측 개선 : 조판 창작 제목 8장에서 0, 부 이름 5개에서 0
- 남는 구멍 : 계약 자체가 틀리면 이 경로로는 못 잡음, 그 방어를 재료 대조기가 짐

### 계약과 재료 대조 규칙

| 단계      | 규칙                                                   |
| --------- | ------------------------------------------------------ |
| 헤딩 수집 | 재료의 1단계에서 4단계 헤딩 전부                       |
| 토큰화    | 숫자와 마침표 제거 후 구분자로 분할, 2글자 이상만 채택 |
| 히트 판정 | 제목 어절이 헤딩 토큰의 접두 또는 피접두면 히트        |
| 판정      | 전 헤딩 중 최대 겹침률이 0.5 미만이면 지어낸 말로 표시 |
| 면제      | 표지, 목차, 간지와 토큰 0개인 제목                     |

- 접두 매칭이 필요한 이유 : 한국어 조사, 계약의 「의사결정과」가 재료 헤딩의 「의사결정」에 붙어야 함
- 안 보는 것 : 수치를 대조하지 않고 제목 문자열만 봄, 그 공백은 [6. 한계](#6-한계)

#### 한글 조판은 두 조각이 쌍

```python
p._p.get_or_add_pPr().set("eaLnBrk", "0")      # 어절 단위 줄바꿈
for tag in ("a:latin", "a:ea", "a:cs"):        # 세 자형 전부에 글꼴
    el.set("typeface", FONT)
```

- 앞 줄을 빼면 : 파워포인트가 글자 단위로 끊어 고아 글자가 생김
- 뒤 줄을 빼면 : 자형 셋 중 하나만 빠져도 한글이 다른 꼴로 나옴
- 둘 다 코드가 강제 : 조판이 잊을 수 없음

#### 칸을 그림에 맞추는 순서

```python
def image_h(fname, w, caption=False, cap_h=0.24) -> float:
    """폭 w를 다 쓸 때 필요한 칸 높이."""
    return w / image_ar(fname) + (cap_h if caption else 0)
```

- 보통의 순서 : 칸을 정하고 그림을 우겨넣으면 칸의 5%가 빔
- 뒤집은 순서 : 폭만 정하고 높이를 그림에게 물음

#### 도해 부품을 만들지 않는 이유

- 코드 주석 원문 : 흐름도와 관계도를 블록으로 굳히면 안 맞는 내용에도 그 형식으로 그리게 됨

| 경계와 밀도 | 경계 이탈, 밀도 미달, 상자가 내용보다 큼            |
| 카드 품질   | 밝은 카드에 구조 자식이 0인 밋밋한 카드             |
| 정보량      | 같은 이름에 같은 서명인 재탕, 같은 이름에 다른 채움 |
| 겹침        | 글자 넘침, 텍스트 겹침, 그림이 글자 침범            |
| 덱 단위     | 아이콘 어휘가 통째로 죽었나                         |

- 경계 선언 : 채움은 클래스라 같은 이름이면 같아야 하고, 테두리와 점선은 상태라 달라도 됨
- 하한을 1보다 올리지 않는 이유 : 장별 커버리지 하한을 만들면 카드 4장 써라가 태어난 경로와 같음

### 검사기의 읽기 전용 원칙

- 사고 내용 : 색을 읽으려 접근한 속성이 XML을 생성해 검정 헤어라인 테두리가 붙음
- 조치 : 색 읽기를 전부 XML 읽기 전용으로 전환
- 이 저장소의 유일한 치명 사고이자 구조적으로 닫힌 경로

### 임계의 실측 파생

```python
{'shapes_min': 22, 'frames_min': 11, 'chars_min': 535, 'shapes_floor': 20, 'n_body': 10}
```

- 글자 하한 계산식 : 골든 본문 장 최소 글자 수의 85%
- 도형 수가 아니라 글자 수로 재는 이유 : 도형 수로 재면 밀도 부족을 카드 4장으로 메우는 반사를 유발

### 렌더 확인의 규율

| 축   | 신규 조판       | 수정 라운드                                |

- 실측 사고 : 게이트 통과와 렌더 확인까지 하고도 사용자가 확대해서야 어긋남을 발견

### 왜 손으로 안 쓰나

- 사고 내용 : 한 문서가 스스로 현재 상태의 단일 출처라 선언한 채 이미 폐기된 구조를 6일 동안 설명
- 결과 : 그걸 읽고 답한 것이 계속 어긋났고 원인을 찾는 데 시간이 감
- 명제 : 손으로 쓴 지도는 갱신을 잊는 순간 거짓말이 되고, 그 거짓말은 읽는 쪽을 없어진 곳으로 보냄

### 지도가 뽑는 것

| 뽑는 곳       | 무엇                                          |
| ------------- | --------------------------------------------- |
| 절차 문서     | 파이프라인 코드블록 원문 그대로               |
| 코드 디렉터리 | 구문 분석으로 줄 수와 공개 함수               |
| 오딧 모듈     | 검사 함수를 러너 본문과 대조해 배선 여부 판정 |
| 문서 디렉터리 | 줄 수, 최종 수정 날짜, 죽은 참조              |

### 종료코드 1을 내는 경고 3종

| #   | 조건                                                |
| --- | --------------------------------------------------- |
| 1   | 절차가 부르는 이름이 저장소에 실재하지 않음         |
| 2   | 검사 함수가 어느 러너에도 배선되지 않음             |
| 3   | 역사 문서가 아닌 문서가 존재하지 않는 심볼을 가리킴 |

- 경고 2가 핵심 방어 : 규칙이 있어도 러너에 안 물리면 없는 규칙
- 실증 : 모듈 3개를 지우자 문서 6개가 방금 지운 것을 현재형으로 설명하고 있어 경고 15건

### 덱 진행 상태

지도가 하네스의 현재라면 이 파일은 그 덱의 현재

- 도입 배경 : 계약 다음부터 산출 직전까지 아무것도 파일로 남지 않아 반려가 세션과 함께 사라짐
- 쌓이는 것 : 지금 몇 단계인지, 장마다 어떤 형태를 왜 골랐는지, 무엇을 반려당했고 그걸 하네스로 내릴지
- 종료코드 1 조건 : 반려 표의 하네스 칸이 미정으로 남아 있으면 종료가 막힘

### 획일화 판정

| 임계           |   값 | 뜻                                                       |
| -------------- | ---: | -------------------------------------------------------- |
| 같은 조합 상한 |    2 | 완전히 같은 조합이 이 수를 넘으면 형태가 아니라 틀       |
| 한 부품 점유율 | 0.60 | 한 부품이 본문 장의 이 비율을 넘으면 그 부품이 덱을 지배 |

- 임계 근거 : 완성본 본문 12장에서 조합 12종, 오탐 0으로 맞춘 값
- 잡으려는 실패 : 전 장이 같은 형식, 36장이 동일한 4카드
- 안전장치 : 본문 표본이 4장 미만이면 판정 자체를 하지 않음

| 14  | 브랜드 토큰 파일이 **2개**        | 값은 현재 일치하나 동기화하는 기계가 없음                  |
| 15  | 골든덱이 자기 게이트를 못 넘음    | 고정 기준선이 오딧 8건 실패, 프레임 기본값 불일치          |
| 16  | 완성본 본문에 토큰 밖 파생 색 7종 | 덱 전용 조판 코드가 토큰을 섞어 만든 값, 템플릿 골격은 0건 |
| 17  | 완성본 반려 2건이 미정 상태       | 하네스로 내릴지 안 정해 진행 상태 대조가 종료코드 1        |

### 자동 강제가 없는 이유

- 배경 : 훅이 메인 대화가 직접 만드는 경로 자체를 차단해 걷어냄
- 트레이드오프 : 강제를 되살리면 그 문제가 같이 돌아옴
- 현재 상태 : 게이트를 안 돌리고 끝내는 것을 막는 장치가 없음

## 7. 기술 스택

| 레이어            | 기술                   | 비고                                            |
| ----------------- | ---------------------- | ----------------------------------------------- |
| 런타임            | Python 3.13 고정       | 버전 파일과 프로젝트 설정 양쪽에 선언           |
| 패키지와 가상환경 | uv, 잠금 파일          | 재현 가능, 별도 활성화 없이 실행                |
