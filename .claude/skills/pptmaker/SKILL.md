# pptmaker — PPT 서식 공장

콘텐츠는 사용자가 프로젝트별로 미리 정리해둔다. 이 스킬은 그 재료를 **장마다 다른 형식으로**
조판한다. 추출 단계는 없다.

## 재료를 무엇으로 삼나 — 사용자가 지정한다

프로젝트마다 정리본이 두 갈래일 수 있다. **어느 쪽을 쓸지 먼저 사용자에게 묻는다.**

| 재료            | 성격                                                    | 언제                                |
| --------------- | ------------------------------------------------------- | ----------------------------------- |
| `README.md`     | 사용자가 문장까지 다듬은 완성판. 목차가 곧 아웃라인 1안 | **압축비가 맞으면 1순위**           |
| `FINAL-REPORT/` | 전수 기반 창고. 근거·수치가 깊지만 지저분               | README가 없거나 얇을 때 · 근거 보충 |

**압축비로 판단한다.** 본문 17장 × 밀도 하한 535자 ≈ **9,100자**가 목표량이다.

- 재료가 그 10배 안쪽(~9만자) → 무엇을 뺄지 인터뷰로 정할 수 있다
- 100배 넘으면(~90만자+) → "무엇을 버릴까"가 작업 전부가 되고 인터뷰조차 못 한다

실측 사례(local-ai-assist, 2026-07-31): README 64,189자(7배) vs FINAL-REPORT 1,353,962자(149배).
README를 골격·문장으로 쓰고 FINAL-REPORT는 근거 창고로 두기로 했다.

**실행 모드: 메인 대화가 직접 한다.** 서브 에이전트 파이프라인 아니다 — 덱 만들기는 사용자와
주고받는 일이고, 에이전트로 쪼개면 그 왕복이 끊긴다(2026-07-29 확정, 근거는 아래 §왜 이렇게).

## 파이프라인

```
① 재료 읽기    사용자가 지정한 재료(README 또는 FINAL-REPORT) + _workspace/01.5_outline.md
               계약이 없으면 deck-outline-grill로 먼저 확정 — 없이 진행 금지
               계약 확정 직후 `deck_state.py init <프로젝트>` — 이후 단계마다 STATE.md 갱신
② 형태 후보    **내용은 ①에서 이미 정해졌다.** 계약의 채록을 초점으로 삼고, 그 초점을
               담는 **배치·인코딩 4~6가지**를 낸다 — 고르는 건 "무엇을"이 아니라 "어떻게"다
③ 갤러리       후보를 **실제 pptx로 그려** 한 벌 만든다. 한 장에 한 주제, 후보를 나란히.
               장 이름·그 장의 초점(채록)·후보별 형태 설명을 같이 적는다(설명 없으면 못 고른다)
               **후보는 스케치다** — 구획 비율만 실제로, 라벨은 대표 2~3개 + "… N개"로 접는다
               갤러리 스크립트에 `CORE = {"S4": [핵심 실체 낱말...]}`를 선언한다
               `deck_state.py gallery <프로젝트>` — 본문 장 수 미달, 또는 후보가 핵심 실체를
               절반 미만 담으면 exit 1 (2026-08-03: 후보 ④에서 5축을 통째로 빼 반려당함)
④ 선택         사용자가 번호로 회신 — "s04=1 · s07=2 · s09=전탈락"
               전탈락이면 그 장은 ②로 되돌아간다
⑤ 본편         고른 형태로 장을 만든다. 파이썬 직접 조판(deckkit — 토큰·골격·블록 8종·커넥터)
⑥ 눈검증       render_deck.ps1 → PNG 전장 확인 → 겹침·잘림·넘침 수정. **이게 진짜 게이트다**
               수정 라운드는 규율이 다르다 — 아래 §수정 라운드
⑦ 기계 채점    score_deck.py — 튀는 곳만 본다(판정자 아님)
               끝내기 전 `deck_state.py check <프로젝트>` — 반려가 `하네스: 미정`이면 exit 1
               (미정으로 덮으면 다음 덱에서 같은 반려가 다시 나온다 — 2026-08-02 실측)
```

③에서 **왕복이 줄어든다.** 장마다 1안씩 내밀면 반려에 방향이 없다("별로다"로 끝난다).
한 벌을 깔면 사용자가 번호로 답한다.

### 두 축을 섞지 않는다 (2026-08-02 실패에서 확정)

| 축                  | 무엇을 고르나              | 어디서 정하나                   |
| ------------------- | -------------------------- | ------------------------------- |
| **A 무엇을 담을까** | 이 장이 다룰 내용·초점     | **①** 아웃라인 계약의 육성 채록 |
| **B 어떻게 그릴까** | 그 내용을 담는 배치·인코딩 | **②③④** 갤러리 선택             |

**②의 후보는 전부 축 B여야 한다.** 후보끼리 주제가 다르면 그건 후보가 아니라 **목차 문제**다
— 갤러리를 다시 그리지 말고 ①로 돌아가 계약을 고친다.

> 실패 기록: S7 후보를 "8단계 / EY→우리 데이터 / 7흐름→20종 / 생성 변수 분포"로 냈다.
> 사용자 반응 — **"이건 다 다른 주제인데? 뭘 고르라는 거야?"** 12장 전부 같은 결함이었고,
> 원인은 이 문서가 ②를 "무엇을 말할까"로 적어 ①과 같은 일을 시킨 것이었다.
>
> 같은 장을 축 B로 내면 이렇게 된다 — 내용은 8단계·시나리오 20종·무결성 관문 전부 고정:
> ① 세로 8단계 스파인 + 우측 관문 3개 + 하단 7흐름 칩
> ② 좌 8단계 흐름 / 우상 20종 트리 / 우하 관문·재생성 호
> ③ 가로 8단계 밴드 + 아래 7흐름 개수 비례 + 좌측 앵커 칼럼
> ④ 중앙 생성 루프(진행 + 폐기 되돌림) + 좌우 상세 칼럼

**②는 재료보다 채록을 먼저 읽는다.** 계약의 "가장 전하고 싶은 것"이 그 장의 초점이고, 재료 중
초점 밖은 버린다. 재료가 넘친다고 후보를 늘리면 그게 축 A로 새는 경로다.

### 갤러리 후보는 스케치다 (2026-08-02 실측)

축 B로 바꾸면 **후보 하나가 장 전체 내용을 담아야 한다.** 그런데 갤러리 미니 캔버스는 본편의
약 1/4(5.75 × 2.08″)이다 — 전 항목 라벨을 넣으면 자리가 모자라 부품이 죽는다.

|           | 갤러리 후보              | 본편    |
| --------- | ------------------------ | ------- |
| 구획 비율 | **실제 그대로**          | 실제    |
| 라벨      | **대표 2~3개 + "… N개"** | 전 항목 |
| 목적      | 배치를 고르게 한다       | 완성품  |

8단계를 보이려면 8칸을 그리되 라벨은 양끝만 있으면 된다 — `1 계정과목표 … 8 CSV`. 사용자는
그것으로 배치를 판단할 수 있다.

> **`pitch`가 죽으면 부품 하한을 낮추지 말고 라벨을 줄인다.** 그 하한은 칩끼리 겹치는 것을 막는
> 실측값이라(2026-07-15: 개념 18개 → 피치 0.109″ < 높이 0.24″), 완화하면 **본편에서 조용히
> 겹친다.** 실측 사고: 가드를 계속 완화하며 5~6바퀴를 돌았고(실패 7/48 → 0/48 → 렌더 → 다시
> 3/48) 한 시간이 소모됐다.

이 규정은 "설명 없이 형태만 늘어놓는다"(반려 목록)와 충돌하지 않는다 — 그건 **후보가 답하는
게 뭔지 안 적었다**는 뜻이지 모든 라벨을 넣으라는 뜻이 아니다.

## 확정 규칙 5개 (2026-07-29 실험 2회로 확정 — 어기면 같은 반려가 재발한다)

| #   | 규칙                                                            | 어겼을 때 실제로 벌어진 일                                                                     |
| --- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | 그림 그리기 **전**에 형태 후보를 내고 사용자가 고른다           | 구조를 혼자 확정해 오독(s05를 병렬로 읽었는데 실제는 순환)                                     |
| 2   | 고른 질문을 **전부** 시각으로 덮는다 (개수 하한 아님, 커버리지) | "시각화 자료가 너무 없음, 모든지 텍스트로 해결하려함"                                          |
| 3   | 글자 수 하한은 유지한다                                         | — 사용자 확정. 단 하한이 **떡칠을 유도**하니 ②의 커버리지로 갚는다                             |
| 4   | 부품함·골든덱은 **재료로만** 본다. 그대로 호출 금지             | 부품을 그대로 부르니 36장이 전부 같은 카드가 됨                                                |
| 5   | **인코딩** 발명은 환영, **잉크** 발명은 금지                    | 기존 잉크(사각·원·선·화살표)로 값을 인코딩하는 건 좋다. 도트·링·그라데이션 같은 새 장식은 금지 |

규칙 4의 뜻: `golden/render/`(골든 17장)는 **보고 배우는 그림**이지 부르는 함수가 아니다.
생산 코드는 2026-07-29에 물러났다 — 되살리지 않는다.

### 이 목록을 다루는 법

**적을 때 "~해라"로 쓰지 않는다.** 반려당한 것을 그대로 적는다. 대안은 매번 그 장에 맞게
새로 찾는다.

> 실제 사고: "이 장 밋밋해"(한 장에 대한 지적) → "카드 4장으로 채워라"(모든 장의 명령)로
> 적었더니 → 다음 덱이 전부 4장이 되어 → **그 규칙이 새 반려를 낳았다.** 규칙이 639줄로
> 불어난 메커니즘이 이것이다.

**새 반려를 적을 때 기존 줄을 훑어 아래에 해당하면 지운다.** 따로 정리하는 날을 만들지
않는다 — 그날은 오지 않는다.

- 기계가 잡게 됐다 (`score_deck`에 검사가 생기면 목록은 중복이다)
- 대상이 없어졌다 (구조가 바뀌어 그 상황 자체가 안 나온다)
- 사용자가 번복했다

**코드나 왕복으로 막을 수 있으면 그걸 먼저 하고, 그때는 목록에 안 적는다.** 산문으로 적힌
규칙은 이 저장소에서 예외 없이 무시됐고, 기계 검사(`check_adhoc_card`)나 왕복(갤러리 선택)으로
바뀐 것은 예외 없이 지켜졌다.

## 수정 라운드는 신규 조판과 다르다 (2026-08-02 사고)

사용자 피드백을 받아 고칠 때는 아래를 지킨다. 신규 조판(⑤)과 같은 방식으로 하면 어긋난
산출물이 그대로 나간다.

|      | 신규 조판       | **수정 라운드**                                      |
| ---- | --------------- | ---------------------------------------------------- |
| 단위 | 전 장을 한 번에 | **한 번에 한 장씩** — 여러 장을 모아 패치하지 않는다 |
| 렌더 | 1920px 전장     | **고친 장만 `-Width 3840`으로 다시**                 |
| 종료 | 전 장 훑고 채점 | **그 장이 끝나기 전에 다음 장으로 넘어가지 않는다**  |

```bash
# 고친 장을 확대해서 본다 — 전장 훑기로는 카드 안 정렬·겹침이 안 보인다
pwsh .claude/skills/pptx-build/scripts/render_deck.ps1 -Pptx <경로> -OutDir <폴더> -Width 3840
```

> **사고 기록(2026-08-02):** 피드백 4건을 받고 여섯 번을 연달아 패치했다. 그 사이 s12 넘침이
> 5~6회 반복됐고, `score_deck`은 FAIL 0을 줬으며 렌더 PNG도 읽었다. 그런데 사용자가 확대해
> 보니 카드 안 정렬이 어긋나 있었다 — **1920px 전장 훑기로는 안 보이는 크기**였다.
> 기계가 못 잡은 이유는 여백을 보는 검사가 없기 때문이고, 눈이 못 잡은 이유는 축소본을
