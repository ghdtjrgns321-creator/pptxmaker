# project-analysis — 프로젝트 사실 추출

기존 프로젝트를 훑어 PPT 재료를 뽑는다. **원칙: 없는 것을 지어내지 않는다.** 추출한 모든
항목에는 근거(파일 경로·라인·커밋)를 붙여, 뒤 단계(셀링 큐레이션)가 과장 없이 선별하게 한다.

## 추출 대상 (셀링에 쓰이는 재료)

| 카테고리            | 어디서                                                     | 예                      |
| ------------------- | ---------------------------------------------------------- | ----------------------- |
| **한 줄 정체성**    | README 상단, package.json description                      | "무엇을 하는 도구인가"  |
| **해결 문제(Pain)** | README 동기, 이슈, 주석의 TODO/문제의식                    | 왜 만들었나             |
| **핵심 기능**       | 주요 모듈·엔드포인트·CLI 명령·UI 화면                      | 사용자가 실제로 얻는 것 |
| **기술 스택**       | 의존성 파일(package.json, requirements 등), Dockerfile, CI | 언어·프레임워크·인프라  |
| **아키텍처**        | 디렉토리 구조, 진입점, 데이터 흐름                         | 구조 다이어그램 재료    |
| **정량 성과**       | README 벤치마크, 테스트 커버리지, 스타 수, 커밋 수, 처리량 | 숫자로 말할 수 있는 것  |
| **차별점**          | 유사 도구 대비 서술, "unlike/기존과 달리" 문구             | 왜 이걸 쓰나            |
| **시각 자료 후보**  | docs/ 이미지, 스크린샷, 다이어그램 파일 경로               | 슬라이드 삽입 후보      |

## 방법

1. README·docs를 먼저 읽는다(의도·성과가 여기 집약됨).
2. 의존성/설정 파일로 기술 스택을 **추정이 아니라 확인**한다.
3. 디렉토리·진입점으로 규모와 구조를 파악한다.
4. git 이력(커밋 수·기간·기여자)으로 성숙도 신호를 뽑는다 — 있으면.
5. 숫자를 찾되, 없으면 "없음"으로 남긴다. 지어내지 않는다.

## 출력: `_workspace/01_facts.md`

카테고리별로 정리하고 각 항목에 근거 경로를 병기한다. 확실치 않은 것은 `(불확실)` 표시.
성과 숫자는 출처 없이 쓰지 않는다.

```markdown
## 한 줄 정체성
- ... (출처: README.md:1-3)
## 정량 성과
- 테스트 커버리지 87% (출처: README badge)
- 처리량: 명시 없음
```

## 근본 원인주의

"기능이 많아 보이게" 하려고 사소한 유틸까지 나열하지 않는다. 셀링에서 중요한 건
**핵심 가치 3~5개**다. 재료는 충분히 뽑되, 선별은 다음 단계(selling-curator)에 맡긴다.
