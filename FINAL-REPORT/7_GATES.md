# 7. 눈검증과 기계 채점 (⑥⑦)

```
 ① 재료 ─ ② 질문 후보 ─ ③ 갤러리 ─ ④ 선택 ─ ⑤ 조판 ─ ▶ ⑥ 눈검증 ⑦ 채점 ◀
```

## 내부 흐름

```
 deck.pptx
     │
     ▼
 ⑥ render_deck.ps1  ── PowerPoint COM ──▶ sNN.png (1920px)
     │                  전역 뮤텍스로 직렬화
     ▼
   PNG를 실제로 Read ── 겹침 · 잘림 · 넘침 · 밋밋 · 아이콘 부정합
     │                  ★ 이게 진짜 게이트다
     ├─ 결함 있음 ──▶ 조판 수정 후 재렌더
     ▼
 ⑦ score_deck.py ── generic_checks 12종 + 밀도 밴드
     │
     └─ FAIL 목록 ── 판정자가 아니라 "어디가 튀나"를 보는 참고값
```

## ⑥ 눈검증이 진짜 게이트인 이유

**게이트는 사용자가 반려한 조립 7장을 전부 통과시킨 전례가 있다**(면적 82~97%로 green).
기계가 보는 것과 사람이 보는 것이 다르다.

| 기계가 보는 것          | 기계가 못 보는 것          |
| ----------------------- | -------------------------- |
| 도형이 상자를 넘었나    | 이 형태가 이 내용에 맞나   |
| 글자가 상자를 넘쳤나    | 같은 색이 두 뜻으로 쓰였나 |
| 두 상자가 겹쳤나        | 밋밋한가                   |
| 글자 수가 하한 미달인가 | 재료를 제대로 읽었나       |

오른쪽은 렌더 PNG를 **실제로 Read**해야 알 수 있다. `render_deck.ps1`은 PowerPoint COM으로
슬라이드별 PNG를 뽑는다 — 동시 렌더가 서로의 `Quit`에 죽지 않도록 전역 뮤텍스로 직렬화한다.

```powershell
$mutex = New-Object System.Threading.Mutex($false, "Global\pptmaker_render_deck")
[void]$mutex.WaitOne()
```

### accent를 채움만 세면 안 되는 이유

v4에서 채움·런만 세서 4로 통과시켰는데 제3자가 **7군데**를 셌다. 선을 안 센 것이다. 그래서
테두리·커넥터도 예산에 넣는다.

단 dense 장은 2단 불릿의 `**강조**`를 accent 텍스트 런으로 쓴다(정상 표현, 장당 28~31런).
그건 장식적 남용이 아니므로 dense에선 `count_runs=False`로 채움·선만 센다.

### 검사기가 대상을 오염시킨 사고

초판은 `sh.line.color.type`으로 색을 읽었는데, python-pptx의 `ColorFormat`은 **접근하는 순간
XML을 만든다** — 빈 `<a:solidFill/>`이 붙고 PowerPoint가 그걸 **검정 헤어라인 테두리**로
그린다. 게이트가 `prs.save()` 전에 돌았으니 그 테두리가 파일에 그대로 저장됐다.
**오딧이 산출물을 오염시킨 것이다.**

지금은 lxml로 XML을 읽기만 한다.

```python
def _solid_srgb(parent):
    """<parent><a:solidFill><a:srgbClr val="RRGGBB"/> → "RRGGBB". 없으면 None(생성하지 않음)."""
```

**교훈: 검사기는 대상을 절대 변형하지 않는다.**

## 밀도 밴드는 리터럴이 아니다

임계를 손으로 정하면 근거가 없다. `density_band()`가 골든 스냅샷에서 **파생**한다.

```python
{'shapes_min': 22, 'frames_min': 11, 'chars_min': 535, 'shapes_floor': 20, 'n_body': 10}
```

`chars_min`은 골든 본문 10장 중 **가장 성긴 장의 글자 수 × 0.85**다. 골든이 바뀌어 스냅샷을
재생성하면 밴드도 따라 움직인다.

### 왜 글자 수인가

도형 수로 재면 밀도 부족을 **카드 4장으로 메우는 반사**를 유발한다. 골든 항목형은 도형이
적어도(예: 37도형) 글자가 꽉 차 통과작이다. 그래서 글자 수가 주 하한이고, 도형 수는 텅 빈
장만 거르는 느슨한 바닥(`shapes_floor` 20)이다.

### 정직한 한계 — 하한이 떡칠을 유도한다

2026-07-29 실측: s16 문장을 줄였더니 밀도 FAIL(519 < 535)이 나서 다시 늘렸다. **게이트가
텍스트 떡칠을 요구한 것이다.** 사용자는 하한 유지를 택했고, 그 빚은 시각 커버리지(질문을 전부
시각으로 덮기)로 갚기로 했다.

## 러너 — `score_deck.py`

```bash
uv run python .claude/skills/pptx-build/scripts/score_deck.py <deck.pptx> [--body 4,5,7]
```

**spec을 안 본다.** pptx만 열어 검사한다. 대상 장은 `--body`로 주거나, 없으면 전 장을 검사하되
도형 12개 미만인 정형 장(표지·목차·간지)은 자동으로 빠진다.

옛 러너 `audit_deck.py`는 `deck-spec.json`을 인자로 받아 장 타입으로 대상을 골랐는데,
deck-spec 경로가 폐기되면서 진입점이 사라졌다. 이 파일이 그 자리다.

## 정직한 공백

**`audit.py`에 있지만 아무도 안 부르는 검사가 4개 있다** — `check_progress_shapes` ·
`check_ink_collision` · `check_node_heights` · `check_air`. 장별 정답지(SPECS)가 필요해 옛
`audit_golden`이 부르던 것들이고, 그게 아카이브되며 고아가 됐다. 지금 이 4종은 눈검증 몫이다.

`legacy` 프로파일도 대상이 0이다 — 겨냥하던 렌더러(`build_pptx`)가 아카이브됐다. 상수와 분기는
"왜 프레임마다 임계가 달라야 하는가"의 실측 근거로 남겨뒀다.

## 실증 예시 — 2차 실험판 본문 9장 채점

```
$ uv run python .claude/skills/pptx-build/scripts/score_deck.py \
      _lab/deck-lab2.pptx --body 4,5,7,9,10,11,12,14,16

== s04  도형  61  PASS
== s05  도형  46  PASS
...
== s14  도형  49  PASS
== s16  도형  55  FAIL 1
    x 텍스트 겹침: 텍스트 상자 세로 겹침: 2
      [('골든 덱 17장', '표지 · 목차 · ', 0.11), ('부품 목업 9종', '장 함수에서 꺼내 ', 0.11)]

본문 9장 총 FAIL 2건  (밀도 밴드 535자 · 도형 바닥 20)
```

s16의 FAIL은 **갤러리 장의 캡션 두 개가 0.11″ 겹친** 것이다. 렌더 PNG에서는 눈에 잘 안 띄는
크기지만 기계는 잡는다 — 이것이 ⑦의 쓸모다. 반대로 "이 장이 밋밋한가"는 ⑦이 전부 PASS를
줘도 ⑥이 잡아야 한다.

이 수치는 하네스를 13,710줄에서 3,185줄로 줄인 **전후가 동일**했다. 정리가 채점 결과를 바꾸지
않았다는 회귀 증거다.
