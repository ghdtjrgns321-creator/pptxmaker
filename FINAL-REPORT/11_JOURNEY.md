## v7 (2026-07-29) — 하네스 대정리

### 무엇이 문제였나

13,710줄 중 실제로 값을 한 것이 약 700줄이었고 나머지는 실전 덱에서 **0회 호출**이었다. 더 큰
문제는 양이 아니라 구조였다.

```
 registry가 장을 통째로 배정        →  15타입이 돌아가며 나와 전 장이 같은 형식
 figures/*.LAYOUT 기본값 = 골든 좌표 →  그대로 부르면 골든이 딸려옴
 dense.hero_card가 유일한 카드      →  36장이 동일한 4카드
 Stop 훅이 "에이전트 경유" 강제      →  메인 대화가 직접 만드는 경로를 차단
```

마지막 줄이 결정적이었다. 새 방식을 시험하려는데 **훅이 그것을 막고 있었다.**

### 정리하다 발견한 것

계획에 없던 5건이 나왔다.

1. **`audit.py`가 아카이브 대상을 물고 있었다** — `reference`→`registry`→본문 렌더러 12종.
   `SLIDE_ORDER`만 쓰길래 `SNAPSHOT_KEYS` 상수로 내려 사슬을 끊었다.
2. **스킬 디렉토리 안에 이전 워크스페이스가 섞여 있었다**(`skills/pptmaker/_workspace_prev/` 4개).
3. **`new_presentation()`이 고아가 될 뻔했다** — 아카이브되는 `reference.py`에 있어서
   `kit.py`로 옮겼다.
4. **골든 기준선이 git에 없었다** — `golden/render/`가 `.gitignore` 대상이고
   `golden-deck.pptx`는 `*.pptx` 규칙에 걸려 있었다. 생산 코드를 아카이브한 이상 재생성이
   불가능해 커밋 대상으로 전환했다.
5. **부품 렌더 27장이 덱의 재료로 쓰이고 있었다** — 코드는 아카이브하되 이미지는 자산으로
   되돌렸다.

### 후속 정리 (2026-07-29~31)

첫 정리 후에도 죽은 지시가 남아 있었다. 경로 검증기만 돌렸을 때 `deck-outline-grill`이
아카이브된 파이프라인을 4곳에서 지시하는데 **전부 통과했다** — `deck-compose`는 경로가 아니라
개념 이름이라 정규식에 안 걸렸다. 검증기에 2부(죽은 개념 이름 20종)를 붙이고 32건을 정리했다.

이어서 반려 축적 방식을 바꿨다([8_INHERITANCE](8_INHERITANCE.md)) — 규칙이 다음 반려를 낳은
사례를 실측에서 찾은 것이 계기였다.

## 반복해서 배운 것

| 시도                        | 결과                                                         |
| --------------------------- | ------------------------------------------------------------ |
| 규칙을 쌓아 품질을 만든다   | 실패 — 규칙을 통과하는 평범한 덱, 그리고 규칙이 낳는 새 반려 |
| 부품을 늘려 다양성을 만든다 | 실패 — 부품이 많아져도 부르는 쪽이 같으면 결과가 같다        |
| 기준선(골든)을 만든다       | 절반 성공 — "저것과 같은가"는 판정되지만 그대로 복제된다     |
| 왕복을 넣는다               | **성공** — 구조 오독·형식 수렴이 멈췄다                      |

**규칙은 나쁜 것을 막을 수 있어도 맞는 것을 고르지는 못한다.** 고르는 일은 사용자에게 남기고,
시스템은 고를 수 있는 형태로 내미는 일만 한다 — 이것이 v7의 요지다.
