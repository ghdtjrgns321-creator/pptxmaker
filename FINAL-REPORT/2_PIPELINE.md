# 2. 전체 파이프라인

원문 단일 출처는 `.claude/skills/pptmaker/SKILL.md`의 `## 파이프라인` 코드블록이다.
`docs/MAP.md`가 그 블록을 **그대로 복사해** 싣고, 블록이 부르는 이름(`*.py`·`*.ps1`·스킬)이
실재하는지 rglob으로 대조한다(`make_map.py:233-238`). 현재 4/4 실재.

## 전 과정

```
                    ┌─ 사용자가 재료를 지정한다 (README / FINAL-REPORT)
                    │  판단 기준 = 압축비. 목표량 ≈ 9,100자 대비 10배 안쪽이면 인터뷰 가능
                    ▼
 ①  재료 읽기 ─────────────────────────────────────────────────────────────────
    · 계약이 없으면 deck-outline-grill 스킬로 먼저 확정 — 없이 진행 금지
    · 확정 직후 deck_state.py init <프로젝트>  →  _workspace/<프로젝트>/STATE.md
    · (선택) scan_material.py --json  →  절마다 표 행 수·목록 개수·화살표를 기계가 센다
                    │
                    ▼
 ②  형태 후보 ─────────────────────────────────────────────────────────────────
    내용은 ①에서 이미 정해졌다. 계약의 채록을 초점으로 삼고
    그 초점을 담는 **배치·인코딩 4~6가지**를 낸다  ← 고르는 건 "무엇을"이 아니라 "어떻게"
                    │
                    ▼
 ③  갤러리 ────────────────────────────────────────────────────────────────────
    후보를 **실제 pptx로 그려** 한 벌 만든다. 한 장에 한 주제, 후보를 나란히.
    갤러리 스크립트에 CORE = {"S4": [핵심 실체 낱말...]} 를 선언한다
    deck_state.py gallery <프로젝트>  → 본문 장 수 미달 · 후보가 핵심 실체 절반 미만이면 exit 1
                    │
                    ▼
 ④  선택 ──────────────────────────────────────────────────────────────────────
    사용자가 번호로 회신 — "s04=1 · s07=2 · s09=전탈락".  전탈락이면 그 장은 ②로
                    │
                    ▼
 ⑤  본편 조판 ─────────────────────────────────────────────────────────────────
    파이썬 직접 조판.  deckkit — 토큰 · 골격 4 · 블록 8종 · 커넥터
    set_parts(O.parts(계약)) 한 줄로 부 내비게이션이 본문 전 장에 깔린다
                    │
                    ▼
 ⑥  눈검증  ★ 진짜 게이트 ────────────────────────────────────────────────────
    render_deck.ps1 → PNG 전장 확인 → 겹침·잘림·넘침 수정
    수정 라운드는 규율이 다르다: 한 번에 한 장 · 고친 장만 -Width 3840 · 끝내고 넘어간다
                    │
                    ▼
 ⑦  기계 채점 ─────────────────────────────────────────────────────────────────
    score_deck.py — 튀는 곳만 본다(판정자 아님)
    deck_state.py check — 계약↔STATE↔pptx↔렌더 장 수 대조 + 반려가 `미정`이면 exit 1
```

## 단계 표

| 단계 | 입력               | 처리                                          | 출력                           | 상세                 |
| ---- | ------------------ | --------------------------------------------- | ------------------------------ | -------------------- |
| ①    | 재료 md            | 인터뷰로 장 제목·헤드라인·부 문구·채록을 확정 | `01.5_outline.md` · `STATE.md` | [3장](3_CONTRACT.md) |
| ②    | 계약의 채록        | 같은 내용을 담는 배치·인코딩 4~6안            | 후보 서술                      | —                    |
| ③    | 후보               | 실제 pptx로 스케치                            | `gallery.pptx`                 | [5장](5_GATES.md)    |
| ④    | 갤러리             | 사용자가 번호로 선택                          | 장별 확정 형태                 | —                    |
| ⑤    | 계약 + 재료 + 선택 | 파이썬 좌표 조판                              | `deck.pptx`                    | [4장](4_TEMPLATE.md) |
| ⑥    | pptx               | COM 렌더 → PNG 전장 눈검증                    | `render/sNN.png`               | [5장](5_GATES.md)    |
| ⑦    | pptx               | 좌표·계약 게이트 + 오딧 채점                  | 결함 목록                      | [5장](5_GATES.md)    |

**②가 축 B(어떻게 그릴까)여야 한다.** 후보끼리 주제가 다르면 그건 후보가 아니라 목차 문제고,
갤러리를 다시 그리지 말고 ①로 돌아가 계약을 고친다. 이 문장이 반대로 박혀 있어서 갤러리
12장이 전부 실패한 적이 있다(→ [9장 사고 8](9_TROUBLESHOOTING.md)).

**⑥이 진짜 게이트인 이유**는 ⑦이 통과시킨 것을 사용자가 반려한 전례가 있기 때문이다. 조립 7장이
게이트를 전부 통과하고(면적 82~97%) 사용자에게 7장 전부 반려당했다. 그중 **최고점 97%를 받은
장이 도해 하나가 통째로 안 보이던 장**이었다.

## 실증 — S10 한 장이 끝까지 통과하는 과정

`local-ai-assist` 덱의 10번 슬라이드 「룰 기반 검증 29종」을 실제 값으로 추적한다.

### ① 재료 → 계약

재료 `README.md`의 `## 3-2. 기술 설명` 절에 두 출처와 빈도표가 있다 — 금융감독원 감리 지적사례
230건(2009~2025), 회계감사기준서 240호, 조작 대상 9종의 지적 빈도 `147 / 80 / 23 / 22 / 20 /
20 / 12 / 3 / 2`, 조작 수법 10종, 활성 룰 29종의 주제별 6그룹 `4·5·5·6·5·4`.

인터뷰가 이 절에서 확정한 계약 행:

```
| S10 | Ⅲ | 룰 29종 | 룰 기반 검증 29종 | "룰 하나하나에 출전이 있다" — 감리 230건 → 대상
       9종(147·80·23…은 실제 지적 빈도), 기준서 240호 → 수법 10종. 주제별 6그룹
       | README 3-2 도출·29종 분류 | 확정 |
```

`장 제목`은 재료 헤딩에서, `헤드라인(확정)`은 슬라이드에 실제로 박히는 한 줄이다. 넷째 칸의
채록은 **사용자 육성 그대로** — 이게 ②의 초점이 된다.

`check_outline.py`가 이 제목이 재료에서 나왔는지 대조한다. 「룰 기반 검증 29종」의 토큰은
`{룰, 기반, 검증, 29종}`이고, 재료 헤딩 `### 룰 기반 검증 (Rule-based)`의 토큰과 겹침률이
임계 0.5를 넘는다 → 통과.

### ② → ④ 형태 후보와 선택

채록의 초점은 *"룰 하나하나에 출전이 있다"*다. 같은 내용을 담는 배치 후보를 갤러리로 그리고
사용자가 번호로 골랐다. 고른 형태는 **두 출처 → 두 축 → 29종**의 인과 구도다.

### ⑤ 조판

`deck.py`가 계약에서 부 목록을 읽고 시작한다.

```python
set_parts(O.parts(OUTLINE))      # 계약 `### 부(간지)` 표 → [("Ⅰ","분석 범위와 문제 인식"), ...]
...
s = blank(prs)
header(s, 10, "Ⅲ", "룰 기반 검증 29종", FOOT)
```

이 한 줄이 그리는 것: 제목(24pt, x=0.60) · 헤더 밑줄(y=1.02) · 좌측 1.15″ 근흑 마디 ·
푸터 룰과 쪽번호 · **그리고 x=6.00부터 우변까지 5부 탭 줄**. 현재 부 `Ⅲ`만 accent 굵게,
밑줄 위에 강조 바가 얹힌다.

본문은 좌표로 짠다 — 좌상에 근흑 출처 박스 2개, 그 오른쪽으로 `CONNECT` 화살표 2개(라벨
「적발 계정·거래 구조화」·「통제 위반 패턴 구조화」), 화살표가 닿는 자리에 연한 박스 2개
(「조작 대상 9종」·「조작 수법 10종」). 중단에 9행 비례 막대(`147`을 1.0으로 정규화, 최댓값만
accent), 하단에 주제별 6그룹 카드, 우측 열에 화면 캡처 2장.

### ⑥ 렌더 눈검증

```bash
pwsh render_deck.ps1 -Pptx deck-final.pptx -OutDir render-final
```

`s10.png`를 열어 확인한다. 이 단계에서만 잡히는 것이 있다 — 다른 장 실측에서 부제가
「실무 관/행」으로 어절 중간에 꺾인 것이 좌표 게이트를 통과한 채 여기서 발견됐다.

### ⑦ 기계 게이트

```bash
uv run python check_deck.py deck-final.pptx --outline=01.5_outline.md
```

이 장에서 실제로 도는 검사: 우변 초과(블리드 면제 적용) · 하변 초과 · 이미지 판독 폭
(캡처 2장 모두 2.40″ 이상) · 헤드라인이 계약과 같은가(「룰 기반 검증 29종」이 밑줄 위
텍스트에 있는가) · 부 내비 5줄이 계약과 문구·순서까지 같은가 · 강조된 부가 `Ⅲ`인가.

결과: `deck-final.pptx — 19장 · 결함 0건`.

게이트가 실제로 무는지 확인한 실측 — s04의 내비 강조를 지우자
`s04 부 내비 강조가 0개다 — 정확히 하나여야 한다`가 즉시 나왔다.
