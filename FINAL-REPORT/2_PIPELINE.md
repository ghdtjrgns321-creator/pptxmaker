# 2. PIPELINE — 입력(FINAL-REPORT)에서 종착(.pptx)까지

> 이 장은 전체 흐름 1장짜리 지도다. 각 단계의 세부 규칙은 상세 장([3_OUTLINE-GRILL.md](3_OUTLINE-GRILL.md)~[8_QA-GATES.md](8_QA-GATES.md))에 위임하고, 여기서는 단계당 1문단까지만 쓴다.
>
> **정직 고지**: 아래 배선은 스킬·에이전트·스크립트 실존이 실측으로 확인된 현행 구조다. 다만 이 흐름을 끝(`results/`)까지 PASS로 완주한 실전 사례는 아직 0건이다. `results/k-ifrs1115/`에 남은 빌드 실물 3건은 전부 현행 골든 체계 이전이거나 QA FAIL 판정분이다([9_KIFRS-PILOT.md](9_KIFRS-PILOT.md)).

## 1. 두 개의 축 — 덱을 찍는 축, 창고를 채우는 축

이 시스템에는 서로 다른 흐름이 둘 있고, 읽을 때 섞으면 안 된다.

```
  [생산 축] 재료 → 덱                        [제작 축] 실물 레퍼런스 → 부품
  ─────────────────────────────             ─────────────────────────────
  FINAL-REPORT                               실물 슬라이드(ref/ · 웹)
      │ ① GRILL 인터뷰                            │ part-design 스킬
      ▼                                          ▼
  아웃라인 계약                               1층 원소  figures/elements.py
      │ ② composer                               │  (선·화살표·칩 — 자리를 모른다)
      ▼                                          ▼
  deck-spec  ◀── 창고에서 부품을 **고른다** ── 2층 도해  figures/*.py (부품 10종)
      │ ③ builder                                │  draw(slide, box, data, kit)
      ▼                                          ▼
  deck.pptx                                  3층 배치  배치 틀 6종 · 골든덱(조합 사례)
      │ ④ QA
      ▼
  results/<프로젝트명>-소개.pptx
```

- **생산 축**은 사용자가 PPT를 요청할 때 돈다(`pptmaker` 오케스트레이터). 이 장의 §2~§4가 그것이다.
- **제작 축**은 창고를 채울 때만 돈다(`part-design` 스킬). 덱을 만들지 않는다. 상세: [6_VISUALS.md](6_VISUALS.md).
- 둘이 만나는 지점은 **②**다 — 컴포저가 창고에서 부품을 고른다. 창고에 없는 물성이 나오면 즉흥으로 그리지 않고 **멈춰서** 제작 축으로 넘긴다. 그 즉흥이 "골든덱에 쓰인 적 없는 목업"으로 새던 경로다.

## 3. 단계 표

| 단계     | 실행 주체                     | 입력                       | 처리                                                             | 출력                                                | 상세 장                                  |
| -------- | ----------------------------- | -------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| ① 인터뷰 | deck-outline-grill(메인 대화) | FINAL-REPORT               | 목차 1안 제시 → 부·장 육성 채록 → 사용자 "확정"                  | `01.5_outline.md`(계약)                             | [3_OUTLINE-GRILL.md](3_OUTLINE-GRILL.md) |
| ② 구성   | deck-composer(에이전트)       | 계약 + FINAL-REPORT        | 선별·배치(창작 0), **부품·틀 선택**, 장 타입 판정, 장당 후보 3안 | `03_exhibit-candidates.json`                        | [4_DECK-COMPOSE.md](4_DECK-COMPOSE.md)   |
| ②.5 승인 | 사용자                        | 후보 사양서                | 실물 렌더 목업 갤러리 확인 → "sNN=X" 회신                        | `02_deck-spec.json` 확정                            | [4_DECK-COMPOSE.md](4_DECK-COMPOSE.md)   |
| ③ 빌드   | pptx-builder(에이전트)        | deck-spec + brand-kit.yaml | 4계열 디스패치 + 채움률·content 계약 + audit_deck                | `deck.pptx`                                         | [5_PPTX-BUILD.md](5_PPTX-BUILD.md)       |
| ④ QA     | consistency-qa(에이전트)      | 계약 + spec + deck.pptx    | check_contract(6종) → audit_pptx → 렌더 눈검증·정성 5항목        | `04_contract-check.md`·`03_qa-report.md`, PASS/FAIL | [8_QA-GATES.md](8_QA-GATES.md)           |

**①** 은 승인 게이트가 아니라 콘텐츠 인터뷰다 — 장별 "가장 전하고 싶은 것"을 육성으로 채록해 원문 그대로 계약에 싣고, 전 장이 "확정"되기 전에는 ②로 못 넘어간다. 계약에는 장 구성뿐 아니라 확정 이미지(md5 대조 대상)와 앵커 수치까지 박힌다. 재료 스캐너(`scan_material.py`)가 md에서 셀 수 있는 것을 미리 세어 두고, **셀 수 없는 것만** 물어볼 목록으로 넘긴다 — "이 표가 나열인가 좌우 대비인가"는 열 이름의 뜻을 읽어야 아는 것이라 기계가 판정하지 않는다.

**②** 는 창작이 아니라 선별·배치다. 그리고 **여기서 부품을 고른다** — 장의 재료를 축 5개(`sets`·`flow`·`order`·`extra`·`ends`)로 세어 창고의 부품 `accepts`와 **비교만** 한다. 산문을 읽고 "이건 흐름 같다"고 판정하는 경로는 없다. 맞는 부품이 없으면 억지로 붙이지 않고 멈춘다.

**③** 은 결정론 빌드다 — 같은 spec과 brand-kit이면 같은 .pptx가 나온다. 네 계열 전부에 시끄럽게 죽는 문이 하나씩 달려 있다: `composed`는 조립 결과가 얕으면 채움률로, `golden.*`는 content 누락으로, 레거시는 모르는 타입으로 죽는다.

**④** 는 "존재 확인이 아니라 교차 검증"이다 — 정답은 골든 기본값도 팩트시트도 아닌 계약(`01.5_outline.md`)이며, 계약 대조가 FAIL이면 나머지가 전부 PASS여도 판정은 FAIL이다. 되돌림은 1회로 제한되고, 재실패면 잔여 결함을 명시한 채 보고한다.

## 4. 장 타입 4계열 — 무엇을 언제 쓰나

| 계열               | 무엇                                                       | 골든과의 관계                           | 죽는 조건                                 |
| ------------------ | ---------------------------------------------------------- | --------------------------------------- | ----------------------------------------- |
| `composed`         | 배치 틀 + 부품으로 **조립**                                | 부품·틀만 빌린다. 장을 통째로 안 가져옴 | 모르는 틀·부품 / 도해 없음 / 채움률 <96%  |
| `golden.<layout>`  | 골든 장 구조가 그대로 맞는 장                              | 구조 그대로, 글은 전량 교체             | content 키 누락·빈 값(`content_contract`) |
| `adapted.<layout>` | 골든 장을 변형한 사본                                      | 장 스크립트를 spec이 지목               | `script` 경로 누락 / `build()` 없음       |
| `novel`            | 골든에 없는 새 장                                          | 밀도만 골든에 앵커                      | 동상                                      |
| 레거시 8종         | section·bullets·two_column·metrics·table·chart·diagram·cta | 무관(마스터 틀 스탬프)                  | 모르는 타입 ValueError                    |

`composed`가 2026-07-27에 생긴 이유는 실측이었다 — 실전 덱의 타입 분포가 골든 `SLIDE_ORDER`와 그대로 겹쳤다. 즉 "골든 장 통째 배정"이 실전 덱을 골든 복제로 만드는 **기계적 원인**이었다. `composed`는 자리는 틀이, 그림은 부품이 맡아 장 전체를 가져오지 않는다.

레거시 계열의 `cover`·`toc`·`part`는 2026-07-25에 폐기됐다 — 골든 프레임(`golden.cover`/`golden.toc`/`golden.part`)이 정본인데 v3 시절 사본이 남아 "어느 쪽이 표준인가"가 갈려 있었다. 지금 이 타입을 쓰면 unknown slide type으로 죽는다.

## 5. 실증 — 재현 가능한 기계 흔적

이 흐름은 아직 완주된 적이 없다. 대신 **지금 명령 한 줄로 재현되는** 구간이 셋 있다.

```
uv run python .claude/skills/pptx-build/scripts/scan_material.py FINAL-REPORT/
  → 73개 절을 세고, 축을 못 정한 47개를 "①GRILL이 물어볼 목록"으로 낸다

uv run python .claude/skills/pptx-build/scripts/verify_selection.py
  → ① 재현: 골든 도해 8장의 부품 선택을 재료만 세어 8/8 맞춘다
    ② 분리: 부품 10종이 축 5개로 9칸에 갈린다(겹침 1개는 개수로 해소)
    ③ 멈춤: 창고에 없는 물성 2건이 후보 0으로 멈춘다 — 억지 매칭 0

uv run python .claude/skills/pptx-build/scripts/compare_golden.py
  → 17/17장 · 797/797도형 · 불일치 0 PASS
```

**①의 의미**가 이 파이프라인의 핵심 주장이다. 골든 8장에서 사람이 손으로 골랐던 도해를, 재료를 세는 규칙만으로 다시 골라 전부 맞췄다 — 부품 선택이 취향이 아니라 재현 가능한 판정이라는 뜻이다. **③의 의미**는 그 반대편이다. 규칙이 아무거나 갖다 붙이지 않고 모르는 것 앞에서 멈춘다.

아직 없는 것은 이 셋을 **한 줄로 꿴 완주 1건**이다. 다음 작업이 그것이고, 막힐 지점은 이미 실측돼 있다 — `composed`를 ④ 검수층이 아직 모른다([8_QA-GATES.md](8_QA-GATES.md) 커버리지 갭).
