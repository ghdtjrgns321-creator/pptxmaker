# 8. 반려를 어떻게 축적하나 — 상속 루프

파이프라인 바깥의 축이다. 덱을 만들 때마다 반려가 나오고, 그 반려를 어디에 어떻게 남기느냐가
다음 덱의 품질을 정한다.

## 문제 — 양쪽 다 실패한다

```
 많이 쌓으면                        안 쌓으면
 ────────────────                  ────────────────
 규칙 639줄                         같은 지적을 매번 반복
 → 500줄 넘으면 무시된다            → 반려 비용이 매번 발생
 → lost in the middle
 → 구조가 바뀌면 통째로 죽는다
```

두 실패를 모두 겪었다. 그리고 **셋째 실패**를 실측에서 발견했다.

## 발견 — 규칙이 다음 반려를 낳았다

`design-rules.md`의 "재발 원인" 노트에 증거가 있다.

```
재발 원인: §8 초판이 4장을 공식으로 박음
재발 원인: 템플릿 지키려
재발 원인: 빈 곳을 채우려다 형제 장 내용 복제
재발 원인: "검은 바"로만 기억해 색을 바꿔 되살림
```

첫 줄의 경위를 복원하면 이렇다.

```
 사용자:  "이 장 밋밋해"                     ← 한 장에 대한 지적
 기록:    "카드 4장으로 채워라"              ← 모든 장의 명령으로 승격
 다음 덱:  모든 장에 카드 4장                ← 규칙을 충실히 지킴
 사용자:  "왜 다 똑같아?"                    ← 새 반려
 기록:    "4장 공식 폐기"                    ← 규칙 하나 더
```

**한 장면에서 나온 지적을 일반 명령으로 바꾸는 순간, 그 명령이 다른 맥락에 잘못 적용된다.**
그리고 그 잘못된 적용이 새 반려를 낳아 규칙이 또 늘어난다. 639줄이 된 메커니즘이 이것이다.

## 해법 ① — 부정형으로만 적는다

| 적지 않는다         | 적는다                                       |
| ------------------- | -------------------------------------------- |
| "카드 4장 써라"     | "밋밋한 카드 나열이 반려됐다"                |
| "2×2 매트릭스 써라" | "관계 이름만 적힌 표를 후보로 내밀지 않는다" |

앞엣것은 **무엇을 할지 정해준다** → 다음에도 같은 걸 한다.
뒤엣것은 **무엇을 하지 말지만 알려준다** → 무엇을 할지는 매번 그 장에 맞게 새로 찾는다.

**변환은 기록하는 쪽이 한다.** 사용자는 "밋밋해", "왜 다 똑같아"처럼 평소대로 말한다.

## 해법 ② — 배치 사다리 4층

새 반려가 나오면 **위에서부터** 내려갈 자리를 찾는다. 아래로 갈수록 약하다.

| 층              | 자리                          | 강제력                                            |
| --------------- | ----------------------------- | ------------------------------------------------- |
| 1 **부품**      | `dense.py`·`kit.py`·`grid.py` | 나쁜 원시도구를 없애 즉흥을 구조적으로 불가능하게 |
| 2 **게이트**    | `audit.py:generic_checks`     | `score_deck.py`가 물어 전 덱에서 강제             |
| 3 **왕복**      | ③④ 갤러리 선택 · ⑥ 눈검증     | 사람이 판정 — 건너뛸 수 없다                      |
| 4 **반려 목록** | `pptmaker/SKILL.md`           | 산문 — **무시될 수 있다**                         |

1층에 단서가 붙는다: **부품을 늘리는 것은 이제 기본 수단이 아니다.** 부품을 그대로 부르니
36장이 전부 같은 카드가 된 것이 2026-07-29 개편의 직접 원인이다. 부품은 재료로 두고 자리
계산(`grid`)과 원시도구(`kit`)만 공유한다.

### 4층이 최후 수단인 근거 — 실측

| 지시                                       | 결과                                       |
| ------------------------------------------ | ------------------------------------------ |
| "밋밋한 카드 쓰지 마"(산문)                | **반복 반려** — 여러 번 적혔는데 계속 당함 |
| 같은 것을 `check_adhoc_card`로 코드에 내림 | **재발 0**                                 |
| "구조를 정확히 읽어라"(산문)               | s05 오독                                   |
| 갤러리를 깔고 사용자가 고르게 함           | 오독 해결                                  |
| `design-rules` "반드시 읽어라" 639줄       | 무시됨                                     |

**산문으로 적힌 건 전부 무시됐고, 기계나 왕복으로 바뀐 건 전부 지켜졌다. 예외가 없다.**

## 해법 ③ — 지우는 시점은 추가하는 시점이다

새 반려를 적을 때 기존 줄을 훑어 아래에 해당하면 지운다.

- **기계가 잡게 됐다** — `score_deck`에 검사가 생기면 목록은 중복이다
- **대상이 없어졌다** — 구조가 바뀌어 그 상황 자체가 안 나온다
- **사용자가 번복했다**

따로 정리하는 날을 만들지 않는다 — **그날은 오지 않는다.** 2026-07-29 정리에서 죽은 참조가
90여 건 쌓여 있던 이유가 그것이다.

**숫자 상한은 두지 않는다.** 근거 없는 임계는 그 자체가 왜곡을 만든다 — 밀도 하한 535자가
텍스트 떡칠을 유도한 것과 같은 종류의 사고다([7](7_GATES.md)). 세 조건으로 지우면 자연히
짧게 유지되고, 안 짧아지면 그건 아직 유효한 줄들이라는 뜻이다.

## `deck-smith` — 배치를 판단하는 에이전트

덱을 만들지 않는다. **결함을 어디에 내릴지 판단해 제안까지만** 한다(코드로 내리는 것은 사용자
승인 후).

```
발견:   무엇이 왜 문제인가 (렌더 PNG·실측 근거)
배치:   사다리 어디에 내리나 + 왜 거기라야 재발이 멈추나 (국소 패치가 아닌 이유)
제안:   내릴 변경 (코드 위치·단일 출처)
정리:   통합한 중복 / 폐기 표시한 틀린 규칙 / 기계로 승격한 산문 (없으면 "없음 — 이유")
영향:   다음 덱이 무엇을 상속하나
경계:   기계로 강제 가능 vs 눈검증에 남는 부분 (정직하게)
```

`정리:` 칸이 핵심이다. **추가만 하고 삭제를 안 하면 이 에이전트를 만든 이유를 부정한다.**
판정 기준은 하나 — "이게 없어져도 내가 다시 배워야 할 게 있나?" 없으면 지운다.

## 외부 근거

이 설계는 우리만의 발견이 아니다. 검색으로 확인한 업계 관측과 일치한다.

- **500줄 넘는 규칙 파일은 대부분 무시된다** — 컨텍스트 예산을 먹고 "lost in the middle"로
  중간이 사라진다. 짧고 앞에 놓인 규칙이 더 잘 지켜진다.
- **제약 준수에서는 명시적 지시가 예시보다 효과적이다**(+11.1 대 +2.9 adaptedness). 예시는
  표면 형식 모방이라 형식은 배워도 제약은 안 지킨다 — 검토 중이던 "반려 그림첩" 안을 이
  근거로 접었다.
- **누적이 아니라 통제**(accumulation → control). Mem0류 메모리 시스템은 새 사실마다
  ADD/UPDATE/**DELETE**/NOOP 넷 중 하나를 고르고, 임계를 넘으면 중복 병합·모순 해소·낡은 항목
  제거를 발동한다. 우리 사다리에는 ADD만 있었고 DELETE가 사실상 작동하지 않았다.
- **비정상 환경에서는 축적된 경험이 해가 될 수 있다** — 조건이 바뀌면 옛 규칙이 실패한다.
  2026-07-29에 파이프라인을 갈아엎자 규칙 90여 건이 통째로 죽은 것이 그 사례다.
