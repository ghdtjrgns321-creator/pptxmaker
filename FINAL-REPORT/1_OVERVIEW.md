## 0. 정체 — 찍어내는 공장이자, 공장을 벼리는 루프

이 프로젝트는 두 얼굴이다.

**(1)** 손으로 깎은 골든 덱을 기준선으로 일관 서식 `.pptx`를 찍어내는 **공장**.

**(2)** 그리고 더 근본적으로 — 덱을 만들거나 **수정**할 때마다 그 과정에서 드러난 버그·배선 공백·부품 부재를 하네스의 **올바른 자리에 내려 다음 덱이 상속하게 하는, 사용자가 방향을 잡는 경화(硬化) 루프**.

공장은 **목표**, 루프는 그 공장을 신뢰 가능하고 **일정하게** 만드는 **방법**이다. 기계 게이트는 '정의된 결함'만 막는다 — 새 결함은 빌드하며 드러나고, 그걸 코드로 내리는 것이 `audit.py`의 철학(*"채점자는 검사기가 아니라 광산이다"*)이자 이 루프다. 국소 스킬에 패치를 덧대는 게 아니라 **배치 판단 사다리(부품 > 게이트 > 배선 > 훅 > prose)**로 재발이 멈추는 자리에 단일 출처·오탐 0·래칫으로 내린다.

이 루프를 수행하는 1급 객체가 **`deck-smith` 에이전트**다. 그리고 사다리의 맨 위 칸("부품")이 2026-07-26에 실물이 됐다 — 그전에는 도해가 전부 장 함수 안에 굳어 있어 **내릴 자리 자체가 없었다.** 결함을 발견해도 게이트나 산문으로만 내릴 수 있었다는 뜻이고, 부품 창고(`goldenfab/figures/`)는 그 칸을 여는 작업이었다.

실증: s16 한계 카드가 밋밋하게 반복 반려된 사고 → 원인은 "카드=hero_card 단일" 규칙이 prose로만 있고 기계 강제가 없던 것 → `check_adhoc_card`(§8) 게이트를 정본 `generic_checks`에 배선(통과작 전수 오탐 0 검증)해 밋밋 카드를 전 경로에서 차단(상세: [13_TROUBLESHOOTING.md](13_TROUBLESHOOTING.md)).

## 1. 문제 정의 — 어떤 실패를 막는 시스템인가

AI에게 "프로젝트 소개 PPT 만들어줘"라고 하면 반복적으로 나오는 실패는 네 갈래다. 이 시스템은 그 넷을 각각 다른 층에서 기계로 차단한다.

| 실패 유형                  | 증상                                                                                         | 이 시스템의 차단 장치                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **서식 비일관(드리프트)**  | 장마다 색·폰트·여백이 조금씩 다름. 수정할 때마다 산출물이 다른 모습으로 재생성됨             | 브랜드 SSOT `brand-kit.yaml` + "같은 spec = 같은 결과" + 수정은 항상 spec/brand-kit 경유 재빌드     |
| **AI티(피치 템플릿 밀도)** | 큰 글자·넓은 여백·불릿 나열 — 기관 문서가 아니라 스타트업 피치처럼 보임                      | 실측 밀도 규율(120~200단어/장) + 골든 덱 17장을 완성도 기준점으로 삼는 스냅샷 회귀·밀도 밴드        |
| **도해의 일회성**          | 매번 박스와 화살표를 새로 그림 — 다음 덱이 아무것도 상속 못 하고, 안 맞으면 범용 박스로 도망 | **부품 창고 10종**(임의 데이터로 부를 수 있는 재사용 단위) + 축 5개 선택 규칙 + **후보 0이면 멈춤** |
| **조용한 거짓**            | 근거 없는 수치 창작, 견본 텍스트가 산출물에 유출, 검증 게이트가 아무것도 안 보면서 PASS      | 창작 0 원칙 + `content_contract`의 빌드 중단 + 계약·spec·pptx 3자 대조 + `test_wiring`(배선 검사)   |

밀도 근거는 실측이다 — BCG NYCHA 111슬라이드: 단어/슬라이드 median 197(p25 145 · p75 252 · max 484), 텍스트 면적 median 35%, 제목 24pt·본문 불릿 12pt·각주 7~8pt. 같은 문서의 함의가 이 시스템의 문제 정의 그 자체다: **"큰 글자·넓은 여백 = 피치 템플릿(AI티). 작은 글자·높은 밀도·중첩 구조 = 기관 문서."**

세 번째와 네 번째 실패는 실제로 이 저장소에서 일어났던 일이다. **도해의 일회성**은 실측으로 드러났다 — 골든 11,867줄 중 재사용 가능한 부품이 479줄(4.0%)뿐이었고, 그래서 골든에 없는 형태는 손코딩 아니면 범용 박스 폴백으로 샜다. **조용한 거짓**은 계약 이행 0/8인 덱이 전 게이트를 PASS로 통과한 사고(2026-07-15 검출)로 나타났고, 그것이 현행 게이트 층의 직접 원인이다.

## 2. 왜 이 접근인가 — 대안 대비

| 결정        | 채택                                                                   | 기각한 대안                  | 근거                                                                                                   |
| ----------- | ---------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| 품질 기준   | **손으로 깎은 골든 덱 역설계** — 확정 판단을 규칙·코드·스냅샷으로 박제 | 규칙 더미 축적(상향식)       | "규칙은 나쁜 것을 막을 수 있지만 좋은 것을 만들지 못한다"                                              |
| 골든의 역할 | **조합 사례 + 회귀 기준**                                              | 복제 템플릿(텍스트 스왑)     | 실전 덱 타입 분포 = 골든 SLIDE_ORDER 실측 — 장 통째 배정이 복제의 기계적 원인이었다                    |
| 도해 단위   | **부품(`draw(slide, box, data, kit)`) + 배치 틀**                      | 장 함수에 도해를 굳혀 두기   | 굳어 있으면 임의 데이터로 못 부르고, 못 부르면 목업도 재사용도 안 된다(재사용 비율 4.0% 실측)          |
| 도해 선택   | **재료를 세어 축 5개로 비교**                                          | 모델이 물성을 판정           | 골든 8장 재현 8/8 — 사람의 선택이 규칙으로 설명된다. 판정을 두면 그림을 먼저 떠올리고 숫자를 맞춘다    |
| 부품 시각   | **실물 레퍼런스에서 옮긴다**(`part-design`)                            | 직접 설계                    | 자체 발명한 잉크 10종이 10라운드 전부 반려됐다(실측 약 6시간)                                          |
| 산출 형식   | **네이티브 .pptx**(python-pptx) — 표·차트가 편집 가능한 실객체         | 이미지/HTML 슬라이드 export  | "데이터만 고치면 자동 반영되는 것이 핵심 가치". 예외는 mpl 확장 9종뿐이며 편집 불가를 명시하고 쓴다    |
| 품질 강제   | **기계 게이트** — 스냅샷 회귀·계약 대조·오딧 러너·배선 검사            | 산문 체크리스트·자기 채점    | "산문 규칙은 잊히지만 assert는 건너뛸 수 없다". 자가채점 8/8 PASS가 제3자 채점에서 4건 FAIL로 기각됨   |
| 부채 처리   | **래칫(감소 전용)**                                                    | 빚 0 요구                    | 상시 적색 게이트는 무시당한다 — skeleton 검사가 전 덱 FAIL이던 시절 그건 검사가 아니라 소음이었다      |
| 콘텐츠 원천 | **사용자의 FINAL-REPORT 단일 원천** + 목차 인터뷰 계약                 | 파이프라인 내 추출·외부 생성 | 창작 0 원칙 — 근거 없는 수치는 쓰지 않고 "재료 부족"으로 보고                                          |
| 브랜드 관리 | **brand-kit.yaml 하나**(색 6·폰트 3·크기 8단)                          | 장·스크립트별 스타일 지정    | 코드 32파일이 전부 이 파일 하나에서 수급 — 파일 하나 수정 = 전체 반영, 그리고 하드코딩은 래칫이 막는다 |

**정직 고지**: 이 표의 장치들은 코드·배선이 실측으로 확인된 상태다. 그러나 이 파이프라인을 처음부터 끝까지 PASS로 완주한 실전 산출물은 아직 0건이다([9_KIFRS-PILOT.md](9_KIFRS-PILOT.md)).

## 3. 구속 구조 한눈

```
   brand-kit.yaml (색 6 · 폰트 3 · 크기 8단 — 브랜드 SSOT)
        │ load_kit (코드 32파일)
        ▼
 deck-spec.json ──▶ build_pptx.py ◀── goldenfab
   (구성 SSOT)          │  ▲            ├─ figures/  부품 10종 (도해)
                        │  │            ├─ frames.py 배치 틀 6종 (자리)
                        │  │            ├─ registry  레이아웃 15종 (골든 장)
                        │  │            └─ grid/kit  좌표·색 단일 출처
                        │  │
                        │  ├─ content_contract: 골든 글 유출 시 빌드 중단
                        │  └─ 채움률 96%: 조립이 얕으면 빌드 중단
                        ▼
                    deck.pptx ──▶ 게이트: check_contract · audit_pptx · audit_deck
                                          ▲
 golden-snapshot.json (17장 797도형) ─────┤ 밀도 밴드 파생(리터럴 0)
                                          └ compare_golden 회귀(goldenfab 보호 전용)
```

해설 1줄: 구성·브랜드·완성도 기준이 각각 단일 파일(spec·brand-kit·스냅샷)에 있고, 빌더와 게이트는 그 파일들을 읽기만 한다 — **사람이 pptx를 직접 고치는 경로는 설계상 없다.**

## 5. 기술 스택
