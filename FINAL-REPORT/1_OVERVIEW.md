# 1. OVERVIEW — 무엇을 막는 시스템이고, 왜 이렇게 지었나

> 이 장은 문제 정의 → 접근 선택(대안 대비) → 아키텍처 원칙 → 기술 스택 순서다. 파이프라인의 단계별 해부는 [2_PIPELINE.md](2_PIPELINE.md), 접근이 여기까지 온 이력(v1→v5·골든 전환)은 [12_JOURNEY.md](12_JOURNEY.md)에 과거형으로만 둔다.

## 1. 문제 정의 — 어떤 실패를 막는 시스템인가

AI에게 "프로젝트 소개 PPT 만들어줘"라고 하면 반복적으로 나오는 실패는 세 갈래다. 이 시스템은 그 셋을 각각 다른 층에서 기계로 차단한다.

| 실패 유형                  | 증상                                                                                                       | 이 시스템의 차단 장치                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **서식 비일관(드리프트)**  | 장마다 색·폰트·여백이 조금씩 다름. 수정 요청마다 산출물이 다른 모습으로 재생성됨                           | 브랜드 SSOT(단일 출처) `brand-kit.yaml` + "같은 spec = 같은 결과" + 수정은 항상 spec/brand-kit 경유 재빌드           |
| **AI티(피치 템플릿 밀도)** | 큰 글자·넓은 여백·불릿 나열 — 기관 문서가 아니라 스타트업 피치처럼 보임                                    | 실측 밀도 규율(120~200단어/장) + 손으로 깎은 골든 덱 17장을 완성도 기준점으로 삼는 골든 계열 빌드 경로               |
| **조용한 거짓**            | 근거 없는 수치 창작, 견본 텍스트가 산출물에 유출, 검증 게이트가 실제로는 아무것도 안 보면서 PASS를 찍는 것 | 창작 0 원칙(재료는 FINAL-REPORT·계약만) + `content_contract`의 빌드 중단 + 계약·spec·pptx 3자 대조(`check_contract`) |

밀도 근거는 실측이다 — BCG NYCHA 111슬라이드 실측: 단어/슬라이드 median 197(p25 145 · p75 252 · max 484), 텍스트 면적 median 35%, 제목 24pt·본문 불릿 12pt·각주 7~8pt(`.claude/skills/pptx-build/references/reference-metrics.md`). 같은 문서의 함의가 이 시스템의 문제 정의 그 자체다: **"큰 글자·넓은 여백 = 피치 템플릿(AI티). 작은 글자·높은 밀도·중첩 구조 = 기관 문서."**

세 번째 실패는 실제로 이 저장소에서 일어났던 일이기도 하다 — 계약 이행 0/8인 덱이 전 게이트를 PASS로 통과한 사고(2026-07-15 검출, 상세: [13_TROUBLESHOOTING.md](13_TROUBLESHOOTING.md))가 현행 게이트 층의 직접 원인이다.

## 2. 왜 이 접근인가 — 대안 대비

| 결정        | 채택                                                                        | 기각한 대안                  | 근거                                                                                                                                                                               |
| ----------- | --------------------------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 품질 기준   | **손으로 깎은 골든 덱 17장 역설계** — 확정 판단을 규칙·코드·스냅샷으로 박제 | 규칙 더미 축적(상향식)       | "규칙은 나쁜 것을 막을 수 있지만 좋은 것을 만들지 못한다"(docs/user/02-failure-analysis.md). 전환 이력은 [12_JOURNEY.md](12_JOURNEY.md)                                            |
| 산출 형식   | **네이티브 .pptx**(python-pptx) — 표·차트가 편집 가능한 실객체              | 이미지/HTML 슬라이드 export  | "값은 spec의 숫자 그대로 — 데이터만 고치면 자동 반영되는 것이 핵심 가치"(pptx-visuals SKILL). 예외는 mpl 확장 9종뿐이며 220dpi PNG·수치편집 불가를 명시하고 쓴다                   |
| 품질 강제   | **기계 게이트** — 스냅샷 회귀·계약 대조·오딧 러너·selftest                  | 산문 체크리스트·자기 채점    | "산문 규칙은 잊히지만 assert는 건너뛸 수 없다"(goldenfab/audit.py). 자기채점은 실측으로 기각됨 — 자가채점 8/8 PASS가 제3자 채점에서 4건 FAIL(pptx-build SKILL P4: 제3자 채점 강제) |
| 콘텐츠 원천 | **사용자의 FINAL-REPORT 단일 원천** + 목차 인터뷰 계약                      | 파이프라인 내 추출·외부 생성 | 창작 0 원칙 — 근거 없는 수치는 쓰지 않고 "재료 부족"으로 보고. 전반부 구조 폐기 이력은 [12_JOURNEY.md](12_JOURNEY.md)                                                              |
| 브랜드 관리 | **brand-kit.yaml 하나**(색 6·폰트 3·크기 8단)                               | 장·스크립트별 스타일 지정    | 코드 소비자 9종(build_pptx·goldenfab/kit.py·visuals·목업 2종·아이콘·audit_pptx·audit_golden·audit_deck)이 전부 이 파일 하나에서 수급 — 파일 하나 수정 = 전체 반영                  |

기계 게이트의 검출력은 실측돼 있다: GRID 상수 `MARGIN_L`을 0.6→0.61로 변조하면 compare_golden이 **197건**을 검출하고, brand-kit accent를 변조(D66E3A→00FF00)하면 **55건**을 검출한다(색을 못 보던 구 게이트는 같은 변조에 0건 — 490/490 통과였다. 상세: [8_QA-GATES.md](8_QA-GATES.md)).

**정직 고지**: 이 표의 장치들은 코드·스킬 실존과 배선이 실측으로 확인된 상태다. 그러나 이 파이프라인을 처음부터 끝까지 PASS로 완주한 실전 산출물은 아직 0건이다 — 유일한 실전 시도(K-IFRS 파일럿)는 QA FAIL 17건 후 동결됐다([9_KIFRS-PILOT.md](9_KIFRS-PILOT.md)).

## 3. 구속 구조 한눈

```
   brand-kit.yaml (색 6 · 폰트 3 · 크기 8단 — 브랜드 SSOT)
        │ load_kit (코드 소비자 9종)
        ▼
 02_deck-spec.json ──▶ build_pptx.py ◀── goldenfab (레이아웃 15종 · kit · grid)
   (구성 SSOT)              │  ▲
                            │  └─ content_contract: 골든 기본값 유출 시 ValueError 빌드 중단
                            ▼
                        deck.pptx ──▶ 게이트: check_contract · audit_pptx · audit_deck
                                              ▲
 golden-snapshot.json (17장 519도형) ─────────┤ 밀도 밴드 파생(리터럴 0)
                                              └ compare_golden 회귀(goldenfab 보호 전용)
```

해설 1줄: 구성·브랜드·완성도 기준이 각각 단일 파일(spec·brand-kit·스냅샷)에 있고, 빌더와 게이트는 그 파일들을 읽기만 한다 — 사람이 pptx를 직접 고치는 경로는 설계상 없다.

크기 단수는 HEAD 기준 **8단**(display·title·section·sub·head·body·caption·foot)이다. 작업 트리에는 고밀도 실험용 `compact: 19`가 1줄 추가돼 있어 9단이지만 미커밋이다(`git status` M — 상세: [9_KIFRS-PILOT.md](9_KIFRS-PILOT.md) §9.5).

| 3   | 창작 0                    | 본문 수치·문장은 FINAL-REPORT와 아웃라인 계약에서만. 재료가 얇으면 부풀리지 않고 부족을 보고 | deck-compose SKILL 원칙 + QA의 계약 대조                               |
| 4   | 골든 = 변형 가능한 출발점 | 복제 템플릿이 아니다 — 구조 일치면 golden.\*, 구획이 다르면 adapted.\*, 매칭 없으면 novel    | layout-matching 결정표 15타입 + build_pptx 3계열 디스패치              |

| 7   | 시끄럽게 죽는다           | 침묵 폴백 금지 — 누락은 그럴듯한 기본값으로 메우지 않고 예외로 빌드를 세운다                 | content_contract·s08 `_pitch` 수용 한계 ValueError 등                  |
| 8   | 수치는 이번 실행 결과만   | 게이트 수치를 기억·이전 리포트에서 복사하지 않는다                                           | consistency-qa 에이전트 규칙(스테일 수치 인용 금지)                    |
