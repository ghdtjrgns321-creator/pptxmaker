# 3. OUTLINE-GRILL — ① 목차·콘텐츠 인터뷰 게이트

> 파이프라인 첫 단계. FINAL-REPORT만으로는 알 수 없는 "사용자 머릿속의 강조점"을
> 개방형 질문으로 채록해 **아웃라인 계약(`01.5_outline.md`)** 으로 박제한다.
> 이 계약이 이후 모든 단계(컴포즈·QA)의 "정답"이 된다.
> 정의 원문: `.claude/skills/deck-outline-grill/SKILL.md`(66줄, 수치 상수 없는 순수 절차 스킬)

## 3.1 파이프라인 내 위치 — 왜 메인 대화가 직접 하나

```
 FINAL-REPORT ─▶ [① GRILL 인터뷰] ─▶ ② deck-compose ─▶ ②.5 승인 ─▶ ③ build ─▶ ④ QA
                 ████████████████
                 이 장의 범위 — 메인 대화(오케스트레이터)가 직접 수행
```

②~④는 서브에이전트가 맡지만 ①만은 오케스트레이터가 메인 대화에서 직접 수행한다. 이유는 단순하다 — **본체가 사용자와의 대화**이기 때문이다. 서브에이전트는 사용자에게 직접 질문을 던지고 답을 되받을 수 없으므로, 인터뷰가 정체성인 이 단계는 구조적으로 메인 대화에만 놓일 수 있다.

## 3.2 왜 이 게이트가 생겼나 (실측 근거)

골든 덱 제작 때 이 게이트 없이 진행한 결과, **S5 중복 삭제와 Part Ⅲ 재편이 전부 빌드 후에 발생**했다. 구성 반려 2건이 모두 "이미 렌더까지 마친 뒤" 나온 것이다. 텍스트 단계에서 한 번 물었다면 시안 반복 비용이 없었을 일 — 그래서 스킬 본문이 이렇게 박는다.

> "구조 승인이 아니라 콘텐츠 인터뷰가 본체다." / "구성은 빌드 전 텍스트 단계에서 확정하는 게 가장 싸다."

## 3.3 인터뷰 내부 흐름

```
 FINAL-REPORT(재료)
     │
     ├─ scan_material.py ── 표 행 수·목록 항목 수·화살표 수를 **기계가 먼저 센다**
     │                       (셀 수 없는 축은 _ask 목록으로 — §3.5)
     ▼
 [1] 목차 추천 1안 제시 ── 빈 종이에서 묻지 않는다(스킬이 먼저 던진다)
     │  사용자 수정/승인
     ▼
 [2] 부(섹션) 단위 강조 질문 ── 개방형 "가장 강조되는 점이 뭐야?"
     │  답변에 구성 정보가 나오면 되받아 확인
     ▼
 [3] 장 단위 전달 포인트 질문 ── 답변 원문 = 그 장의 핵심 메시지(의역 금지)
     │
     ▼
 [4] 새 재료 수집 ── "스크린샷 줄게" → 워크스페이스 편입 + 출처 기록
     │
     ▼
 [5] 반복(한 번에 질문 하나) ──┬─ 중복 감지 ─▶ 삭제/병합 먼저 제안
     │                         └─ 재료 없는 장 ─▶ 계약에서 제외(또는 재료 요청)
     ▼
 사용자 "확정" 발화 ─▶ 01.5_outline.md(계약) ─▶ ② deck-compose 진입 허용
```

종료 조건은 문장이 아니라 **사용자의 "확정" 발화**다 — 전 장 상태가 "확정"이 되기 전에는 ② 진행이 금지된다(부분 "보류"는 그 장만 재질문).

## 3.4 구조 표 — 질문 축·산출물·소비자

인터뷰 질문 축 3층:

| 축      | 질문 형태                            | 채록 대상                        |
| ------- | ------------------------------------ | -------------------------------- |
| 덱 전체 | 목차 추천 1안 → 수정/승인            | 목차·대상 독자·서사축            |
| 부 단위 | "이 부에서 가장 강조되는 점이 뭐야?" | 부별 강조점 + 구성 정보(되확인)  |
| 장 단위 | "여기서 가장 전해주고 싶은 게 뭐야?" | 장별 핵심 메시지(육성 원문 보존) |

산출물(아웃라인 계약)의 구성 요소:

| 구성 요소      | 내용                                                  | 개수 규칙         |
| -------------- | ----------------------------------------------------- | ----------------- |
| 헤더           | 대상 독자·목차(확정)·상태("확정" + 날짜·발화 근거)    | 1식               |
| 장 목록 표     | #·부·장 제목·전하고 싶은 것(채록 원문)·재료 출처·상태 | 장당 1행, 빈 칸 0 |
| 추가 재료 목록 | 인터뷰에서 받은 이미지 등 + 편입 경로                 | 받은 건 전부 기록 |
| 삭제·병합 이력 | 중복 감지로 지운/합친 장                              | 발생 건 전부      |

계약의 소비자(배선 실측):

| 소비자                  | 소비 방식                                     |
| ----------------------- | --------------------------------------------- |
| deck-composer 에이전트  | 장 구성·채록 메시지 준수(임의 추가·삭제 금지) |
| consistency-qa 에이전트 | "정답은 계약" — 계약 대조 FAIL이면 전체 FAIL  |
| `check_contract.py`     | 계약·spec·pptx 3자 대조의 1번 인자            |
| `content_contract.py`   | 에러 메시지에서 계약을 콘텐츠 출처로 지목     |

## 3.5 재료 스캐너 — 기계가 세고, 사람에게는 못 센 것만 묻는다

```
uv run python .claude/skills/pptx-build/scripts/scan_material.py FINAL-REPORT/
```

**이 스캐너가 하는 일**은 md 문법에서 셀 수 있는 것만 세는 것이다 — 표 행 수·열 수, 번호 목록·글머리 목록 항목 수, 코드펜스 안 화살표 수. 한 절에 여러 구조가 있으면 가장 큰 것을 그 절의 골격으로 보고 나머지는 `_others`로 남긴다.

**하지 않는 일**이 더 중요하다.

- **어느 절이 슬라이드가 되는지 고르지 않는다** — 그건 ① 인터뷰와 컴포저의 일이다.
- **의미를 읽지 않는다** — "이 표가 대비인가 나열인가"는 판정이고, 여기서는 열 수만 센다.

그래서 출력에 `_evidence`(무엇을 보고 세었나)를 붙인다 — 사람이 뒤집어 볼 수 있어야 한다.

**왜 기계가 세나.** 그 값을 사람이 손으로 적어 넣던 시절에 두 가지가 무너졌다. ① 사람이 그림을 먼저 떠올리고 거기 맞는 숫자를 적을 수 있다 — 판정을 앞으로 숨긴 것이다. ② 재현되지 않는다. 같은 보고서를 두 번 읽으면 두 번 다른 값이 나온다.

**파서를 똑똑하게 만들지 않는 것도 규율이다.** 셀 안 화살표를 전부 링크로 세면 15행 표가 1:N 방사로 잡히는 오판이 났다(실측). 그래서 "대부분의 행(≥80%)이 쌍일 때만" 구조로 인정하고, 소수 행의 화살표는 산문 표기로 보고 무시한다.

**못 센 것은 물어볼 목록(`_ask`)으로 나간다.**

```
■ 축을 못 정한 절 N개 — ①GRILL이 물어볼 목록
  <절 제목>  이 표가 그냥 나열인가, 두 쪽을 맞대어 비교하는 것인가 / 행에 순서(시간·단계)가 있나
```

이 설계의 요점은 **사용자가 도해 용어를 몰라도 답할 수 있다**는 것이다. "이건 옛날 방식과 비교예요"는 말할 수 있어도 "이 장의 물성은 좌우 대비입니다"는 못 한다.

**알려진 배선 공백**: 스캐너가 `_ask` 목록을 내지만 `deck-outline-grill` 스킬이 그것을 질문으로 쓰는 배선이 없다. 지금은 사람이 목록을 보고 인터뷰에 반영해야 한다 — 덱 한 벌 완주 시 막힐 지점 중 하나다(`상세: 8_QA-GATES.md` 커버리지 갭 4).

## 3.6 규칙

- **전 장 "확정" 전 ② 진행 금지.** 부분 보류가 남으면 그 장만 재질문한다.
- **채록 원문 보존** — 육성 답변을 컨설팅 어투로 다듬는 것은 deck-composer의 일이고, 계약에는 원문이 남는다. 요약·의역이 강조점을 왜곡하는 것을 막는 장치다.
- **재료 없는 장은 계약에 넣지 않는다** — "추가 추출할까/재료 줄래?"를 먼저 묻는다.
- **내부 용어 검사** — 장 제목·메시지에 독자가 모를 내부 용어가 보이면 인터뷰 중 "독자 언어로 바꿀까?"를 묻는다.
- **후속 수정도 계약 경유** — "목차 다시/강조점 바꿔" 요청은 계약 파일을 수정한 뒤 ②부터 재실행한다. 완성물 직접 수정 금지 원칙과 같은 결이다.
- **자체 점검 4문항** — ① 전 장 육성 채록 빈 칸 0 ② 중복 메시지 없음 ③ "확정" 명시 ④ 추가 재료 출처 전부 기록. 하나라도 아니오면 인터뷰로 복귀.
- 진행 리듬은 **"한 번에 질문 하나"**.

**낡은 흔적 2건**(동작에는 영향 없음): 스킬의 계약 양식 예시 목차("문제 인식 → 기술 설명 → 차별점 → TEST 결과")는 차별점 부 삭제 이전 구성이고, 워크스페이스 경로 표기가 `_workspace/`로 남아 있다(실물은 프로젝트별 워크스페이스).

## 3.7 이 게이트가 실제로 돌았던 유일한 사례

K-IFRS 1115 파일럿의 계약(`_workspace_kifrs/01.5_outline.md`, 2026-07-14 확정)이 이 인터뷰의 유일한 실물이다. 확인되는 것 셋만 여기 적고 전말은 [9_KIFRS-PILOT.md](9_KIFRS-PILOT.md)에 위임한다.

1. **사용자가 기준을 직접 지정했다** — "README 순서 그대로". 추천안이 아니라 사용자 기준이 목차가 됐고, 대상 독자·서사축까지 계약에 채록됐다.
2. **병합 지시가 확정 발화가 됐다** — 사용자 조정 4건(S4+S5 병합, 검증 1장 유지, S16+S17 병합, 실제 사용 이미지)이 계약에 그대로 남았고 상태 줄이 "확정(사용자 병합 지시 = 확정 발화)"로 박혔다.
3. **계약이 나중에 정답지가 됐다** — 채록 단계에서 들어간 앵커 수치(등재 423·간선 2,694·78/92·59.1%)와 확정 이미지 3종이 ④ QA에서 `check_contract`의 대조 대상이 됐고, **계약이 이미지를 지정했기 때문에** "네이티브 PICTURE 0"이 미덕이 아니라 FAIL 사유가 됐다. 계약 없이는 내릴 수 없는 판정이다.
