# 3. OUTLINE-GRILL — ① 목차·콘텐츠 인터뷰 게이트

> 파이프라인 첫 단계. FINAL-REPORT만으로는 알 수 없는 "사용자 머릿속의 강조점"을
> 개방형 질문으로 채록해 **아웃라인 계약(`01.5_outline.md`)** 으로 박제한다.
> 이 계약이 이후 모든 단계(컴포즈·QA)의 "정답"이 된다.
> 정의 원문: `.claude/skills/deck-outline-grill/SKILL.md`

## 3.1 파이프라인 내 위치

```
 FINAL-REPORT ─▶ [① GRILL 인터뷰] ─▶ ② deck-compose ─▶ ②.5 승인 ─▶ ③ build ─▶ ④ QA
                 █████████████████
                 이 장의 범위 — 메인 대화(오케스트레이터)가 직접 수행
```

②~④는 서브에이전트(deck-composer·pptx-builder·consistency-qa)가 맡지만, ①만은
오케스트레이터가 메인 대화에서 직접 수행한다(`deck-outline-grill/SKILL.md` frontmatter).
이유는 단순하다 — **본체가 사용자와의 대화**이기 때문이다. 서브에이전트는 사용자에게
직접 질문을 던지고 답을 되받을 수 없으므로, 인터뷰가 정체성인 이 단계는 구조적으로
메인 대화에만 놓일 수 있다. 파이프라인 전체 그림은 `상세: 2_PIPELINE.md`.

## 3.2 왜 이 게이트가 생겼나 (실측 근거)

골든 덱(K-IFRS 1115) 제작 때 이 게이트 없이 진행한 결과, **S5 중복 삭제와 Part Ⅲ 재편이
전부 빌드 후에 발생**했다(`deck-outline-grill/SKILL.md:13-15`). 구성 반려 2건이 모두
"이미 렌더까지 마친 뒤" 나온 것이다. 텍스트 단계에서 한 번 물었다면 시안 반복 비용이
없었을 일 — 그래서 스킬 본문이 이렇게 박는다:

> "구조 승인이 아니라 콘텐츠 인터뷰가 본체다." / "구성은 빌드 전 텍스트 단계에서
> 확정하는 게 가장 싸다." — `.claude/skills/deck-outline-grill/SKILL.md:9,14-15`

## 3.3 인터뷰 내부 흐름

```
 FINAL-REPORT(재료)
     │
     ▼
 [1] 목차 추천 1안 제시 ── 빈 종이에서 묻지 않는다(스킬이 먼저 던진다)
     │  사용자 수정/승인
     ▼
 [2] 부(섹션) 단위 강조 질문 ── 개방형 "가장 강조되는 점이 뭐야?"
     │  답변에 구성 정보가 나오면 되받아 확인
     ▼
 [3] 장 단위 전달 포인트 질문 ── 답변 원문 = 그 장의 핵심 메시지(의역 금지)
     │
     ▼
 [4] 새 재료 수집 ── "스크린샷 줄게" → 워크스페이스 편입 + 출처 기록
     │
     ▼
 [5] 반복(한 번에 질문 하나) ──┬─ 중복 감지 ─▶ 삭제/병합 먼저 제안
     │                         └─ 재료 없는 장 ─▶ 계약에서 제외(또는 재료 요청)
     ▼
 사용자 "확정" 발화 ─▶ 01.5_outline.md(계약) ─▶ ② deck-compose 진입 허용
```

각 단계는 `.claude/skills/deck-outline-grill/SKILL.md`의 "진행 순서" 1~5를 그대로
옮긴 것이다. 종료 조건은 문장이 아니라 **사용자의 "확정" 발화** — 전 장 상태가
"확정"이 되기 전에는 ② deck-compose 진행이 금지된다(부분 "보류"는 그 장만 재질문).

## 3.4 구조 표 — 질문 축·산출물·소비자

인터뷰 질문 축 3층:

| 축      | 질문 형태                            | 채록 대상                        | 근거(SKILL.md) |
| ------- | ------------------------------------ | -------------------------------- | -------------- |
| 덱 전체 | 목차 추천 1안 → 수정/승인            | 목차·대상 독자·서사축            | 진행 순서 1    |
| 부 단위 | "이 부에서 가장 강조되는 점이 뭐야?" | 부별 강조점 + 구성 정보(되확인)  | 진행 순서 2    |
| 장 단위 | "여기서 가장 전해주고 싶은 게 뭐야?" | 장별 핵심 메시지(육성 원문 보존) | 진행 순서 3    |

산출물(아웃라인 계약)의 구성 요소:

| 구성 요소      | 내용                                                  | 개수 규칙         |
| -------------- | ----------------------------------------------------- | ----------------- |

| 장 목록 표     | #·부·장 제목·전하고 싶은 것(채록 원문)·재료 출처·상태 | 장당 1행, 빈 칸 0 |
| 추가 재료 목록 | 인터뷰에서 받은 이미지 등 + 편입 경로                 | 받은 건 전부 기록 |

## 3.5 규칙 (세부)

- **전 장 "확정" 전 ② 진행 금지.** 부분 보류가 남으면 그 장만 재질문한다(SKILL.md 규칙 1).
- **채록 원문 보존** — 육성 답변을 컨설팅 어투로 다듬는 것은 deck-composer의 일이고,
  계약에는 원문이 남는다(규칙 2). 요약·의역이 강조점을 왜곡하는 것을 막는 장치.
- **재료 없는 장은 계약에 넣지 않는다** — "추가 추출할까/재료 줄래?"를 먼저 묻는다(규칙 3).
- **내부 용어 검사** — 장 제목·메시지에 독자가 모를 내부 용어('1홉 탐색' 류)가 보이면
  인터뷰 중 "독자 언어로 바꿀까?"를 묻는다(규칙 4).
- **후속 수정도 계약 경유** — "목차 다시/강조점 바꿔" 요청은 계약 파일을 수정한 뒤
  ②부터 재실행한다(규칙 5). 완성물 직접 수정 금지 원칙과 같은 결.
- **자체 점검 4문항** — ① 전 장 육성 채록 빈 칸 0 ② 중복 메시지 없음 ③ "확정" 명시
  ④ 추가 재료 출처 전부 기록. 하나라도 아니오면 인터뷰로 복귀(SKILL.md 자체 점검).
- 진행 리듬은 "한 번에 질문 하나" — grilling 원칙을 그대로 상속한다(진행 순서 5).

수치 상수가 없는 순수 절차 스킬이라 코드 대응 검사 대상은 없다. 다만 낡은 흔적이
하나 있다: SKILL.md의 계약 양식 예시 목차("문제 인식 → 기술 설명 → 차별점 → TEST
결과")는 차별점 부 삭제(2026-07-16 골든 5부 개편) 이전 구성을 예시로 유지하고 있다 —
규범이 아닌 예시라 동작에는 영향이 없다.

## 3.6 실증 예시 (walked example) — K-IFRS 1115 인터뷰 → 계약 확정

실물 계약 `_workspace_kifrs/01.5_outline.md`(2026-07-14 확정)로 인터뷰가 계약이 되는
과정을 추적한다. 주의: 이 파일은 작성 당시 워크스페이스가 `_workspace/`였던 시절의
산출물이라 내부 경로 표기가 전부 `_workspace/…`로 남아 있다 — **현 실물 위치는
`_workspace_kifrs/`** 이고, 문서 안 경로는 낡은 표기다.

**[1] 목차 확정** — 추천안 대신 사용자가 기준을 직접 지정했다: "README 순서 그대로".
그 결과 목차(확정)는 `문제 정의 → 파이프라인 → 기술 설명(4장) → 검증 → 핵심 의사결정`
5부가 됐고, 대상 독자는 "회계법인 채용 담당(나를 파는 포트폴리오 셀링 덱)", 서사축은
"painpoint → AI 해결 → 기술 선택"으로 채록됐다(`01.5_outline.md:3-5`).

**[2] 부·장 배분** — 총 16장. 표지·목차 2장 + 5개 부 각각 간지 1장 + 본문 배분:
Ⅰ 문제 정의 1장(S4), Ⅱ 파이프라인 1장(S6), Ⅲ 기술 설명 4장(S8~S11: 용어사전·
지식그래프·판단트리·구조화 출력), Ⅳ 검증 1장(S13), Ⅴ 핵심 의사결정 1장(S15) +
마무리(S16). Ⅲ부가 4장인 것 자체가 인터뷰 산물이다 — 골든의 Part Ⅲ 2장 압축을
사용자 지시로 README식 4장 확장으로 뒤집었다(`01.5_outline.md:45`).

**[3] 병합 지시 = 확정 발화** — 사용자 확정 조정 4건이 계약에 그대로 남았다
(`01.5_outline.md:37-41`): ① S4(2종 오류)+S5(범용 LLM 한계) → 1장 병합, ② 검증은
1장 유지(홀드아웃 성과+미재현 분해 함께), ③ S16(1115 선정·전환)+S17(임베딩 vs
온톨로지) → 1장 병합, ④ 실제 사용 이미지 사용(README 방식). 상태 줄은 "**확정**
(2026-07-14, 사용자 병합 지시 = 확정 발화)"로 박혔다.

**[4] 장 단위 채록의 실물** — 예컨대 S9(지식그래프) 행의 "전하고 싶은 것":
"기준서의 명시적 위계를 노드·간선으로. 개념80·문단250·사례188·간선2694. 뼈대는
기계생성(AI 판단 0), 결정적 1홉 탐색. 비슷한 것 추측 대신 연결된 것 추출"
(`01.5_outline.md:21`). 앵커 수치(등재 423·간선 2694·78/92·59.1%·리랭커 105중 103
탈락)가 채록 단계에서 이미 계약에 들어갔고, 이 수치들이 나중에 QA의 앵커수치 검사
대상이 된다.

**[5] 추가 재료 수집의 실물** — "README처럼 실제 사용 이미지·지식그래프 이미지 사용"
지시로 이미지 4종이 편입됐고 그중 3종이 배치 지정됐다: `screenshot_answer.png`→S6,
`knowledge_graph_3d.png`+`screenshot_graph_node.png`→S9, `screenshot_home.png`는
"예비"(`01.5_outline.md:31-35`). 계약에 적힌 경로는 `_workspace/images/`지만 실물은
`_workspace_kifrs/images/`다(경로 스테일). S16 재료 출처에 적힌 "골든 s17"은 현행
`goldenfab/reference.py` SLIDE_ORDER의 S17(closing)과 번호가 일치하므로, 구 19장 시절
표기인지 현행 지칭인지 단정할 수 없다(당시 SLIDE_ORDER 기록 부재 — `미검증`).

**[6] 계약이 정답이 된 순간** — 이 계약은 이후 ④ QA에서 check_contract.py의 1번
인자로 들어가 16장 덱과 3자 대조됐고, 2026-07-15 판정은 **FAIL — 계약 위반 17건**
이었다. 세는 단위는 `_workspace_kifrs/03_qa-report.md`가 명시한 대로 슬라이드 기준이다 —
골든오염 9(슬라이드당) + 계약 이미지 2(슬라이드당, 파일로는 3종) + 플레이스홀더
4(슬라이드×단어) + 앵커수치 2(슬라이드당) = 17.
계약이 확정 이미지 3종을 지정했으므로 "네이티브 PICTURE 0"이 미덕이 아니라 FAIL
사유가 됐다 — 계약 없이는 내릴 수 없는 판정이다. 파일럿은 그 후 재빌드 기록 없이
동결 상태다(`상세: 9_KIFRS-PILOT.md`).
