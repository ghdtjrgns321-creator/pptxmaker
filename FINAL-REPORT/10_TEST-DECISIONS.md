| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| **결정**        | 생산 코드를 아카이브하고 pptx + 렌더 PNG만 남긴다                                                                 |

| **후속 조치**   | 재생성이 불가능해졌으므로 `.gitignore`에서 풀어 **커밋 대상으로 전환**(pptx 1 + 렌더 44장)                        |

### ADR-4. 반려를 부정형으로만 축적한다

|                 |                                                                                                                      |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| **결정**        | "~해라" 금지. 반려당한 것을 그대로 적고, 대안은 매번 새로 찾는다                                                     |
| **검토한 대안** | ① 그림첩(반려 렌더 PNG 축적) ② 개수 상한 + 4연산 ③ 부정형 + 조건부 삭제                                              |
| **기각 ①**      | 연구상 제약 준수에서 예시는 지시보다 약하다(+2.9 대 +11.1). 예시는 표면 형식 모방이라 형식은 배워도 제약은 안 지킨다 |
| **기각 ②**      | 숫자 상한에 근거가 없다. 자의적 임계는 그 자체가 왜곡을 만든다(밀도 535자 선례)                                      |

### ADR-6. 조용한 폴백을 두지 않는다

|                 |                                                                                                                                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **결정**        | 모르는 `layout`은 `ValueError`. 항목이 수용 한계를 넘으면 `pitch()`가 빌드를 세운다                                                                                                                                                |
| **검토한 대안** | ① 기본 레이아웃으로 폴백 ② 경고 후 진행 ③ 즉시 중단                                                                                                                                                                                |
| **채택 이유**   | 폴백이 **어휘 수렴의 기계적 원인**이었다("어휘를 안 고르면 박스+화살표"). 그리고 `pitch`는 하한을 안 넘으면서 칩이 겹치는 **조용히 틀린 값**을 만든다 — 2026-07-15 케이스 테스트가 개념 18개에서 피치 0.109″ < 높이 0.24″를 잡았다 |

## 검증되지 않은 것

- **실전 완주** — 이 시스템의 핵심 주장("장마다 다른 형식이 나온다")은 2차 실험 9장으로
  뒷받침되지만, 재료 읽기부터 최종 산출물까지의 완주는 아직 없다.
- **다른 프로젝트 재료** — 지금까지 시험한 재료는 pptmaker 자신뿐이다.
- **브랜드 교체** — `brand-kit.yaml` 하나로 전 덱이 바뀐다는 주장은 코드 구조상 성립하지만
  실제로 다른 브랜드로 갈아끼운 기록이 없다.
