# 8. QA 게이트 — 오딧·검증층 전체

> 이 장은 검증층 전체를 다룬다: 어느 산출물에 어느 게이트가 물리는지(게이트 지도), 각 게이트가 실제로 보는 것, 커버리지가 닿지 않는 곳(정직 기재), 그리고 "규칙이 있어도 러너에 안 물리면 없는 규칙"을 막는 현재 장치.
> 전제: 이 프로젝트는 미완성이며 이 파이프라인으로 ④까지 통과한 실전 .pptx는 0건이다. 검증층의 유일한 실전 판정 기록은 K-IFRS 파일럿의 **QA FAIL(계약 위반 17건, 2026-07-15)**이다(상세: [9_KIFRS-PILOT.md](9_KIFRS-PILOT.md)).

## 8.1 게이트 지도

```
┌─ 보호 대상 ────────────────┐   ┌─ 게이트 ─────────────────────────────────────┐
│                            │   │                                              │

│                            │ └▶│ compare_golden (CLI) — 스냅샷 회귀           │

│                            │   │                                              │
```

역할 분담의 핵심: **compare_golden(스냅샷 회귀)은 goldenfab 보호 전용**이고, 실전 장은 스냅샷 대상이 아니다. 실전 장은 3겹으로 검증한다 — ① `audit_deck`(전역 오딧+밀도 밴드), ② P4 전 장 병렬 채점(FAIL 장만 재채점), ③ 창고 편입은 사용자 선택.

## 8.2 규칙의 단일 출처 — `generic_checks`

세 러너(`audit_deck` · `preflight_dense` · `build_pptx._gate_density`)가 **같은 함수 하나**를 부른다. "스킬별 경쟁 임계 신설 금지"가 규율이고, 실제로 `preflight_dense`가 자체 검사를 따로 갖고 있다가 통합됐다.

**프레임은 셋, 규칙은 하나.** 임계만 프로파일별로 갈리고 규칙 코드는 공유한다.

| 검사               | sparse | dense | legacy | 비고                                             |
| ------------------ | ------ | ----- | ------ | ------------------------------------------------ |
| §2 accent 상한     | ●      | ●     | ●      | dense·legacy는 런 제외(2단 불릿 **강조**는 정상) |
| P4⑤ 판정 단어 대비 | ●      | ●     | ✗      | legacy는 check_matrix 회색 ✓가 idiom → 오탐 4    |
| P4④ 채움률         | ●      | ●     | ✗      | legacy는 풀폭 배너가 구조상 26% → 오탐 1         |
| P4③ 노드 재탕      | ●      | ●     | ●      | `dup_allow`로 장별 예외                          |
| P4⑩ 노드 클래스    | ●      | ●     | ●      |                                                  |
| §F 그림 침범       | ●      | ●     | ●      |                                                  |
| 텍스트 넘침        | ●      | ●     | ●      |                                                  |
| 텍스트 겹침        | ●      | ●     | ●      |                                                  |
| P2③④ 경계          | ●      | ●     | ●      | 프레임별 하한이 다르다                           |
| §8 즉흥 카드       | ✗      | ●     | ●      | sparse는 카드 idiom이 다르다                     |
| §6-D 밀도 밴드     | ●      | ●     | ✗      | 골든 458자 하한은 legacy에 부적합 → 93/111 적색  |

**어느 검사를 어느 프로파일에 물릴지는 오탐 0 실측으로 정했다.** legacy 배선(2026-07-25)이 그 표본이다 — 산출물 111장 전수에 돌려 오탐 0인 부분집합만 물렸고, 미배선 3종은 억지로 물리면 상시 적색이 된다. **상시 적색은 무시당하고, 그건 이 프로젝트가 이미 겪은 우회 경로다.**

같은 판단이 `audit_pptx`의 skeleton 검사에도 적용됐다. 2026-07-25까지 리터럴 `["cover","toc"]`·`"cta"`만 봐서 **모든 현행 덱에서 상시 FAIL**이었다 — 골든 덱은 `golden.cover`/`golden.closing`이고 legacy `cover`는 폐기됐기 때문이다. 검사가 아니라 소음이었고, 접두사를 벗겨 판정하도록 고쳤다.

공용 임계: AIR_MIN 0.12 · ACCENT_MAX 4(dense·legacy는 완화) · CONTRAST_MIN 4.5(WCAG AA) · 채움률 min_ratio 0.30 · 한글 1자 ≈ 0.8×pt/72.

## 8.4 세부 — 게이트가 실제로 보는 것

### 8.4.1 compare_golden — 스냅샷 회귀

지금 빌드한 골든 덱을 `golden-snapshot.json`과 전수 대조한다. 비교 축: 도형 수 / type / text / fill(솔리드 fore_color, **enum 직접 대조 — str 비교 금지**) / run(첫 런 pt·bold) / run_colors(전 런) / cells(표 셀) / l·t·w·h ±0.005" / names 순서.

민감도 실측: MARGIN_L 0.6→0.61(0.01인치) 변조 시 **197건**, brand-kit accent 변조(D66E3A→00FF00) 시 **55건** 검출. 색 서명이 없던 구 게이트는 같은 변조에 **0건**이었다 — 형광 초록 덱이 회귀 게이트를 무사 통과하는 상태였다.

이 게이트가 못 보는 것도 명시돼 있다: **폰트 이름은 비교하지 않는다**(크기·볼드만). "형태가 내용에 맞나"도 못 본다 — 그건 P1(물성 선언)·P4(제3자 채점) 몫이다.

### 8.4.2 audit_golden — 레이아웃별 기대값 + 규칙 14종

골든 기본값으로 각 레이아웃을 렌더한 뒤 SPECS의 기대값을 건다. 검사 규칙 **14종**(실행 출력 실측): §5 진행형 도형 / §2 accent 상한 / P4⑤ 판정 단어 대비 / P4④ 채움률 / P4③ 노드 재탕 / P4⑩ 노드 클래스 / P4⑩ 검정 충돌 / P4⑧ 노드 높이 / §F 그림 침범 / §6 공기 / §8 즉흥 카드 / 텍스트 넘침 / 텍스트 겹침 / P2③④ 경계.

`generic_checks`(§8.2)와 겹치는 11종에 레이아웃 특정 4종(§5 진행형 도형 · P4⑩ 검정 충돌 · P4⑧ 노드 높이 · §6 공기)이 더 얹힌 형태다 — 골든은 기준선이므로 실전 장보다 두껍게 본다.

**known 래칫**: FAIL이어도 위반 수가 등록된 기준선 이하면 DEBT/GOOD으로 통과, 기준선 초과 시 FAIL. 알려진 빚을 기준선으로 박아 두고 **더 나빠지는 것만** 막는 설계다.

`--selftest` **16케이스**는 규칙 민감도를 뮤테이션으로 자체 검증한다. 절반이 **오탐 0 케이스**인 것이 특징이다 — 검출 케이스(셰브런·흐린 판정·그림 침범·클래스 충돌·§6-D 희소·텍스트 겹침) 6건과, 정상인데 잡으면 안 되는 케이스(산문·PICTURE 정상·같은 클래스·의도된 대조·골든 전수·좁은 라벨·fill 노드) 9건, 대비 산수 1건이다. **규칙이 결함을 못 잡아도 FAIL이고, 정상을 잡아도 FAIL이다** — 한쪽만 보면 "전부 FAIL을 내는 검사기"가 통과한다.

### 8.4.3 verify_selection — 부품 선택 규칙의 회귀

```
① 재현  골든 도해 8장의 선택을 재료만 세어 맞추나          → 8/8 일치
② 분리  축 5개로 부품이 칸에 갈리나                        → 10종 → 9칸(겹침 1은 개수로 해소)
③ 멈춤  없는 물성이 후보 0으로 멈추나                      → 2건 전부 멈춤(억지 매칭 0)
```

**②가 이 검사의 예방 기능이다.** 부품이 늘어 축이 창고를 못 가르게 되면 여기서 알려준다 — 두 부품이 같은 칸에 들어가면 선택이 임의가 되기 때문이다.

### 8.4.4 test_wiring — "규칙이 러너에 물렸나"를 검사하는 게이트

이 프로젝트에서 반복된 사고 유형이 하나 있다: **선언과 기계가 다른 것을 본다.** 결정표가 "(A) 먼저"라고 적었는데 판정 기계는 (B)만 후보로 올렸고, 채움률 규칙이 존재했는데 러너에 등록되지 않아 미러 매트릭스의 FAIL 9건이 방치됐다. `test_wiring`이 그 유형 전용 게이트다.

| 검사  | 무엇을 잇는지                                                             |
| ----- | ------------------------------------------------------------------------- |
| 가드  | content_contract 전 레이아웃 해석 + 두 문(golden·scripted) 배선           |
| 가드  | 오딧 읽기 전용 — 검사가 도형 XML을 변형하지 않음                          |
| 통합A | 밀도/검사 지표 단일 출처(preflight가 generic_checks 재사용, 중복 없음)    |
| 통합B | 결정표 단일 출처(layout-matching + 세 어휘 crosswalk)                     |
| 통합C | 카탈로그 렌더러 실존 — **hollow 행 금지**(L-ID 29종 전수)                 |
| 통합D | brand-kit 밖 hex 하드코딩 **래칫**(초과 = 신규 하드코딩)                  |
| 통합E | 골든 문법 축 등재 — 출처 실존·계약 키 실제 읽힘·항목수 래칫·결정표 양방향 |
| 통합F | dense 계약 구멍 **래칫**(주입해도 무시되는 키 22건, 증가 시 FAIL)         |
| 통합G | legacy 정본 게이트 배선 — fixture 31장 어휘 census + 오탐 0               |
| 통합H | (A) 우선 판정 기계화 — 추천 1순위=A · 유령 추천 0 · 의무 양방향           |
| 통합I | 부품 선택 규칙 배선 — 창고 census · accepts 전수 · 스킬 호출 · 회귀 green |

**양방향 검증이 이 게이트의 특징이다.** 예컨대 통합E는 카탈로그 등재 집합과 결정표 참조 집합이 **정확히 일치**해야 통과시킨다 — 유령 문법(참조는 있는데 실물 없음)도, 고아 어휘(실물은 있는데 아무도 안 부름)도 0이어야 한다.

**래칫 3종**(통합D·F, audit_golden known)이 이 프로젝트의 부채 관리 방식이다. 빚을 0으로 만들라고 요구하지 않고 **늘지 못하게** 막는다.

### 8.4.5 audit_deck — 실전 장 러너 + 밀도 밴드

spec에서 `golden.*`(정형 FIXED={cover,toc,part,closing} 제외)·`adapted.*`·`novel` 장을 골라 `generic_checks`를 적용한다.

**밀도 밴드는 리터럴 0**이다 — `golden-snapshot.json`에서 fixed 제외 본문 장의 도형 수·비어있지 않은 텍스트 프레임 수의 **최솟값을 파생**한다. 골든이 고밀도로 진화하면 실전 장의 하한도 자동으로 따라 올라간다. 장별 예외는 코드 수정 없이 spec의 `"audit": {"dup_allow": N, "known": {...}}` 선언으로 처리한다.

### 8.4.6 check_contract — "정답은 계약이다"

아웃라인 계약 vs deck-spec vs 빌드 pptx 3자 대조. 검사 6종:

| #   | 검사        | 무엇을 보나                                                                               |
| --- | ----------- | ----------------------------------------------------------------------------------------- |
| ⓪   | 장 수       | 계약 행 수 = pptx 장 수                                                                   |
| ①   | 제목 대조   | 계약 제목의 토큰이 슬라이드 텍스트에 실존(역할 라벨 행은 스킵)                            |
| ②   | 골든 오염   | spec type의 레이아웃 키로 **살아있는** `golden_defaults()`에서 len≥12 문자열 수집 후 대조 |
| ③   | 계약 이미지 | **md5 대조** — "아무 그림"이 아니라 그 그림                                               |
| ④   | 금지어      | My Company / 회사 로고 / Lorem ipsum / TODO / 샘플 텍스트                                 |
| ⑤   | 앵커 수치   | 계약 message의 수치 패턴이 슬라이드 텍스트에 실존                                         |

②가 살아있는 코드에서 골든 문자열을 뽑는 것이 요점이다 — 스냅샷 JSON을 쓰면 그 파일이 스테일이 되는 순간 검사가 hollow가 된다. 원칙 문장이 코드에 박혀 있다: **"정답은 계약이다. 골든 기본값·팩트시트 대응은 통과 근거가 아니다."**

### 8.4.7 Stop 훅 — 덱 작업이 하네스를 우회하는 것을 막는다

게이트 중 유일하게 **세션 자체**를 본다. 무장 2종을 `pptx_arm.py`가 세션 스코프로 기록한다.

```
① 소스 arm    goldenfab dense/build/audit 소스를 편집했다
              차단 = preflight red OR 렌더 스테일(편집 후 PNG 없음)
② 산출물 arm  이 세션의 명령이 .pptx를 저장/빌드/복사/렌더했다
              차단 = 대화 기록에 덱 에이전트의 **완료 실행**이 없음
```

②가 막는 것은 "메인 대화가 즉흥으로 덱을 만드는 것"이다. 덱 작업은 에이전트 루프를 경유해야 하네스가 상속되는데, 스크래치 우회가 하네스 전체를 잠재우던 구멍이 실측으로 드러났다.

**판정을 문자열 존재가 아니라 tool_use↔tool_result 페어링으로 한다.** 옛 방식(grep으로 에이전트 이름 존재 확인)은 **거부된 호출도 통과시켰다** — 거부돼도 tool_use JSON은 대화 기록에 남기 때문이다. 실증 후 실제 완료 판정으로 전환했다.

**자기 규제 장치도 있다**: 같은 시그니처로 3회 무진행 재차단되면 로그를 남기고 자동 통과 + 음소거한다. 근거는 이 프로젝트가 여러 번 확인한 것이다 — **상시 적색 게이트는 무시당한다.**

### 8.4.8 consistency-qa 에이전트 — 층의 지휘자

④ 단계의 실행 주체. 규칙: 실행 순서 강제(check_contract 먼저 → audit_pptx) / 계약 대조 FAIL이면 나머지 전부 PASS여도 판정 FAIL / **게이트 수치는 이번 실행 결과만 인용**(기억·이전 리포트 복사 금지) / 집합 주장에 분모 명시 / 되돌림 1회, 재실패면 잔여 결함 명시 후 전달.

"이번 실행 결과만"이 규칙이 된 이유는 사고다 — 스테일 산출물의 수치를 재측정 없이 복사해 "PASS"와 "501/501"을 보고한 기록이 있고, 뒤에 거짓으로 자백·정정됐다(`상세: 13_TROUBLESHOOTING.md`).

## 8.7 실증 — 규칙이 러너에 안 물려 방치됐던 FAIL 9건

이 층이 왜 이렇게 생겼는지를 보여주는 사례다.

**[1] 규칙은 있었다.** 채움률 규칙(P4④)이 design-rules에 문장으로 존재했다.

**[2] 러너에 등록되지 않았다.** 미러 매트릭스 레이아웃이 `audit_golden`의 SPECS에 없었다.

**[3] 그래서 아무도 못 봤다.** 그 장의 채움률이 14~29%였는데 FAIL 9건이 방치됐다. 규칙이 있고 위반이 있는데 검사가 안 돌았다.

**[4] 봉합.** `mirror_matrix`(ink_allow 8)·`boundary`(ink_allow 3)를 SPECS에 등록해 러너에 물렸다. 그리고 원칙이 코드에 문장으로 박혔다 — **"규칙이 있어도 러너에 안 물리면 없는 규칙"**(`audit_golden.py`).

**[5] 재발 방지가 게이트가 됐다.** 이 유형은 사람이 기억으로 막을 수 없으므로 `test_wiring`이 생겼다. 지금은 규칙을 신설하면 "스킬 호출 · 회귀 검증 · census"를 동시에 물려야 통과한다(통합I가 그 형태).

같은 원칙의 **미봉합 지점도 있다**: `golden/_pilot_s06/ref_anatomy.md`의 고밀도 규칙 R1~R12는 임계 표까지 있으나 design-rules·오딧 러너에 미등록이다 — 문서 스스로 "러너에 안 물리면 없는 규칙" 상태라고 적어 두었다.
