# 핸드오프 — 부품 선택 모델 재설계 (2026-07-26)

> **이 문서의 용도.** 부품 도구함의 **선택 기준**을 처음부터 다시 설계하기 위한 인수 문서다.
> 새 컨텍스트에서 이 파일만 읽고 시작할 수 있게 **실측으로 확인된 사실**과 **열린 질문**만 담는다.
> 추측·계획은 담지 않는다. 현재 상태의 정본은 `docs/PIPELINE.md`.

## 왜 새로 시작하나

`물성`(내용이 어떤 형태의 것인가)을 부품 선택의 단일 축으로 쓰던 설계가 **기준으로 부족**하다는
결론이 났다. 사유 3개 — 전부 실측이다.

1. **판정 질문이 배타적이지 않다.** "여기서 갈리나 / 대응되나 / 순서가 메시지인가"는 한 내용에
   둘 이상 참이 된다("3단계로 판정하고 애매하면 사람에게 넘긴다" → 순서·갈림·위임 모두 예).
   겹치면 결정이 모델 취향으로 넘어간다 — 기계 판정이 아니다.
2. **실제 1순위는 물성이 아니라 항목 수였다.** 등재 15종의 항목 수 계약은 **파생 5 · 고정 10**.
   고정 문법은 개수가 다르면 `zip`으로 **초과분이 조용히 잘린다**. 결정표 본문도 "항목 수 계약을
   먼저 보라"고 적어놨다 — 축이 둘인데 표 제목은 하나다.
3. **물성이 겹칠 때 우선순위 규칙이 없다.** (A)↔(B) 겹침 규칙은 있으나(=(A) 우선), 물성끼리
   겹칠 때는 없다. 현재 걸려 있는 사례: `hub_spoke`(1:N 소속·동등) vs `dense.hero_card`
   (순서 없는 독립 항목 N개·병렬) — 차이가 "중심이 있나" 하나뿐이다.

### 부품이 안 물려서 생긴 결과 (핵심 인과)

실전 덱 `_workspace_kifrs/02_deck-spec.json`의 타입 분포가 골든 `SLIDE_ORDER`와 **사실상 동일**하다
(`golden.cover`·`toc`·`part`×5·`problem_grid`·`exec_graph`·`tech_evidence`·`tech_tree`·
`tech_mechanism`·`tech_capture`·`validation`·`ab_simulation`·`closing`).

`PIPELINE.md`는 "골든은 이대로 글자만 갈아끼우는 정답지가 **아니다**"라고 못 박았는데 그 사용법이
실제로 일어났다. **기계적 원인**: 도해를 장에서 꺼낼 수 없으니(부품 0) 컴포저가 **장을 통째로**
배정할 수밖에 없다.

```
지금:      물성 판정 → 꺼낼 부품 없음 → 장 통째 배정 → 골든 복제
부품화 후:  판정      → 부품 꺼냄      → 3층이 새로 조합
```

`adapted.*`(항목 수 불일치 시 유일한 합법 경로) 사용 실적 **0건**. 즉 그 경로는 검증된 적이 없다.

### 골든 15종의 도메인 종속성 — 형태는 범용이다

형태 자체는 도메인 무관이다(◇판정 갈림 = 대출 심사·반품·채용 / N→1 수렴 = 이탈 원인 /
가로 공정+이탈 = 주문처리·온보딩 / N:M = 요구사항↔기능 / 1→N→M = 조직도 / 순위+컷 = 벤더 평가).

K-IFRS에 묶여 있는 것은 **둘뿐**이고, 부품 계약이 정확히 그것을 겨눈다:

| 묶여 있는 것                                                            | 떼는 계약 조건                     |
| ----------------------------------------------------------------------- | ---------------------------------- |
| 항목 수가 좌표 리터럴로 박힘 (고정 10종, `zip` 절단)                    | ② 개수 파생 (`grid.pitch`/`track`) |
| 글이 코드에 하드코딩 (`const:BRANCHES`·`const:STEPS_SHORT`·`const:OPS`) | ③ 글 무소유 (문자열 상수 0)        |

→ "K-IFRS 전용 세트"가 아니다. **부품화를 해야 범용이 되는 것**이고, 지금 도메인에 묶여 보이는
이유가 곧 부품화가 안 된 이유다.

## 제안된 새 모델 (미확정 — 검토 대상)

판정을 **모델이 하지 않는** 두 입력으로 가른다.

```
재료(FINAL-REPORT)   ──[센다]──▶  데이터 모양 ─┐
                                              ├─▶ 조건 맞는 후보 N개 ─▶ ??? ─▶ 확정
아웃라인 계약(①GRILL) ──[받는다]─▶  하고 싶은 말 ┘
```

- **데이터 모양**은 센다(판정 아님). **하고 싶은 말**은 ①에서 사용자가 이미 말한 것을 받는다.

### 데이터 모양 — 5축 (전부 셀 수 있음)

| 축      | 값                 | 어떻게 아나      |
| ------- | ------------------ | ---------------- |
| 항목 수 | n                  | 센다             |
| 집합 수 | 1 · 2              | 센다             |
| 관계    | 없음 · 1:N · N:M   | 센다             |
| 순서    | 없음 · 단계 · 시간 | 번호·날짜가 있나 |
| 값      | 없음(범주) · 수치  | 숫자가 붙어 있나 |

### 부품 선언을 산문에서 기계 조건으로

```python
ACCEPTS = {"집합": 2, "관계": "N:M", "순서": None, "값": None, "n": (2, 9)}
```

컴포저는 센 값과 이 조건을 **비교만** 한다(산문 해석 없음). 만들 부품 목록도 5축 조합표의
**빈 칸**에서 기계적으로 나온다 — 내가 "필요할 것 같다"고 지어내지 않는다.

## 열린 질문 (해결해야 할 것)

### Q1. 후보 중 하나를 고르는 규칙 — **최대 미해결**

위 모델은 후보를 좁히기만 하고 최종 선택을 ②.5 사용자 승인 게이트로 미룬다. 그러면 **매 슬라이드
사용자가 판정자**가 되어 자동화가 아니다. 기계화 가능한 축 후보(전부 셀 수 있음):

- 개수 적합도 — n이 부품 수용 범위의 어디쯤인가(중앙 ↔ 경계)
- 덱 내 중복 회피 — 이미 쓴 부품 재사용 억제(다양성 게이트가 이미 존재)
- 앞 장과의 대비 · 자리 밀도(몇 겹이 들어가나)

**이 규칙 설계가 새 세션의 1순위다.**

### Q2. 5축이 맞나
축을 더 늘리면 셀 수 없는 것이 섞일 위험, 줄이면 후보가 안 좁혀진다. 검증 방법: 골든 15종 +
(B) 9종 + 차트 13종을 5축으로 **실제로 분류해보고** 같은 칸에 여러 부품이 몰리는지 본다.

### Q3. "하고 싶은 말"을 축으로 넣을까
넣으면 물성이 재발한다(모델 판정 복귀). 안 넣으면 데이터 모양만으로 후보를 좁혀야 한다.
현재 판단: **넣지 않는다**를 기본으로 두고 Q1 규칙으로 대신 푼다.

### Q4. `hub_spoke` vs `hero_card` 중복 판정
차이가 "중심이 있나" 하나뿐이다. 카탈로그가 G18을 기각한 사유와 동형("차이가 배지 하나뿐 —
새 ID 신설은 중복"). 살릴지 흡수할지 판정 필요. 같은 사유로 `hub_spoke`의 `converge` 모드는
골든 `G02 cause_fanin`(N→1 수렴)과 물성이 같아 **제거 후보**다.

### Q5. 골든 13종 부품화 — 방법은 정해져 있고 순서만 남았다
장 함수의 도해를 `figures/*.py`로 꺼내고 장 함수는 부품 호출로 교체한다. 검증은
`compare_golden` **픽셀 동일** — 새 시각을 만드는 게 아니라 이미 승인된 시각을 그대로 꺼내는
것이므로 **디자인 반려 위험 0**이다. 대상(골든 유래 · `bipartite_map` 제외 12종):
`gate_branch`(s04) · `fan_in`(s04) · `pipeline_chain`(s06) · `decision_tree`(s11) ·
`node_tree`(s09) · `relation_catalog`(s09) · `numbered_steps`(s11) · `evidence_chain`(s14) ·
`rank_cut`(s14) · `asym_blocks`(s15) · `boundary_box`(s16) · `capture_ops`(s10).

### Q6. 도구함을 미리 다 갖출지, 프로젝트 재료를 보고 늘릴지
미리 갖추면 안 쓰이는 부품이 쌓인다(방금 6개 삭제한 경로). 재료를 먼저 세고 없는 것만
만드는 쪽이 안전하나, 그러면 첫 프로젝트에서 대기 시간이 생긴다.

## 되풀이하면 안 되는 실패 (전부 이번·직전 세션 실측)

1. **시각을 지어내기.** 자체 발명한 잉크 10종(채움 원·두꺼운 링·진한 파이·회색 칩·선끝 도트·
   밑줄 룰·비중 막대·폴라 막대·버블·게이지) 전부 반려. 약 6시간·10라운드 폐기.
   → 실물을 내려받아 `Read`로 직접 보고 옮긴다(`part-design` 스킬).
2. **1안씩 내놓기.** 방향 없는 반려만 돌아와 수렴하지 않는다. → 6~9개를 한 장에 깔고 번호로 고른다.
3. **배선 확인 없이 부품 만들기.** 이번 세션에 `hub_spoke`·`layer_stack`을 만들었는데 어떤 장도
   `figures/`를 import하지 않아 **덱에 들어갈 경로가 없었다**. 만들기 전에 꽂히는 자리를 확인한다.
4. **배치 치수에 상한을 두지 않기.** 자리(12.1"×5.9")를 그대로 반지름·폭으로 쓰면 노드가 화면
   네 귀퉁이로 흩어지고(scatter), 3층이 세 줄 표로 읽히고(layer_stack), 화살이 4.5"가 되어
   그림이 전부 선이 된다(converge). 상한은 자리가 아니라 **가독성**에서 온다. 남는 자리는
   비우고 `measure()`로 3층에 알린다.
5. **부품에 새 번호 발명.** 카탈로그 G번호와 충돌했다. 유일 키는 모듈 이름.
