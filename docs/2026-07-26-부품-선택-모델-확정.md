# 확정 설계 — 도구함 → 골든덱 → PPT 사슬 (2026-07-26 인터뷰)

> 핸드오프 `2026-07-26-부품-선택-모델-핸드오프.md`의 열린 질문을 사용자 인터뷰로 닫은 기록.
> **사용자가 확정한 것만** 적는다. 코드 변경은 전 항목 확정 + 승인 후.
> 진단: 사슬 세 칸(도구함 채우기 → 골든덱 → 그걸로 PPT 만들기)이 전부 안 정해진 상태였고,
> 그래서 "쓸데없는 데이터만 쌓였다". 세 칸을 순서대로 확정한다.

## 1칸 — 도구함을 어떻게 채우나

### D1. 방향 = 골든덱을 뜯어서 부품을 꺼낸다

실물 레퍼런스로 부품을 새로 만들어 골든덱을 다시 짓는 방향은 **택하지 않는다**.
이유: 골든 17장의 그림은 이미 사용자 승인을 받았으므로 디자인 반려 위험이 0이고, 창고가 한 번에
13종 늘어난다. 반대 방향은 직전 세션에 6개 만들어 6개 전부 반려된 경로다.

검증은 `compare_golden` **픽셀 동일** — 꺼낸 뒤 골든덱을 다시 찍어 이전과 같으면 무손실이다.

### D2. 단위 = 장 하나씩

한 장을 끝낼 때마다 (a) 그 장의 그림을 `figures/*.py`로 꺼내고 (b) 장 함수를 부품 호출로 바꾸고
(c) 골든덱 재빌드 픽셀 동일 확인 (d) 그 장이 부르던 시안 파일 삭제 — 여기까지 한 묶음이다.
중간에 멈춰도 골든덱이 정상 상태로 남는다. 그림 종류별로 묶는 방식은 여러 장을 동시에 열어
중단 시 골든덱이 깨진 채 남으므로 택하지 않는다.

### D3. 쌓인 것의 정체 — 별도 청소 작업이 아니다

`goldenfab` 10,640줄 중 약 4,900줄이 **시안 파일**(`*_variants.py`·`_variant_h`·`_variant_k`)이고,
죽은 게 아니라 **정본이 거기에 매달려 있다**:

    registry.py → s08_dense.py  → import s08_variants          (674줄)
                → s11_dense.py  → import s11_variants.DEFAULT   (1,031줄)
                → s14_dense.py  → import s14_variants as V      (681줄)

시안 파일에 K-IFRS 글과 도해 함수가 들어 있어서 지울 수 없는 상태다. 부품 계약 ③(글 무소유)로
글을 밖으로 밀어내면 정본이 시안을 부를 이유가 사라진다 — **부품화의 부산물로 삭제된다.**
완전히 죽은 것은 2개뿐: `s06_mid`(373줄, 미배선) · `s11_branch_snap`(164줄).

## 2칸 — 골든덱의 역할

### D4. 골든 장 15종은 골든 전용으로만 남긴다

실전 PPT에서 `golden.<layout>` 장 통째 지정을 **못 하게 막는다**. 그 지정이 골든 복제의 직접
원인이었다(실전 덱 타입 분포가 골든 `SLIDE_ORDER`와 사실상 동일했던 실측).

15종은 계속 살아 있되 쓰이는 곳은 둘뿐이다 — 골든덱을 찍는 것, 그리고 부품화가 무손실인지
확인하는 시험지. 실전 덱의 조립 어휘가 아니다.

골든덱을 틀로 다시 짓는 방향은 택하지 않는다 — 픽셀 동일 기준이 사라지면 D1의 검증 수단이
없어져 D2와 충돌한다.

### D5. 골든 17장은 배치 틀의 공급원이다

배치 틀은 새로 디자인하지 않고 골든 17장에서 4~5종을 추출한다(승인된 배치를 꺼내는 것이므로
반려 위험 0).

## 3칸 — 실전 PPT를 어떻게 만드나

### D6. 한 장의 조립 단위

    실전 한 장 = 배치 틀 1개 + 그림 1개 + 글

배치 틀은 그림을 모르고 자리만 안다. 슬라이드 한 장이 그림 하나가 아니라는 것(제목·핵심 메시지·
설명 패널·수치 띠·그림 크기와 자리)이 지금까지 장 통째 배정을 강제한 원인이고, 그림만 부품화해도
이 부분이 골든에 굳어 있으면 복제는 계속된다.

**추후 과제로 명시 — 배치 틀 도구함을 별도로 만든다.** 지금은 골든에서 4~5종을 뽑아 쓰지만,
도해 부품과 같은 지위의 창고가 되어야 한다(틀도 이름·계약·목업·눈검증을 갖는다). 그러지 않으면
틀이 다시 장 함수 안에 굳어 같은 문제가 재발한다. 착수 시점은 도해 부품 창고가 채워진 뒤.

### D7. 그림 선택 규칙 — 2단

부품마다 "이런 내용에 맞다"를 셀 수 있는 조건으로 선언하고, 그 장 내용을 세어 조건이 맞는 것만
후보로 올린다. 후보가 여럿이면:

1. **덱 내 미사용** — 이 덱에서 아직 안 쓴 부품을 먼저 쓴다. 같은 그림이 여러 장에 반복되는 것을
   선택 시점에서 막는다(consistency-qa의 사후 다양성 검사를 앞으로 옮긴 것).
2. **개수 적합도** — 1순위가 동점이면(덱 초반엔 전부 미사용이라 항상 동점) 항목 수가 부품 수용
   범위의 중앙에 가까운 쪽. 범위 경계에 걸려 헐거워지는 부품이 자동으로 밀린다.

사용자 판정은 이 두 단계로 가르지 않는다 — 자동화가 목적이므로.

### D8. 틀 선택 규칙 — 같은 방식

틀은 그림 크기만으로 못 고른다. 틀마다 **채워야 하는 칸**이 있고 그 칸을 채울 재료가 그 장에
있어야 성립한다. 그래서 틀마다 필요 재료를 선언하고, 재료가 있는 틀만 후보로 올린 뒤 D7과 같은
2단 규칙으로 고른다.

    틀 A  그림 + 오른쪽 설명 3줄     필요: 설명 문장 3개
    틀 B  그림 + 아래 카드 3개       필요: 짧은 항목 3개
    틀 C  위에 수치 띠 + 아래 그림   필요: 수치 2~4개
    틀 D  그림 하나만 크게           필요: 없음

수치가 FINAL-REPORT에 없으면 수치 띠 틀은 애초에 못 쓴다 — 취향이 아니라 재료에 달린 것이다.

**남는 위험과 대책:** 설명·카드를 억지로 만들어 원하는 틀을 성립시킬 수 있다. 설명·카드는
FINAL-REPORT 문장을 가져오게 하고 발명한 원문은 ④ consistency-qa의 원문 대조가 막는다.

### D9. 데이터 파일과 그림 결정을 분리한다

지금은 `deck-spec.json` 한 파일에 그림 종류와 데이터를 같이 쓴다. 한 시점에 둘을 쓰면 그림을
먼저 정하고 데이터를 거기 맞춰 적을 수 있어서, 뒤에서 세는 것이 규칙이 아니라 **사후 검산**이 된다.

    1단계 산출  그림 칸이 없는 데이터 파일   ← 재단이 물리적으로 불가능
    2단계 산출  deck-spec.json              ← 프로그램이 세서 그림·틀을 채운다

### D10. 후보가 0개면 멈추고 사용자에게 보고한다

가장 가까운 부품을 변형해 넘기지 않는다(`adapted.` 경로는 사용 실적 0건이라 검증된 적도 없고,
그렇게 만든 도해는 다음 덱이 상속하지 못한다). 미사항을 모아 한 묶음으로 보고하고, 부품을
만들지 항목을 줄일지는 사용자가 지시한다. 파이프라인 원칙 6(즉흥 금지)과 같은 취지.

## 축 확정 (2026-07-27 실측) — 핸드오프 Q2 해결

**축은 5개이고, 핸드오프가 제안한 5축과 다르다.** 지어내지 않고 부품 실물 9종을 분류해서
나온 결과다. 재현·회귀는 `verify_selection.py`가 진다(산문 주장 아님).

| 축      | 값                            | 어떻게 아나                        |
| ------- | ----------------------------- | ---------------------------------- |
| `sets`  | 1 · 2                         | 항목이 한 무리인가 두 무리인가     |
| `flow`  | 없음 · 1:N · N:1 · N:M · 순차 | 링크의 좌·우 중복도를 센다         |
| `order` | bool                          | 번호·날짜가 있나                   |
| `extra` | bool                          | 항목마다 설명·출처·태그가 딸렸나   |
| `ends`  | bool                          | N개를 감싸는 단일 머리/바닥(1→N→1) |

**`ends`는 실측으로 추가됐다.** 앞 4축에서 `numbered_steps`↔`layer_stack`이 같은 칸에 몰렸고
개수 범위까지 같아 2순위 규칙으로도 안 갈렸다. 둘의 실제 차이가 "층을 감싸는 정의 띠와
수렴 바닥이 있나"였고 그건 셀 수 있어서 축이 됐다.

핸드오프의 "항목 수"는 축이 아니라 **2순위 규칙**(개수 적합도)으로 갔다 — 축으로 두면 칸이
개수만큼 쪼개져 창고가 흩어진다. "값(수치)"은 뺐다 — 정량 물성은 부품이 아니라 차트(L-ID)가
정본이라 이 축에서 가를 대상이 아니다.
