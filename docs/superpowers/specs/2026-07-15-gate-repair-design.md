# 게이트 신뢰 복원 설계 — 계약을 정답으로

- 날짜: 2026-07-15
- 상태: 사용자 승인(2026-07-15)
- 범위: 0~3단계(검사기 복원). 4단계(덱 재구성)는 복원된 게이트 위에서 별도 진행.

## 배경 — 무엇이 일어났나

계약(`_workspace/01.5_outline.md`, 16장, 사용자 확정)에 8장 전부 "README §번호"와 실제 이미지
4종 배치가 "확정"으로 적혔다. 빌드된 덱에 반영된 것은 목차 순서와 장 제목뿐이다. 본문 글·이미지
반영 0. 그런데 ②.5 목업 승인 게이트·④ QA·회귀 게이트가 **전부 초록불**을 냈다.

### 근본 원인 — 게이트가 주문서를 안 본다

세 게이트 모두 "계약대로인가"가 아니라 **자기들끼리의 일관성**만 검사했다.

| 게이트         | 실제로 검사한 것             | 계약을 보는가 |
| -------------- | ---------------------------- | ------------- |
| compare_golden | goldenfab이 golden/과 같은가 | 아니오        |
| QA(정성)       | 수치가 FINAL-REPORT에 있는가 | 아니오        |
| 물성 assert    | (배선 0곳 — 작동 안 함)      | 아니오        |

QA 규칙서(`consistency-qa/SKILL.md:64`)의 근거 기준은 "숫자·고유명사가 FINAL-REPORT에 대응
(창작 0)"이다. 골든 기본값은 이 프로젝트(k-ifrs) 팩트시트로 만들어졌으므로 **FINAL-REPORT에
대응한다**. 그래서 QA는 규칙대로 하고도 PASS를 냈다. 규칙 자체가 구멍이었다.

### 증거 — 실측 (2026-07-15)

빈 장이 나오면 걸렸겠지만, **그럴듯하게 채워진 장**이 나온다.

## 골든 덱의 역할 (재정의)

모델하우스다. 제공하는 것은 셋뿐이다.

1. **틀** — 장 유형 15종의 시각 구조(배치·골격).
2. **서식** — 색·폰트·여백·밀도. 어느 프로젝트로 찍어도 같은 브랜드로 보이게 하는 것.
3. **회귀 기준점** — 레이아웃 코드를 고쳤을 때 서식이 깨졌는지 비교하는 잣대(compare_golden).

**골든의 글과 숫자는 공장 문 밖으로 한 글자도 못 나간다**(1단계). 짐 없는 방 = 빌드 에러.

## 사용자 지시가 지켜지는 경로 (재정의)

기존: 지시 → 계약에 적힘 → **끝(아무도 안 읽음)**.
변경: 지시 → 계약에 적힘 → **계약 표의 각 행이 검사 항목** → 위반 시 FAIL.

사용자가 확인할 문서는 **계약 하나**. 인터뷰 끝에 계약 표를 "확정"하면 그 뒤로는 적힌 것을
기계가 강제한다.

**한계(정직하게)**: 기계가 강제하는 것은 계약에 적힌 것의 **존재**까지다 — 이미지가 있나,
수치가 있나, 골든 글이 아닌가, 금지어가 없나. "README §3을 *잘* 요약했나"는 여전히 QA 정성
평가와 사용자 눈이 최종이다. 다만 이번 같은 **통째 무시**는 기계 단계에서 전부 걸린다.

## 3단계 — QA 재배선

`consistency-qa/SKILL.md`에 다음을 박는다.

- **스텝 1 = 계약 대조**. 계약을 먼저 읽고 `check_contract.py`를 실행한다. FAIL이면 이후 검사
  결과와 무관하게 리포트 판정은 FAIL.
- **근거 기준 교체**: "FINAL-REPORT에 대응" → "**계약이 지정한 출처에 대응**". 팩트시트에
  있다는 이유로 통과시키지 않는다.
- **확정 격하 금지**: 계약에 "확정"인 항목을 "사용자 선택 대기"·"원하면 추가 가능"으로 격하
  금지. 확정 항목 미이행 = FAIL.
- **스테일 수치 인용 금지**: 게이트 수치는 재실행 결과만 인용. 기억·이전 리포트에서 베끼지 않는다.
- **이미지 0을 미덕으로 쓰지 않는다**: "네이티브 도형" 칭찬은 계약이 이미지를 요구하지 않는
  장에만 유효.

## 5단계 — golden/ ↔ goldenfab/ 단일화 (완료 2026-07-15)

매번 세금이라 미루는 게 오히려 손해다.

### 왜 두 벌이었나 (조사 결과)

`docs/user/07`: *"골든 덱(19장, 동결 기준 원본)을 공장 레이아웃 엔진으로 **이식**한다. 검증은

**이식 공사용 비계였다.** 이식은 15/15·490/490으로 끝났는데 비계를 안 걷었고, "goldenfab에서만"
규칙도 깨져(S4 재설계 때 양쪽 수정) **1회성 이식 검증이 영구 동기화 세금**이 됐다.

(둘 다 같은 코드) 동기화 비용만 든다.

### 운영 규칙 (바뀐 것)

레이아웃을 **의도적으로** 바꿨으면 `compare_golden.py --update-snapshot`으로 기준선을 재생성하고
**git diff로 무엇이 바뀌었는지 리뷰**한다. 스냅샷 손편집 금지. "양쪽 다 고쳐라"는 폐기.

> `--update-snapshot`은 **오염된 상태도 정답으로 박제한다**(제3자 실증: 오염 brand-kit에서 실행
> → `00FF00` 60개가 기준선이 되고 게이트가 초록으로 바뀜). 방벽은 git diff 리뷰뿐이므로
> **스냅샷이 반드시 커밋 추적 상태여야 그 방벽이 성립한다** — 최초 감사 때 미추적이라 방벽이
> 무효였고, `git add`로 해소했다.

### 제3자 반증 결과 (5단계)

핵심 반증 시도는 "단일화로 검출력을 잃지 않았나"였다. 결론: **잃지 않았고 오히려 강화됐다.**

- 서명 함수 6개(`shape_sig`·`diff_shapes` 등) 구·신 **byte-identical** → 도형 단위 검출력 불변.
- **역방향 발견**: 구 게이트는 golden/kit.py와 goldenfab/kit.py가 **같은 brand-kit.yaml**을 읽어,
  accent를 `D66E3A→00FF00`으로 바꿔도 **490/490 PASS(완전 장님)**였다. 신 게이트는 같은 변조에
  **55건 검출**. 공유 입력 축에서 0 → 55.
- **동일성 증명(가장 강한 근거)**: git worktree에서 삭제된 `golden/` 트리를 실제로 빌드해 대조
